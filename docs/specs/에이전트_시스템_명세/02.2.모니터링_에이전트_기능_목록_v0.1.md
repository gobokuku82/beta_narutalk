# 모니터링 에이전트 기능 목록

| 항목 | 내용 |
|------|------|
| 담당자 | 도윤 |
| 분류 | 개발 - AI 에이전트 (자동화) |
| 진행상태 | 계획 |
| 버전 | v0.1 |
| 최종 수정일 | 2026-04-01 |

> 이 문서는 **모니터링 자동화 시스템**의 에이전트 기능 목록이다.
> 실행 에이전트(사용자 요청 기반)와 별도 시스템이며, Tool은 일부 공유한다.
> 추후 고도화 계획으로, 현재는 기능 나열 및 구조 설계 단계이다.

---

## 1. 실행 에이전트 시스템과의 차이

| | 실행 에이전트 시스템 | 모니터링 자동화 시스템 |
|--|---|---|
| 트리거 | 사용자 입력 ("분석해줘") | 크론잡 / 이벤트 / 이상치 감지 |
| 흐름 | Cognitive → Planning → Execution → Response | 수집 → 전처리 → 탐지 → 분류 → 조치/알림 |
| 성격 | 요청-응답 (1회성) | 상시 가동 (반복) |
| 4-Layer | 사용 | **사용하지 않음** |
| Tool 공유 | - | 수집/전처리/분석 Tool 일부 공유 |

---

## 2. 전체 구조

```
모니터링 자동화 시스템
  │
  ├── 모니터링 데이터 수집 에이전트
  │     └── 4대 매체 성과 데이터 주기적 수집
  │
  ├── 모니터링 전처리 에이전트
  │     └── 매체별 포맷 정규화 + 데이터 확정 관리
  │
  ├── 이상치 탐지 에이전트
  │     └── Rule-based → 통계 → ML 3단계 고도화
  │
  ├── 심각도 분류 + 자동 조치 에이전트
  │     └── Critical/High/Medium/Low 분류 → 캠페인 ON/OFF, 예산 조정
  │
  ├── 예산 분배 에이전트
  │     └── ROAS 기반 예산 자동 최적화
  │
  ├── 알림 에이전트
  │     └── 심각도별 멀티채널 알림
  │
  └── 총괄 관제 에이전트 (오케스트레이터)
        └── 에이전트 간 데이터 흐름 관리 + HITL 승인
```

## 3. 에이전트별 기능 상세

### 에이전트 1: 모니터링 데이터 수집

**역할**: 4대 매체(네이버, 카카오, 구글, 메타)에서 광고 성과 데이터를 주기적으로 자동 수집한다.

| 항목 | 내용 |
|------|------|
| 수집 대상 | CPC, CTR, ROAS 등 성과 지표 |
| 수집 주기 | 15~30분 배치 수집 |
| 계정 관리 | 잔액 부족, 광고 정지 등 5분 단위 헬스체크 |
| 매체별 분리 | 매체별 전용 워커로 독립 실행 |
| 장애 대응 | 신규 계정 연결 시 과거 60~90일치 백필(Backfill) |

**내장 기능:**
- Rate Limit 핸들링 (매체별 API 호출 토큰 버킷 관리)
- 429 에러 시 Exponential Backoff
- 매체 API 변경 대응을 위한 어댑터 패턴

**Tool 후보:**

| Tool | 유형 | 실행 에이전트와 공유 |
|------|------|:-:|
| `naver_ads_monitor` | tool/subgraph | △ (수집 로직 공유, 스케줄링 별도) |
| `kakao_ads_monitor` | tool/subgraph | - |
| `google_ads_monitor` | tool/subgraph | - |
| `meta_ads_monitor` | tool/subgraph | △ |
| `account_health_checker` | tool | - |
| `backfill_executor` | tool | - |

**사용 API:**
- 네이버 SearchAd API (GET /stats)
- 카카오 모먼트 API (GET /report)
- Meta Marketing API (GET /insights)
- Google Ads API (gRPC SearchStream)

### 에이전트 2: 모니터링 전처리

**역할**: 수집된 Raw 데이터를 정규화·통합하는 ETL 처리를 수행한다.

| 항목 | 내용 |
|------|------|
| 매체별 매핑 | 매체별 상이한 지표 명칭을 통합 체계로 자동 매핑 |
| 포맷 통일 | "클릭률" = 구글 "CTR" = 메타 "링크 클릭률" |
| 구조화 | 클라이언트별·매체별·기간별 구조화 → Single Source of Truth |
| 데이터 확정 | 매체별 데이터 확정 시점을 반영한 2단계 DB 설계 (staging → confirmed) |

**내장 기능 — 데이터 확정 판단 로직:**

| 매체 | 확정 시점 |
|------|----------|
| 네이버 | D+1 오전 8시 확정 (무효클릭 필터링 후) |
| 카카오 | 당일 데이터 변동성 높음 → 신뢰도 가중치 허용 |
| 메타 | 전환 데이터 최대 7일 후 소급 업데이트 |
| 구글 | 전환 데이터 최대 90일 소급 조정 |
| 미확정 데이터 | 기본 이상치 판단 시 오탐 방지를 위한 가중치 반영 |

**Tool 후보:**

| Tool | 유형 | 실행 에이전트와 공유 |
|------|------|:-:|
| `metric_normalizer` | tool | △ (`format_normalizer` 로직 공유 가능) |
| `kpi_format_parser` | tool | ✅ 공유 |
| `staging_confirmer` | tool | - |
| `data_freshness_checker` | tool | - |

**사용 기술:**
- ETL Pipeline (Python)
- PostgreSQL + TimescaleDB
- pandas / NumPy
- Cron Job (확정 시점별 재처리)

### 에이전트 3: 이상치 탐지

**역할**: 광고 성과 지표의 비정상 패턴을 감지하고 심각도를 판별한다.

**3단계 고도화 계획:**

| Phase | 방법 | 개발 기간 |
|-------|------|----------|
| Phase 1 (MVP) | Rule-based 규칙 감지 | ~2주 |
| Phase 2 | 통계 모델 (NeuralProphet, Z-Score) | 2~4주 축적 후 |
| Phase 3 | ML 고도화 (Isolation Forest, LSTM Autoencoder) | 3개월+ 축적 후 |

**Phase 1 규칙 예시:**
- 예산 급소진 (12시 이전 80%+ 소진 시 경고)
- ROAS 급락 (7일 동시간대 평균 대비 50%↓)
- CPA 폭등 (목표CPA × 1.5 연속 3회)
- 데이터 중단 (노출=0 또는 클릭=0 30분+)
- CTR 급변 (7일 동일 요일 평균 대비 ±40%, 단 누적 클릭수 ≥ 100)

**Phase 2 통계 모델:**
- NeuralProphet 또는 statsforecast (요일·시간대 시즈널리티 자동 학습)
- Z-Score + 7일 이동평균 (±2.5 이상 → 이상치)

**Phase 3 ML:**
- Isolation Forest: 다변량 이상치 + 부정클릭 탐지 (CTR+CVR↓ 패턴)
- LSTM Autoencoder: 재구성 오차 기반 시계열 이상치
- 목표 F1-Score: 0.75~0.85

**Tool 후보:**

| Tool | 유형 | 실행 에이전트와 공유 |
|------|------|:-:|
| `rule_based_detector` | tool | - |
| `statistical_detector` | tool | - |
| `ml_anomaly_detector` | tool | - |
| `kpi_trend_analyzer` | tool | ✅ 공유 |

**사용 기술:**
- Rule Engine (if-else 조건 테이블)
- NeuralProphet / statsforecast
- scikit-learn (Isolation Forest)
- PyTorch (LSTM Autoencoder)

### 에이전트 4: 심각도 분류 + 자동 조치

**역할**: 이상치 탐지 결과를 심각도로 분류하고, 등급에 따라 자동 조치를 실행한다.

**심각도 4단계:**

| 심각도 | 조건 | 자동 조치 |
|--------|------|----------|
| **Critical** | 예산 폭주(50%+ 초과), 전환=0 지출 지속, 계정·픽셀 장애 | 캠페인 자동 정지 (Circuit Breaker) |
| **High** | ROAS/CPA 지속 악화, 노출 급락, 부정클릭 의심 | HITL 승인 요청 + 예산 조정 제안 |
| **Medium** | CTR/CPC 미세 변동, 크리에이티브 피로 | 일일 리포트에 포함 |
| **Low** | 정상 범위 소폭 변동, 계절성 일시 변화 | 로그 기록만, 알림 미발송 |

**자동 조치 — 매체 API 연동:**

| 매체 | 캠페인 제어 API |
|------|---------------|
| 네이버 | PUT /ncc/campaigns, /adgroups, /keywords |
| 카카오 | PUT /campaigns/dailyBudgetAmount |
| 메타 | POST /campaign_id |
| 구글 | CampaignBudgetService.Mutate |

**안전 장치:**
- 매체 AI 충돌 방지 Guard (PMax, Advantage+ 등 자동입찰 모드 감지)
- 수동 입찰 캠페인 → 자동 조정 모드 활성화
- 네이버 자동입찰 확인 상태 체크 후 변경 여부 결정
- 변경 빈도·폭 안전가드 (시간 테스트 후 경계값 결정)

**Tool 후보:**

| Tool | 유형 |
|------|------|
| `severity_classifier` | tool |
| `circuit_breaker` | tool |
| `budget_adjuster` | tool |
| `campaign_controller` | subgraph |
| `safety_guard` | tool |

### 에이전트 5: 예산 분배

**역할**: 4대 매체 간 예산·입찰가를 자동으로 재분배하는 핵심 에이전트.

**3단계 고도화 계획:**

| Phase | 방법 | 설명 |
|-------|------|------|
| Phase 1 (MVP) | 휴리스틱 + HITL 승인 | ROAS 상위 20% → +20%, 하위 20% → -20% |
| Phase 2 | MAB Thompson Sampling | 캠페인×채널을 Arm으로, 80% Exploitation + 20% Exploration |
| Phase 3 | PPO 강화학습 | 상태(CTR,ROI,CPA,잔여예산,시간대) → 행동(유지/±10%/±20%) |

**안전 장치:**
- 모든 조정은 AE 승인 후 실행 (HITL)
- MVP 단계: 통합 운영, Phase 2 이후 트래픽 증가 시 분리 가능
- Clipping으로 극단적 예산 집중 방지
- 콜드 스타트 대응: SFT(2주) → Buffer(2~4주) → RL 이관(4주+)

**Tool 후보:**

| Tool | 유형 |
|------|------|
| `heuristic_allocator` | tool |
| `thompson_sampler` | tool |
| `ppo_optimizer` | tool |
| `budget_simulator` | tool |
| `cold_start_handler` | tool |

### 에이전트 6: 알림

**역할**: 심각도별 자동 알림을 멀티채널로 발송한다.

**심각도별 알림:**

| 심각도 | 알림 방식 |
|--------|----------|
| Critical | 즉시 알림 + 자동 정지 결과 통보 |
| High | HITL 승인 요청 (승인/거부 버튼 포함) |
| Medium | 일일 리포트에 원인 분석·대응 방안 포함 |
| Low | Slack·카카오톡·이메일 멀티채널 발송 |

**HITL 승인 흐름:**
```
AI 대응안 제안 → AE 알림 → 승인 버튼 → 매체 API 실행
거부 시 현 상태 유지 + 대안 재제시
예: "카카오 DA 예산 10만원을 메타 전환 캠페인으로 이동할까요?"
```

**액션 로깅:**
- 모든 자동 액션의 근거·결과를 설명 가능한 자연어로 기록
- 형식: [시간] 캠페인명 + 이상치 내용 + 조치 + 근거 규칙
- 승인/반려/수정 이력 추적 → 대시보드 데이터로 활용
- 법적 문제 대비 감사 로그(Audit Log) 보존 필수

**Tool 후보:**

| Tool | 유형 |
|------|------|
| `slack_notifier` | tool |
| `kakao_notifier` | tool |
| `email_notifier` | tool |
| `websocket_notifier` | tool |
| `hitl_approval_handler` | tool |
| `audit_logger` | tool |

**사용 기술:**
- Slack Webhook / Slack API (Interactive Buttons)
- 카카오 알림톡 API
- Email (SMTP / SendGrid)
- WebSocket (실시간 승인 UI)
- Action Queue (단일 대기열)
- PostgreSQL (action_log 테이블)

### 에이전트 7: 총괄 관제 (오케스트레이터)

**역할**: 전체 모니터링 에이전트를 조율하는 총괄 관제 에이전트.

| 기능 | 설명 |
|------|------|
| 이상치 탐지 결과 수신 | 심각도에 따라 적절한 에이전트 트리거 |
| 에이전트 간 데이터 흐름 관리 | 실행 순서 및 의존성 관리 |
| 최적화 액션 계획 생성 | JSON Action Plan 생성/배포 |
| 에이전트 장애 시 Fallback 처리 | 장애 감지 → 대체 경로 실행 |
| HITL 통합 관리 | AE 알림 발송 + HITL 승인 관리 + 액션 로그 기록 통합 |

**사용 기술:**
- LangGraph (멀티 에이전트 오케스트레이션)
- LangChain
- CrewAI
- WebSocket (실시간 상태 관리)
- JSON Action Plan

## 5. 모니터링 시스템 전체 흐름

```
[크론잡 / 15~30분 주기]
        │
        ▼
모니터링 데이터 수집
  (4대 매체 API → Raw 데이터)
        │
        ▼
모니터링 전처리
  (정규화 → 매핑 → staging → confirmed)
        │
        ▼
이상치 탐지
  (Phase 1: Rule → Phase 2: 통계 → Phase 3: ML)
        │
        ▼
심각도 분류
  (Critical / High / Medium / Low)
        │
        ├── Critical → Circuit Breaker (자동 정지) → 알림
        ├── High → 예산 분배 에이전트 + HITL 승인 요청 → 알림
        ├── Medium → 일일 리포트 포함 → 알림
        └── Low → 로그 기록만
        │
        ▼
총괄 관제 (오케스트레이터)
  전체 흐름 조율 + HITL 관리 + 액션 로깅
```

## 6. 미확정 사항

| 항목 | 선택지 | 결정 시점 |
|------|--------|----------|
| 오케스트레이터 프레임워크 | LangGraph vs LangChain vs CrewAI | 프로토타입 후 |
| 예산 분배 Phase 2~3 시작 시점 | 데이터 축적량에 따라 | 2~4주 운영 후 |
| 이상치 탐지 Phase 2~3 시작 시점 | 히스토리 축적량에 따라 | 2~4주 운영 후 |
| 매체 AI 충돌 방지 범위 | PMax/Advantage+ 감지만 vs 자동 대응 | 매체별 테스트 후 |
| 알림 채널 우선순위 | Slack 우선 vs 멀티채널 동시 | 사용자 선호 확인 후 |
| 실행 에이전트와의 통합 수준 | 완전 별도 vs Tool 레이어 공유 vs 통합 관제 | 두 시스템 모두 MVP 완료 후 |
