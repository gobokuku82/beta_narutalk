# State 설계 규칙

> 이 문서는 **State를 언제, 왜, 어떤 기준으로 나누는가**를 정의하는 상위 규칙이다.
> 개별 State의 필드 정의·R/W 매트릭스·Reducer 등은 [State 명세서 작성 가이드](langgraph_state_명세서_가이드_260329.md)를 따른다.

---

## 1. 문서 체계에서의 위치

```
[이 문서] State 설계 규칙
   "State를 몇 개 만들고, 각각의 범위는 어디까지인가"
   "그래프/서브그래프 경계를 어떻게 나누는가"
        ↓ 경계가 정해지면
State 명세서 작성 가이드
   "정해진 State 하나를 어떻게 문서화하는가"
        ↓ 가이드에 따라
개별 State 명세서 (산출물)
   "Main State 명세서", "Execution State 명세서", ...
```

---

## 2. 핵심 원칙

### 2.1 그래프 = State = 명세서

| 개념 | 의미 |
|------|------|
| 그래프 1개 | State(TypedDict) 1개 |
| 서브그래프 1개 | 별도 State(TypedDict) 1개 (선택) |
| State 1개 | 명세서 3종 세트 1개 (State 명세서 + Interface Contract + Pydantic 정의서) |

**서브그래프는 자체 State를 가질 수도 있고, 부모 State를 그대로 쓸 수도 있다.**
자체 State를 만들면 → 명세서가 필요하다.
부모 State를 쓰면 → 부모 명세서의 R/W 매트릭스에 노드를 추가한다.

### 2.2 노드와 State의 관계

노드는 State를 **상속하지 않는다**. 노드는 함수이고, State 전체를 dict로 받아서 필요한 필드만 꺼내 쓴다:

```python
# 노드 = 그냥 함수
async def my_node(state: AgentState) -> Command:
    # State 전체가 들어옴. 필요한 것만 꺼냄
    plan = state["plan"]          # 읽기
    todos = state["todos"]        # 읽기

    # 필요한 것만 업데이트
    return Command(update={"execution_results": result})  # 쓰기
```

**코드 레벨에서 "이 노드는 이 필드만 접근 가능"이라는 제한은 없다.**
→ R/W 매트릭스(명세서)로 규칙을 문서화하고, 리뷰로 강제한다.

## 3. State 분리 규칙

### 3.1 판단 기준

| 질문 | "예"이면 | "아니오"이면 |
|------|---------|------------|
| 이 노드 그룹이 서브그래프로 분리되는가? | 별도 State 후보 | 부모 State 사용 |
| 이 데이터를 부모 그래프가 알 필요 있는가? | 부모 State에 둠 | 서브그래프 State에 둠 |
| 이 데이터가 Checkpoint에 매번 저장되어야 하는가? | 부모 State에 둠 | 서브그래프 State에 둠 |
| 이 노드 그룹만 사용하는 필드가 3개 이상인가? | 분리 신호 | 분리 불필요 |

### 3.2 분리해야 하는 경우

**신호 1: 특정 노드 그룹 전용 필드가 많아짐**

```
Main State에 이런 필드가 쌓이면:
  agent_messages        ← Execution 전용
  intermediate_data     ← Execution 전용
  current_agent_id      ← Execution 전용
  agent_retry_count     ← Execution 전용

→ Execution을 서브그래프로 분리하고 자체 State를 만든다
```

**신호 2: 중간 데이터가 Checkpoint를 비대하게 만듦**

```
agent A → 중간 결과 10MB → agent B → 최종 결과 1KB

중간 결과가 Main State에 있으면:
  → 매 Checkpoint마다 10MB 저장
  → 다른 레이어(Cognitive, Response)에겐 불필요한 데이터

→ Execution 서브그래프 State에서만 다루고, Main에는 최종 결과만 올린다
```

**신호 3: Agent 간 소통용 데이터가 필요함**

```
Agent A, B, C가 서로 메시지를 주고받는 경우:
  → 이 메시지는 Execution 내부에서만 의미 있음
  → Main State에 둘 이유 없음

→ Execution 서브그래프 State에 messages 필드를 둔다
```

### 3.3 분리하면 안 되는 경우

| 상황 | 이유 |
|------|------|
| 노드 1개만을 위한 State | 노드 내부 로컬 변수로 충분. State는 노드 **간** 공유를 위한 것 |
| 부모 State와 필드가 거의 동일 | 복사·동기화 오버헤드만 늘어남. 그냥 부모 State 사용 |
| "나중에 필요할 것 같아서" | 필요할 때 만든다. 지금 안 쓰는 State는 관리 부채 |
| 필드 1~2개만 다른 경우 | 부모 State에 필드 추가가 더 간단 |

### 3.4 분리 결정 흐름도

```
"이 데이터를 여러 노드가 공유하는가?"
     │
     ├─ 아니오 → 로컬 변수로 처리. State에 넣지 않음
     │
     └─ 예 → "이 노드들이 같은 그래프에 있는가?"
                │
                ├─ 예 → 해당 그래프의 State에 필드 추가
                │
                └─ 아니오 (서브그래프) → "부모 그래프도 이 데이터가 필요한가?"
                              │
                              ├─ 예 → 부모 State에 둠
                              │
                              └─ 아니오 → 서브그래프 자체 State에 둠
                                          + Interface Contract 정의
```

## 4. 그래프 경계 설계

### 4.1 Dream Agent의 그래프 경계

```
Main Graph (orchestrator/)
  ├── cognitive_node          ← 순수 Python, Main State 사용
  ├── planning_node           ← 순수 Python, Main State 사용
  ├── execution (subgraph)    ← LangGraph, 자체 State 가능
  │     ├── agent 노드들
  │     ├── tool (함수)       ← 단일 기능. State 불필요
  │     └── tool (subgraph)   ← 복합 기능. 자체 State 가능
  └── response_node           ← 순수 Python, Main State 사용
```

### 4.2 State 계층과 데이터 흐름

```
Main Graph State (AgentState)
  │  가볍게 유지: 레이어 간 공유 데이터만
  │
  │  ┌──────────── Interface Contract ────────────┐
  │  │ Main → Execution: plan, todos              │
  │  │ Execution → Main: execution_results        │
  │  └────────────────────────────────────────────┘
  │
  ↓
Execution Subgraph State (별도 TypedDict)
  │  자유롭게: 내부 작업 데이터
  │  - agent 간 메시지, 중간 결과, 재시도 카운터 등
  │
  │  ┌──────────── Interface Contract ────────────┐
  │  │ Execution → Agent: todo, context           │
  │  │ Agent → Execution: result                  │
  │  └────────────────────────────────────────────┘
  │
  ↓
Agent State (필요 시 별도 TypedDict)
     - 복잡한 agent만 자체 State
     - 단순 agent는 Execution State 공유
```

**핵심: 데이터는 위로 자동 전파되지 않는다.**
서브그래프가 끝날 때 명시적으로 "이것만 올려보낸다"를 정의해야 한다.
이 정의 = Interface Contract.

### 4.3 서브그래프에 자체 State를 줄 때의 비용

| 항목 | 비용 |
|------|------|
| Interface Contract 작성 | 경계에서 뭘 넘기는지 문서화 필요 |
| 데이터 변환 | 부모 State → 서브그래프 State 매핑 코드 |
| 명세서 관리 | State 명세서 3종 세트 추가 |
| 디버깅 | State가 2개 이상이면 "데이터가 어디 있지?" 추적 필요 |

→ **비용을 감수할 만큼 분리의 이점이 있을 때만** 자체 State를 만든다.

## 5. State 생성 규칙

### 5.1 새 State를 만들 때 반드시 함께 만드는 것

```
새 State (TypedDict) 정의
  │
  ├── ① State 명세서         → graph_state_specs/{name}_state_명세서.md
  │     (필드, R/W 매트릭스, Reducer, 데이터 흐름도)
  │
  ├── ② Interface Contract   → 부모 그래프와의 데이터 전달 합의
  │     (입력: 부모에서 뭘 받는지 / 출력: 부모로 뭘 올리는지)
  │
  └── ③ Pydantic 정의서      → State 필드에 들어가는 모델 상세
        (타입, 검증 규칙, 직렬화 규칙)
```

### 5.2 State 이름 규칙

| 그래프 | State 이름 | 파일 |
|--------|-----------|------|
| Main Graph | `AgentState` | `states/agent_state.py` |
| Execution Subgraph | `ExecutionState` | `states/execution_state.py` |
| 특정 Agent | `{Agent명}State` | `states/{agent명}_state.py` |

### 5.3 State 필드 규칙

| 규칙 | 설명 |
|------|------|
| **JSON 직렬화 가능** | Checkpoint 저장을 위해 필수. datetime → ISO string 등 |
| **필드 하나에 책임 하나** | 하나의 필드가 여러 의미를 가지면 분리 |
| **큰 데이터는 참조만** | 바이너리, 대용량 데이터는 URL/경로만 저장 |
| **함수/객체 저장 금지** | 식별자만 저장, 런타임에 resolve |
| **`total=False` 기본** | 모든 필드 Optional. 각 필드의 "없을 때의 의미"를 명세서에 기록 |

### 5.4 새 State 추가 체크리스트

- [ ] 분리 판단 기준(3.1)을 검토했는가
- [ ] 분리하면 안 되는 경우(3.3)에 해당하지 않는가
- [ ] Interface Contract(부모 ↔ 서브그래프 경계)를 정의했는가
- [ ] State 명세서 3종 세트를 작성했는가
- [ ] 이 문서의 State 계층도(4.2)를 업데이트했는가
- [ ] 기존 State에 영향이 없는지 확인했는가

## 6. Agent 추가/수정/삭제 시 절차

### 6.1 새 Agent 추가

```
1. 소속 그래프 확인
   "이 agent는 어느 서브그래프에 들어가는가?"

2. 기존 State로 충분한지 판단
   "소속 그래프의 State에 필요한 필드가 있는가?"
   → 있으면: R/W 매트릭스에 새 노드 열 추가
   → 없으면: 필드 추가 or 자체 State 생성 판단 (3.1 기준)

3. 명세서 업데이트
   → 해당 State 명세서의 R/W 매트릭스에 새 agent 추가
   → Interface Contract에 새 agent의 입출력 추가
   → 필요 시 Pydantic 모델 추가
```

### 6.2 기존 Agent 수정

```
1. 영향 범위 파악
   → R/W 매트릭스에서 이 agent가 쓰는 필드 확인
   → 같은 필드를 읽는 다른 agent 확인

2. 필드 변경이 있으면
   → State 명세서 업데이트
   → 영향 받는 agent 목록 검토
   → Interface Contract 변경 여부 확인
```

### 6.3 Agent 삭제

```
1. R/W 매트릭스에서 이 agent 행 확인
   → 이 agent만 쓰던 필드 → 필드 삭제 후보
   → 이 agent만 읽던 필드 → 쓰는 쪽에 "읽는 곳 없음" 경고

2. 명세서에서 agent 제거 + 불필요 필드 정리
```
