## 1. 시스템 개요

### 1.1 Dream Agent란

Dream Agent는 광고대행사 퍼포먼스 마케터를 위한 **4-Layer + Manager 아키텍처** 기반의 AI 에이전트 시스템이다.

사용자의 자연어 입력을 **이해(Cognitive) → 계획(Planning) → 실행(Execution) → 시각화(Response)** 파이프라인으로 처리하며, 실행 레이어에서 복수의 전문 실행 Agent를 조율하여 데이터 분석, 보고서 생성, 광고 크리에이티브 제작 등을 수행한다.

### 1.2 핵심 설계 원칙

| 원칙 | 설명 | 이유 |
|------|------|------|
| **Layer Separation** | 각 레이어는 독립적 책임. 레이어 간 통신은 오직 State를 통해서만 | 레이어 교체/수정 시 다른 레이어에 영향 없음 |
| **Hand-off** | 각 레이어는 자기 일만 하고, 결과를 State에 쓰고, 다음 레이어에 넘긴다 | 단방향 흐름으로 디버깅/테스트 용이 |
| **Planning ≠ Execution** | Planning = "무엇을 할지" (Todo 문서), Execution = "어떻게 할지" (오케스트레이션) | 계획 변경 시 실행 코드를 수정할 필요 없음 |
| **Pure Python First** | 레이어 내부는 순수 Python. LangGraph 기능은 실제 필요할 때만 도입 | 불필요한 프레임워크 종속 방지 |
| **Manager Pattern** | 횡단 관심사(HITL, 메모리, 콜백 등)는 Manager 모듈로 분리 | 레이어가 비즈니스 로직에 집중 |
| **Hybrid State** | AgentState = TypedDict (성능), I/O·도메인 = Pydantic (검증) | 성능과 안전성의 균형 |

### 1.3 LangGraph 도입 범위

| Layer | 구현 방식 | 이유 |
|-------|----------|------|
| Cognitive | 순수 Python | 단방향 파이프라인. LangGraph 기능 불필요 |
| Planning | 순수 Python | Todo 문서 생성만 담당. LangGraph 기능 불필요 |
| **Execution** | **LangGraph** | HITL interrupt, Send(병렬), 루프, Checkpoint 모두 필요 |
| Response | 순수 Python | 결과 포맷팅만 담당. LangGraph 기능 불필요 |
| **레이어 간 배선** | **LangGraph** | Command hand-off, 조건부 라우팅, Checkpoint |

## 2. 4-Layer 아키텍처

### 2.1 Layer 요약

| Layer | 역할 | 핵심 질문 | 입력 | 출력 | 구현 |
|-------|------|-----------|------|------|------|
| **Cognitive** | 이해 | "사용자가 무엇을 원하는가?" | 사용자 원문 | 정제된 의도(Intent) | 순수 Python |
| **Planning** | 계획 | "무엇을 해야 하는가?" | Intent | Todo 리스트 + 의존 관계 | 순수 Python |
| **Execution** | 실행 | "어떻게 실행할 것인가?" | Todo 리스트 | 실행 결과(Agent별) | LangGraph |
| **Response** | 시각화 | "결과를 어떻게 보여줄 것인가?" | 실행 결과 | 포맷팅된 응답 | 순수 Python |

### 2.2 Cognitive Layer — 이해

**책임**: 사용자 입력을 분석하여 정확한 의도(Intent)를 파악한다.

**하는 것:**
- 오타 처리 / 간접 표현 해석 / 은어·비유법 해석
- 업계 전문 용어 인식 (퍼포먼스 마케팅 도메인)
- 3-depth 의도 분류 (domain → category → subcategory)
- 엔티티 추출 및 정규화 (브랜드, 매체, 기간 등)
- 모호성 탐지 → Response로 명확화 질문 전달 (HITL 아님, 멀티턴 대화)

**하지 않는 것:**
- 실행 계획 수립 (→ Planning)
- 어떤 Agent를 쓸지 결정 (→ Planning)

#### 처리 흐름

```
user_input (원문)
    │
    ▼
┌─ 입력 정규화 ──────────────────────────────────────┐
│  오타 교정, 간접 표현 → 직접 표현 변환              │
│  은어/비유법/업계 표현 → 표준 표현 변환              │
└────────────────────────────┬───────────────────────┘
                             │
                             ▼
┌─ 의도 분류 (3-depth) ──────────────────────────────┐
│  domain: analysis | content | operation | inquiry   │
│  category: review_analysis | ad_creation | ...      │
│  subcategory: sentiment | competitor | ...          │
└────────────────────────────┬───────────────────────┘
                             │
                             ▼
┌─ 엔티티 추출 ──────────────────────────────────────┐
│  브랜드, 매체, 기간, 예산, 타겟 등                   │
│  정규화: "삼전" → "삼성전자", "지난달" → 2026-02    │
└────────────────────────────┬───────────────────────┘
                             │
                             ▼
┌─ 모호성 판단 ──────────────────────────────────────┐
│  "리뷰 분석해줘" → 브랜드 불명 → 명확화 질문 생성    │
│  "삼성전자 리뷰 분석해줘" → 명확 → 그대로 진행       │
│                                                     │
│  ※ 세션 메모리 참조: 직전 턴의 컨텍스트가 있으면      │
│    "삼성전자" 단독 입력도 맥락으로 해석 가능           │
└────────────────────────────┬───────────────────────┘
                             │
                 ┌───────────┴───────────┐
                 │                       │
          명확한 경우               모호한 경우
                 │                       │
                 ▼                       ▼
      goto="planning"           goto="response"
      (Intent 전달)             (명확화 질문을 일반 응답으로)
                                (그래프 종료 → 다음 턴에서
                                 새 입력으로 재실행)
```

#### State I/O

| 방향 | 필드 | 설명 |
|------|------|------|
| Read | `user_input` | 사용자 원본 입력 |
| Read | `language` | 언어 코드 (ko/en/ja) |
| Read | `session_id` | 세션 식별자 |
| Write | `cognitive_result` | Intent + 명확화 여부 + 추천 Agent/Tool |
| Write | `error` | 에러 발생 시 |

#### 출력 검증

| 검증 항목 | 기준 | 실패 시 |
|----------|------|--------|
| Intent confidence | 0.5 이상 | 재분류 (최대 2회) → 실패 시 명확화 질문으로 전환 |
| 필수 엔티티 존재 | domain별 필수 엔티티가 추출되었는가 | 명확화 질문 생성 |
| Intent 일관성 | domain-category-subcategory 조합이 유효한가 | 재분류 |

#### 라우팅

| 조건 | 목적지 | 설명 |
|------|--------|------|
| error 존재 | `__end__` | 에러 시 종료 |
| 명확화 필요 | `response` | 사용자에게 질문 (Planning 스킵) |
| 의도 명확 | `planning` | 정상 진행 |

### 2.3 Planning Layer — 계획

**책임**: Cognitive 결과(Intent)를 기반으로 **"무엇을 할지"** Todo 리스트를 생성한다.

**하는 것:**
- 사용 가능한 Agent/Tool 카탈로그 참조
- 큰 단위 계획 수립 → 세부 Todo 분해 → 검증 (3단계)
- Todo 간 의존 관계(DAG) 정의
- 각 Todo에 Tool + 파라미터 지정

**하지 않는 것:**
- 실행 전략 결정 (직렬/병렬/fan-out → Execution)
- 실행 순서 최적화 (→ Execution)
- Todo 직접 실행 (→ Execution)

#### Todo 출력 포맷

Planning이 생성하는 Todo 리스트의 구조:

```python
# Plan = Todo 리스트 + 메타데이터
{
    "plan_id": "plan_uuid",
    "intent_summary": "삼성전자 네이버 리뷰 감성 분석",
    "todos": [
        {
            "id": "todo_001",
            "task": "삼성전자 네이버 리뷰 수집",
            "description": "최근 3개월 리뷰 100건 수집",
            "agent": "data_analysis_agent",
            "tool": "naver_review_collector",
            "tool_params": {
                "brand": "삼성전자",
                "period": "3months",
                "count": 100
            },
            "depends_on": [],
            "priority": 1,
            "requires_approval": false
        },
        {
            "id": "todo_002",
            "task": "수집 데이터 텍스트 전처리",
            "description": "리뷰 텍스트 정제 및 토큰화",
            "agent": "data_analysis_agent",
            "tool": "text_preprocessor",
            "tool_params": {
                "source_todo_id": "todo_001"
            },
            "depends_on": ["todo_001"],
            "priority": 2,
            "requires_approval": false
        },
        {
            "id": "todo_003",
            "task": "감성 분석 실행",
            "agent": "data_analysis_agent",
            "tool": "sentiment_analyzer",
            "tool_params": {
                "source_todo_id": "todo_002",
                "model": "multilingual"
            },
            "depends_on": ["todo_002"],
            "priority": 3,
            "requires_approval": false
        }
    ],
    "dependency_graph": {
        "todo_001": [],
        "todo_002": ["todo_001"],
        "todo_003": ["todo_002"]
    }
}
```

**포맷 설계 이유:**
- `agent` + `tool` 명시 → Execution이 라우팅 판단 없이 바로 실행 가능
- `depends_on` → DAG로 직접 해석 가능, 병렬/직렬 판단의 근거
- `tool_params` → 실행에 필요한 파라미터를 Planning 시점에 확정
- `requires_approval` → HITL 필요 여부를 Planning이 판단

> **상세 필드 정의는 Pydantic 정의서(6번)에서 확정한다.**
> 여기서는 구조와 용도만 정의한다.

#### 내부 3단계 처리 흐름

```
cognitive_result (Intent)
        │
        ▼
┌─ Step 1: 큰 단위 계획 수립 (LLM) ─────────────────┐
│                                                     │
│  Intent를 분석하여 작업 단계를 큰 단위로 분해한다.     │
│                                                     │
│  입력: Intent (domain, category, entities)           │
│  출력: 작업 단계 리스트                               │
│                                                     │
│  예시: "삼성전자 전 채널 리뷰 분석 + 보고서"          │
│    → 1. 데이터 수집 (삼성전자, 전 채널)               │
│    → 2. 데이터 전처리                                │
│    → 3. 분석 (감성 + 키워드 + 트렌드)                 │
│    → 4. 인사이트 종합                                │
│    → 5. 보고서 생성 + PDF                            │
│                                                     │
└────────────────────────────┬───────────────────────┘
                             │
                             ▼
┌─ Step 2: 세부 Todo 분해 (LLM + Tool 카탈로그) ─────┐
│                                                     │
│  각 큰 단위를 구체적인 Tool 호출로 분해한다.           │
│  Tool 카탈로그를 참조하여 실행 가능한 Tool을 매핑.     │
│                                                     │
│  예시: "1. 데이터 수집 (삼성전자, 전 채널)"           │
│    → todo_001: naver_collector (삼성전자)             │
│    → todo_002: youtube_collector (삼성전자)           │
│    → todo_003: tiktok_collector (삼성전자)            │
│    → todo_004: oliveyoung_collector (삼성전자)        │
│                                                     │
│  각 Todo에 지정하는 것:                               │
│    - tool: 어떤 Tool을 쓸지                          │
│    - tool_params: 어떤 파라미터로                     │
│    - depends_on: 어떤 Todo가 선행되어야 하는지         │
│    - requires_approval: HITL 필요 여부                │
│                                                     │
└────────────────────────────┬───────────────────────┘
                             │
                             ▼
┌─ Step 3: Todo 검증 ───────────────────────────────┐
│                                                     │
│  3-1. 구조 검증                                      │
│    - 모든 Todo에 id, tool, tool_params가 있는가       │
│    - tool이 Tool 카탈로그에 존재하는가                 │
│    - depends_on이 유효한 todo_id를 참조하는가          │
│                                                     │
│  3-2. DAG 검증                                       │
│    - 순환 의존성 없는가 (DFS)                         │
│    - 고아 Todo 없는가 (의존 대상이 삭제된 경우)         │
│                                                     │
│  3-3. 논리 검증                                      │
│    - 전처리 Todo가 수집 Todo보다 뒤에 있는가           │
│    - 분석 Todo가 전처리 Todo보다 뒤에 있는가           │
│    - 보고서/이미지 Todo가 분석 Todo보다 뒤에 있는가     │
│                                                     │
│  3-4. 검증 실패 시                                    │
│    - 구조/DAG 오류 → Step 2로 돌아가 재생성 (최대 2회) │
│    - 논리 오류 → LLM에게 오류 내용 전달 → 재생성       │
│    - 재시도 초과 → error 기록 → 전체 중단              │
│                                                     │
└────────────────────────────┬───────────────────────┘
                             │
                             ▼
                  검증 통과 → goto="execution"
                  (Plan + Todos 전달)
```

> **왜 3단계인가?**
> - Step 1에서 바로 세부 Todo를 만들면 LLM에 부담이 크고 품질이 떨어짐
> - 큰 단위 → 세부 분해로 나누면 각 단계의 LLM 호출이 가벼워짐
> - Step 3 검증이 별도이므로 "생성"과 "검증"의 책임이 분리됨

#### State I/O

| 방향 | 필드 | 설명 |
|------|------|------|
| Read | `cognitive_result` | Intent 정보 |
| Read | `session_id` | 세션 식별자 |
| Write | `planning_result` | PlanningOutput (메타데이터) |
| Write | `plan` | Plan 전체 (Todo 리스트 + DAG) |
| Write | `todos` | TodoItem 리스트 (Reducer 사용) |
| Write | `error` | 에러 발생 시 |

### 2.4 Execution Layer — 실행 (Orchestrator)

**책임**: Planning이 만든 Todo 리스트를 받아 **실행 전략을 결정**하고, **전문 Agent를 조율**하여 Todo를 실행한다.

**하는 것:**
- Todo의 의존 관계(DAG)를 분석하여 실행 전략 결정
- 전문 Agent에게 Todo를 배분하고 실행 조율
- 실행 결과 수집 및 Todo 상태 업데이트
- HITL interrupt 처리 (실행 중 사용자 확인)
- 실패 시 재시도 / fallback 처리

**하지 않는 것:**
- Todo 자체를 만들거나 변경 (→ Planning 또는 TodoManager)
- 실제 비즈니스 로직 실행 (→ 실행 Agent)
- 결과 포맷팅 (→ Response)

#### 실행 전략

| 전략 | 조건 | 동작 |
|------|------|------|
| **단일(single)** | Todo 1개 | 직접 실행 |
| **직렬(sequential)** | 의존성 체인 존재 | 하나씩 순차 실행 |
| **병렬(parallel)** | 독립 Todo 그룹 존재 | Send API로 동시 실행 |
| **fan-out** | 같은 Tool을 파라미터만 바꿔 N번 | 다수 Send 동시 실행 |
| **루프(cyclic)** | 품질 기준 충족까지 반복 | 재진입 루프 |

#### 실행 Agent 조율 흐름

```
plan, todos
    │
    ▼
┌─ 전략 결정 (StrategyDecider) ──────────────────────┐
│  DAG 분석 → 실행 전략 결정                           │
│  (단일/직렬/병렬/fan-out/루프)                       │
└────────────────────────────┬───────────────────────┘
                             │
                             ▼
┌─ 실행 가능 Todo 탐색 ──────────────────────────────┐
│  status=pending + depends_on 모두 완료된 Todo       │
└────────────────────────────┬───────────────────────┘
                             │
              ┌──────────────┴──────────────┐
              │                             │
       독립 Todo들                    의존 Todo
       (병렬 실행)                   (순차 대기)
              │                             │
              ▼                             ▼
┌─ Agent 배분 ───────────────────────────────────────┐
│  Todo.agent 필드를 보고 해당 실행 Agent에 전달        │
│                                                     │
│  ┌─────────────────┐  ┌─────────────────┐          │
│  │ data_analysis   │  │ image_creation  │  ...     │
│  │ _agent          │  │ _agent          │          │
│  └────────┬────────┘  └────────┬────────┘          │
│           │                    │                    │
│      Tool 실행            Tool 실행                  │
│           │                    │                    │
│      결과 반환            결과 반환                   │
└────────────┬───────────────────┬───────────────────┘
             │                   │
             ▼                   ▼
┌─ 결과 수집 + Todo 상태 업데이트 ───────────────────┐
│  Todo status: pending → in_progress → completed    │
│  execution_results에 결과 저장                      │
└────────────────────────────┬───────────────────────┘
                             │
              ┌──────────────┴──────────────┐
              │                             │
       미완료 Todo 있음              모든 Todo 완료
              │                             │
              ▼                             ▼
       goto="execution"             goto="response"
       (루프)                       (결과 전달)
```

#### 입력 검증 (Plan 수신 시)

| 검증 항목 | 기준 | 실패 시 |
|----------|------|--------|
| Plan 존재 | plan 필드가 비어있지 않은가 | error → 전체 중단 |
| Todo 존재 | todos 리스트가 1개 이상인가 | error → 전체 중단 |
| Tool 유효성 | 모든 Todo의 tool이 Tool 카탈로그에 존재하는가 | error → 전체 중단 |
| DAG 유효성 | depends_on이 유효한 todo_id를 참조하는가 | error → 전체 중단 |

> Planning Step 3에서 이미 검증하지만, Execution 진입 시 **이중 검증**한다.
> "신뢰하되 검증한다 (Trust but verify)"

#### Tool 실행 결과 검증 (매 Todo 실행 후)

| 검증 항목 | 기준 | 실패 시 |
|----------|------|--------|
| 결과 존재 | Tool이 결과를 반환했는가 | 재시도 (최대 2회) → 실패 시 전체 중단 |
| 결과 형태 | 예상 출력 형태와 일치하는가 | 재시도 → 전체 중단 |
| 타임아웃 | Tool 실행이 제한 시간 내 완료되었는가 | 전체 중단 |

#### 실행 Agent 목록 (Tool 그룹)

| Agent | 도메인 | 역할 |
|-------|--------|------|
| `data_analysis_agent` | 데이터/분석 | 데이터 수집, 전처리, ML/LLM 분석 |
| `report_agent` | 보고서 | 분석 결과 종합, 인사이트 보고서, PDF 생성 |
| `image_creation_agent` | 크리에이티브 | 광고 이미지 생성, 리사이징, 썸네일 |
| `video_creation_agent` | 크리에이티브 | 스토리보드, 영상 프레임 이미지, 영상 편집 |

> **각 Agent의 상세 기능은 에이전트 기능 정의서(2번)에서 정의한다.**

#### State I/O

| 방향 | 필드 | Reducer | 설명 |
|------|------|---------|------|
| Read | `plan` | - | Plan 정보 |
| Read | `todos` | todo_reducer | 현재 Todo 목록 |
| Read | `execution_results` | results_reducer | 이전 실행 결과 |
| Write | `todos` | todo_reducer | 상태 업데이트된 Todo |
| Write | `execution_results` | results_reducer | 새 실행 결과 추가 |
| Write | `error` | - | 에러 발생 시 |

#### 에러 처리 방침

```
Todo 실패 시: 전체 중단 + 에러 메시지 출력
  → 어디서 왜 실패했는지 정확히 보고
  → error 필드에 실패 위치 + 원인 기록
  → goto="__end__" (그래프 종료)

이유: 초반에는 문제 원인 파악이 우선.
안정화 후 부분 진행(degraded mode) 도입 검토 가능.
```

### 2.5 Response Layer — 시각화

**책임**: Execution 결과를 집계하고, 사용자에게 적합한 형태로 포맷팅하여 출력한다.

**하는 것:**
- 여러 Agent의 실행 결과 집계
- 출력 포맷 결정 (text / image / pdf / video / mixed)
- 최종 응답 생성 및 포맷팅
- 명확화 질문 전달 (Cognitive에서 바로 올 때)

**하지 않는 것:**
- 데이터 분석이나 생성 (→ Execution)
- 결과의 품질 판단 (→ 평가 기준서)

#### 출력 포맷

| 포맷 | 설명 | 예시 |
|------|------|------|
| `text` | 텍스트 응답 | 분석 요약, 질의 응답 |
| `image` | 이미지 첨부 | 광고 이미지, 차트 |
| `pdf` | PDF 리포트 | 상세 분석 보고서 |
| `video` | 영상 첨부 | 광고 영상 소재 |
| `mixed` | 복합 포맷 | 텍스트 + 차트 + 이미지 |

#### 처리 흐름

```
execution_results, cognitive_result
        │
        ▼
┌─ 명확화 케이스? ───────────────────────────────────┐
│  cognitive_result.requires_clarification = True     │
│  → 명확화 질문을 text 응답으로 바로 반환              │
│  (Execution 결과 집계 스킵)                         │
└────────────────────────────┬───────────────────────┘
        │ (일반 케이스)
        ▼
┌─ 결과 집계 ────────────────────────────────────────┐
│  여러 Agent의 결과를 todo_id별로 통합                 │
└────────────────────────────┬───────────────────────┘
                             │
                             ▼
┌─ 포맷 결정 ────────────────────────────────────────┐
│  결과 유형에 따라 text / image / pdf / video / mixed │
└────────────────────────────┬───────────────────────┘
                             │
                             ▼
┌─ 응답 생성 ────────────────────────────────────────┐
│  LLM으로 자연어 요약 생성                            │
│  차트/이미지/PDF 첨부 구성                           │
│  메타데이터 추가 (처리 시간, 완료 Todo 수 등)          │
└────────────────────────────┬───────────────────────┘
                             │
                             ▼
                          goto=END
```

#### 출력 검증

| 검증 항목 | 기준 | 실패 시 |
|----------|------|--------|
| 응답 텍스트 존재 | response_result.text가 비어있지 않은가 | 재생성 (최대 2회) |
| 포맷 일치 | 선택된 format에 맞는 첨부물이 있는가 (image면 이미지 첨부 존재) | 포맷 재결정 |
| 첨부 파일 유효성 | 첨부된 파일 경로가 실제로 존재하는가 | 해당 첨부 제거 + 텍스트로 대체 |

#### State I/O

| 방향 | 필드 | 설명 |
|------|------|------|
| Read | `execution_results` | Todo별 실행 결과 |
| Read | `cognitive_result` | 원본 의도 (명확화 판단용) |
| Read | `todos` | Todo 목록 (통계용) |
| Read | `language` | 응답 언어 |
| Write | `response_result` | 최종 응답 (포맷 + 텍스트 + 첨부) |
| Write | `error` | 에러 발생 시 |

### 2.6 Layer 추가 규칙

새 Layer를 추가할 때 확인해야 할 것:

1. 기존 Layer와 책임이 겹치지 않는가
2. Hand-off 흐름에 어디에 삽입되는가
3. State에 새 필드가 필요한가 → State 명세서 업데이트
4. 라우팅 규칙이 변경되는가 → Orchestrator 수정
5. 관련 명세서(State, Interface Contract)를 업데이트했는가

## 3. Orchestrator

### 3.1 그래프 구조

```python
# 노드 등록
graph.add_node("cognitive", cognitive_node)
graph.add_node("planning", planning_node)
graph.add_node("execution", execution_node)    # 내부적으로 LangGraph subgraph
graph.add_node("response", response_node)

# 엣지 정의
START → cognitive
cognitive →[conditional]→ planning | response | __end__
planning  →[conditional]→ execution | __end__
execution →[conditional]→ execution | response | __end__   # 자기 루프 포함
response  → END
```

### 3.2 LangGraph Primitives

| Primitive | 사용처 | 설명 |
|-----------|--------|------|
| **Command** | 레이어 간 hand-off | `Command(update={...}, goto="next_node")` |
| **Send** | Execution 내 병렬 실행 | 독립 Todo를 여러 Agent에 동시 배분 |
| **interrupt()** | HITL 중단점 | 사용자 승인/수정 대기 |
| **Checkpoint** | 자동 상태 저장 | 노드 경계마다 저장, 중단/재개 지원 |

### 3.3 설정

```python
@dataclass
class OrchestratorConfig:
    interrupt_before: list[str] = []    # HITL 중단 노드
    recursion_limit: int = 50           # 무한 루프 방지
    debug: bool = False
```

## 4. Manager 시스템

### 4.1 개요

Manager는 **4-Layer에 직교하는 횡단 관심사**를 담당한다.
레이어 노드가 비즈니스 로직에 집중할 수 있도록, 공통 기능을 분리한 모듈이다.

```
┌───────────────────────────────────────────────────────────────┐
│                      4-Layer Pipeline                          │
│   Cognitive → Planning → Execution (Agent 조율) → Response    │
├───────────────────────────────────────────────────────────────┤
│                      Manager System                            │
│                                                                │
│  ┌────────────────┐  ┌────────────────┐  ┌────────────────┐  │
│  │ HITL Manager   │  │ Todo Manager   │  │ Memory Manager │  │
│  │ (중단/재개/    │  │ (상태 전이/    │  │ (세션 메모리/  │  │
│  │  승인/수정)    │←→│  의존성 해결)  │  │  장기 기억)    │  │
│  └────────────────┘  └────────────────┘  └────────────────┘  │
│                                                                │
│  ┌────────────────┐  ┌────────────────┐  ┌────────────────┐  │
│  │ Callback Mgr   │  │ Session Mgr    │  │ Learning Mgr   │  │
│  │ (실시간 이벤트/ │  │ (세션 CRUD/    │  │ (트레이스 로깅/│  │
│  │  진행률 알림)   │  │  대화 이력)    │  │  패턴 수집)    │  │
│  └────────────────┘  └────────────────┘  └────────────────┘  │
│                                                                │
│  ┌────────────────┐                                           │
│  │ Feedback Mgr   │                                           │
│  │ (사용자 피드백/ │                                           │
│  │  품질 평가)     │                                           │
│  └────────────────┘                                           │
└───────────────────────────────────────────────────────────────┘
```

### 4.2 Manager 목록

| Manager | 역할 | 주요 소비자 | 상태 |
|---------|------|------------|------|
| **HITL Manager** | 중단/재개, 승인, 수정 요청, Pause | Cognitive, Planning, Execution | 핵심 |
| **Todo Manager** | Todo 상태 전이, 의존성 해결, 수정/삭제 | Planning, Execution | 핵심 |
| **Memory Manager** | 세션 메모리, 장기 기억 | Cognitive, Response | 핵심 |
| **Callback Manager** | WebSocket 실시간 이벤트, 진행률 알림 | 전 레이어 | 핵심 |
| **Session Manager** | 세션 CRUD, 대화 이력 관리 | API Layer | 핵심 |
| **Learning Manager** | 실행 트레이스 로깅, 패턴 수집, 데이터 익스포트 | Execution, Response | Phase 3+ |
| **Feedback Manager** | 사용자 피드백 수집, 품질 평가 (RLHF) | Response | Phase 3+ |

### 4.3 HITL Manager 상세

**책임**: 사용자와 시스템 간의 모든 상호작용을 관리한다.

#### HITL 유형 2가지

| 유형 | 트리거 | 방향 | 설명 |
|------|--------|------|------|
| **Type 1: Agent 트리거** | 코드에 미리 심어둔 트리거 지점 | 시스템 → 사용자 | 실행 중 사용자 확인이 필요한 시점에서 interrupt 발동 |
| **Type 2: 사용자 Pause** | 사용자가 Pause 버튼 클릭 | 사용자 → 시스템 | 작업 즉시 멈추고, 자연어로 수정/삭제/재개/리셋 요청 |

> **명확화 질문은 HITL이 아니다.** Cognitive에서 모호한 입력 탐지 시 Response로 질문을 전달하고 그래프를 종료한다. 다음 턴에서 새 입력으로 재실행하는 멀티턴 대화이다.

#### Type 1: Agent 트리거

실행 Agent가 사용자 확인이 필요한 시점에서 interrupt를 발동한다.

| 시나리오 | 발생 지점 | 예시 |
|----------|----------|------|
| Plan 승인 | Planning → Execution | "이 계획으로 진행할까요?" |
| 중간 결과 확인 | Execution 내부 | "이미지 3장 생성했습니다. 어떤 걸로?" |
| 위험 작업 확인 | Execution 내부 | "외부 API에 데이터를 전송합니다. 진행할까요?" |

```
Agent가 트리거 발동
  → interrupt() 호출
  → State에 hitl_pending 기록:
      {
          "hitl_type": "agent_trigger",
          "todo_id": "todo_005",
          "trigger": "image_selection",
          "question": "이미지 3장 중 선택해주세요",
          "options": ["이미지A", "이미지B", "이미지C"],
          "data": { ... }      ← 사용자에게 보여줄 중간 결과
      }
  → Checkpoint 저장
  → Callback Manager → 사용자에게 알림
  → 사용자 응답 → hitl_pending 해제 → 해당 지점부터 계속
```

#### Type 2: 사용자 Pause

사용자가 **언제든 Pause 버튼을 눌러** 작업을 멈출 수 있다.
멈춘 후 **자연어로 요청**하면, 시스템이 의도를 해석하여 처리한다.

```
사용자: [Pause 버튼 클릭]
  → 작업 즉시 멈춤
  → State에 hitl_pending 기록:
      {
          "hitl_type": "user_pause",
          "paused_at": "execution",
          "current_todo_id": "todo_003",
          "user_request": None       ← 자연어 입력 대기
      }
  → Checkpoint 저장

사용자: "3번 Todo 삭제해줘" (자연어)
  → LLM이 의도 해석 (Cognitive와 유사한 자연어 이해)
  → 해석 결과에 따라:
      ├── Todo 수정 → Todo Manager에 요청
      ├── Todo 삭제 → Todo Manager에 요청
      ├── 재개 (Resume) → hitl_pending 해제 → 이어서 실행
      └── 리셋 → 처음부터 다시 (새 그래프 실행)
```

#### Manager 간 호출 규칙

```
HITL Manager → Todo Manager: Todo 수정/삭제 요청 가능
HITL Manager → Callback Manager: 사용자 알림 요청 가능
Todo Manager → HITL Manager: 호출 불가 (순환 의존 금지)
```

### 4.4 Todo Manager 상세

**책임**: TodoItem의 상태 전이를 관리하고, HITL 상태에서의 Todo 수정/삭제를 처리한다.

#### 상태 전이

```
pending ──→ in_progress ──→ completed  (최종)
        ──→ blocked          ──→ failed
        ──→ needs_approval
        ──→ cancelled        failed ──→ pending (재시도)
        ──→ skipped                 ──→ skipped
                                    ──→ cancelled
```

#### HITL-Todo 협력

HITL 상태에서 Todo 변경이 필요한 경우:

```
사용자가 Todo 수정/삭제 요청
          │
          ▼
┌─ 변경 규모 판단 ─────────────────────────────────┐
│                                                   │
│  단순 변경:                  구조적 변경:           │
│  - 파라미터 수정             - Todo 추가/삭제       │
│  - 우선순위 변경             - 의존 관계 변경       │
│  - Agent/Tool 교체           - 새로운 Agent 필요    │
│                                                   │
│  → Todo Manager 직접 처리    → Planning 재호출      │
│    (Planning 불필요)          (새 Plan 생성)        │
└───────────────────────────────────────────────────┘
```

**단순 변경**: Todo Manager가 직접 처리
- `todo.with_updated_params(new_params)` → 새 버전 생성
- 의존 관계에 영향 없음을 확인
- Execution에 변경 사항 반영

**구조적 변경**: Planning Layer 재호출
- 변경된 요구사항을 Planning에 전달
- 새 Plan 생성 (기존 완료된 Todo는 유지)
- Execution이 새 Plan으로 재시작

### 4.5 Memory Manager 상세

| 기능 | 설명 |
|------|------|
| 세션 메모리 | 대화 컨텍스트, 이전 실행 결과 참조 |
| 장기 기억 | 사용자 선호도 (자주 쓰는 매체, 브랜드, 분석 방식 등) |

### 4.6 Callback Manager 상세

| 이벤트 | 시점 | 데이터 |
|--------|------|--------|
| `layer_start` | 각 레이어 진입 | layer_name, timestamp |
| `layer_complete` | 각 레이어 완료 | layer_name, duration_ms |
| `todo_start` | Todo 실행 시작 | todo_id, agent, tool |
| `todo_complete` | Todo 실행 완료 | todo_id, success, duration_ms |
| `progress` | 주기적 | completed/total, percentage |
| `hitl_request` | HITL 발동 | 유형, 질문/선택지, 타임아웃 |
| `error` | 에러 발생 | error_message, layer, todo_id |

### 4.7 Session Manager 상세

| 기능 | 설명 |
|------|------|
| 세션 생성/조회/삭제 | 사용자별 작업 세션 관리 |
| 대화 이력 | 세션 내 사용자 입력/응답 기록 |
| 세션 상태 | active, paused, completed, failed |

### 4.8 Manager 공통 패턴

모든 Manager는 동일한 생명주기를 따른다:

```python
class BaseManager:
    async def initialize(self):   # 리소스 초기화
    async def ready(self) -> bool: # 준비 완료 확인
    async def shutdown(self):      # 리소스 정리
```

ManagerRegistry를 통해 의존성 기반으로 초기화 순서가 관리된다.

### 4.9 Manager 추가 규칙

새 Manager를 추가할 때 확인해야 할 것:

1. 기존 Manager와 책임이 겹치지 않는가
2. 특정 Layer에 종속되지 않는, 진정한 횡단 관심사인가
   (특정 Layer에만 쓰인다면 Manager가 아니라 그 Layer의 내부 모듈)
3. BaseManager 패턴(initialize/ready/shutdown)을 따르는가
4. ManagerRegistry에 등록되었는가
5. 이 문서의 Manager 목록을 업데이트했는가

## 5. State 관리 (개요)

### 5.1 Hybrid State 전략

| 용도 | 타입 시스템 | 이유 |
|------|-----------|------|
| `AgentState` (그래프 상태) | TypedDict | 성능, 부분 업데이트, Reducer 호환 |
| Layer I/O (CognitiveOutput 등) | Pydantic BaseModel | 런타임 검증, 직렬화 |
| 도메인 모델 (Intent, Plan, TodoItem) | Pydantic BaseModel | 검증, 불변성, 직렬화 |

### 5.2 직렬화 경계

```
쓰는 노드                    AgentState                   읽는 노드
PydanticModel ──.model_dump()──→ dict ──→ **dict ──→ PydanticModel
```

### 5.3 Reducer 요약

| Reducer | 필드 | 동작 |
|---------|------|------|
| `todo_reducer` | `todos` | ID 기반 upsert. 최종 상태 보호 |
| `results_reducer` | `execution_results` | 재귀적 dict 병합 |
| `trace_reducer` | `trace` | append-only 연결 |

> **상세 State 명세는 Graph State 명세서(4번)에서 정의한다.**

## 7. Tool 시스템 (개요)

### 7.1 Tool 분류

| 분류 | 구현 | 설명 | 예시 |
|------|------|------|------|

```
    ↓ Execution이 매핑
Agent → Tool 실행
    ↓
결과 반환
```

## 8. 실행 흐름 예시

### 8.1 정상 흐름: "삼성전자 리뷰 감성 분석해줘"

```
1. User Input: "삼성전자 리뷰 감성 분석해줘"
   │
   ▼
2. Cognitive Layer
   - 오타/은어 없음, 직접 표현
   - IntentClassifier: domain=analysis, category=review_analysis
   - EntityExtractor: {brand: "삼성전자"}
   - Clarifier: requires_clarification=False
   → cognitive_result 저장
   │
   ▼
3. Planning Layer
   - Agent/Tool 카탈로그에서 매칭
   - 3개 Todo 생성:
     ├── todo_001: data_analysis_agent / naver_review_collector
     ├── todo_002: data_analysis_agent / text_preprocessor (depends: 001)
     └── todo_003: data_analysis_agent / sentiment_analyzer (depends: 002)
   - 의존 관계 검증: 순환 없음 ✓
   → plan, todos 저장
   │
   ▼
4. Execution Layer (3회 루프)
   - 전략 결정: SEQUENTIAL (직렬 체인)
   - Loop 1: todo_001 → data_analysis_agent → completed
   - Loop 2: todo_002 → data_analysis_agent → completed
   - Loop 3: todo_003 → data_analysis_agent → completed
   → execution_results 저장
   │
   ▼
5. Response Layer
   - 결과 집계: 감성 분석 결과 통합
   - 포맷 결정: mixed (텍스트 요약 + 감성 차트)
   - 응답 생성: LLM이 자연어 요약 + 차트 첨부
   → response_result 저장
   │
   ▼
6. User Output: 감성 분석 결과 + 차트
```

### 8.2 명확화 흐름: "리뷰 분석해줘"

```
1. User Input: "리뷰 분석해줘"
   │
   ▼
2. Cognitive Layer
   - Clarifier: 브랜드 정보 없음 → requires_clarification=True
   - clarification_question: "어떤 브랜드/제품의 리뷰를 분석할까요?"
   │
   ▼
3. route_after_cognitive → "response" (Planning 스킵)
   │
   ▼
4. Response Layer
   - 명확화 질문을 text 응답으로 반환
   │
   ▼
5. User Output: "어떤 브랜드/제품의 리뷰를 분석할까요?"
```

### 8.3 HITL + Todo 수정 흐름

```
1. 실행 중 Pause 요청
   │
   ▼
2. HITL Manager: interrupt() 발동
   - 현재 상태 Checkpoint 저장
   - Callback Manager → 사용자에게 현재 진행 상황 전달
   │
   ▼
3. 사용자: "todo_003의 분석 모델을 multilingual → korean으로 바꿔줘"
   │
   ▼
4. HITL Manager → Todo Manager에 수정 요청
   - 변경 규모 판단: 파라미터 수정 = 단순 변경
   - Todo Manager가 직접 처리
   - todo_003.tool_params.model = "korean" (새 버전 생성)
   │
   ▼
5. HITL Manager: 실행 재개
   - Checkpoint에서 복원
   - 변경된 todo_003으로 계속 실행
```
