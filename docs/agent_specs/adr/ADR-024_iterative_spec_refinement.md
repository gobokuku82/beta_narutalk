# ADR-024: Iterative Spec Refinement — 작성-검증-수정 사이클의 작업 방법론 박제

## Status

**Accepted** (2026-05-27) — 본 spec 작업 (65·ADR-023·68 등) 에서 *이미 적용되던 패턴* 의 *공식 박제*.

## Context

### 1. 사용자 통찰 (2026-05-27)

사용자 발언: *"a-b-c 는 단일작업이 아니라 작성-검증-수정 의 순환식으로 해야 하지 않는가?"*

→ Claude (제) 가 *waterfall* 식 순차 작업 (A → B → C → Phase 1) 제안 → 사용자가 *Iterative Refinement* 직관으로 정정.

### 2. 산업 표준 매핑

| Framework | 본 방법론과의 대응 |
|---|---|
| **TDD (Test-Driven Development)** | Red (검증 실패) → Green (작성) → Refactor (수정) |
| **Scrum** | Sprint (작성) → Review (검증) → Retrospective (수정) |
| **PDCA (Plan-Do-Check-Act)** | Plan = 작성 / Do = 적용 / Check = 검증 / Act = 수정 |
| **Spec-First Design (RFC)** | Draft → Comments → Revision → Accepted |
| **Agile Iterative Refinement** | Iterate → Validate → Adjust → Accept |
| **Anthropic CLAUDE.md 가이드** | Explore → Plan → Code → Review → Commit |

→ 본 ADR = 산업 표준 패턴의 *본 시스템 정합 + 명시적 박제*.

### 3. 기존 작업의 *암묵적 적용* 사례

본 시스템에서 *이미* 부분적으로 사이클 진행 (단 공식 박제 X):

| 작업 | 사이클 횟수 | 결과 |
|---|---|---|
| **65 spec 작성** | **4 차 검증** (코드 정합·ADR-022·구조·§ 번호) | swap·정정 8건 + Round 1·2·3 정정 |
| **ADR-023 작성** | **7 라운드** 사용자 토의 | Fetcher 철회·Skills 박제·Trigger 추상화·Tool-Data 분리·POC v1/v2·Maker 위치·Agent sandbox |
| **D1 카탈로그** | **D1.6 검토 게이트** (5 결정) | 우선순위 정정 (🟠 → 🟡 의존성 정합) |
| **G1·G2·G3** | git stash 검증 + cross-link 검증 | 라인 수 정정·DATA_DIR 진단 |
| **68 Batch 1** | (검증 사이클 *미적용*) | ⚠️ 사용자 지적 — 본 ADR 의 *동기* |

→ **암묵적 적용 → 공식 박제 시점 도래**.

### 4. Waterfall 위험

```
[잘못된 framing — waterfall]
A 작성 → B 작성 → C 작성 → Phase 1 진입
   ↑ 검증·수정 단계 누락 ⚠️

위험:
  - A 의 결함이 B·C 에 누적
  - Phase 1 진입 시 *대규모 수정* 필요 (비싼 시점)
  - 사용자 검토 게이트 부재 → 의도 어긋남 늦게 발견
```

```
[올바른 framing — iterative]
A 작성 → A 검증 → A 수정 → A 채택
   ↓
B 작성 → B 검증 → B 수정 → B 채택
   ↓
Phase 1 진입 (위 모든 채택 결과 위에서)

장점:
  - 결함 *조기 발견* + *조기 수정*
  - 누적 정확도 ↑
  - 사용자 검토 게이트 = 자연 stop point
```

## Decision

### 1. 표준 사이클 정의

```
[1. 작성]
  spec / 계획서 / 코드 작성
        ↓
[2. 검증]
  5 검증 방법 적용 (아래 §2)
        ↓
[3. 수정]
  발견 사항 반영
        ↓
[4. 채택]
  - 사용자 동의
  - commit (영구 박제)
  - 다음 단계 진입
```

### 2. 5 검증 방법

| # | 검증 종류 | 누가 | 무엇을 |
|:---:|---|---|---|
| **V1** | **코드 정합성** | Explore agent (자동) | spec 의 file path·class name·line 번호·라이브러리 함수 정확성 |
| **V2** | **Cross-reference** | Claude (수동) | 다른 spec / ADR 의 영역 침범 X, cross-link 일관성, 어휘 통일 |
| **V3** | **사용자 검토** | 사용자 (game review) | framing 정확성, 누락 영역, 우선순위, 의도 정합 |
| **V4** | **정답값 보존** | pytest / 정답 17 | POC mock 데이터의 산출값 변화 X |
| **V5** | **영역 침범 X** | Claude | spec 의 *책임 경계* 명확 (단일 진실 소스 X 영역 분담) |

### 3. 검증 적용 결정 매트릭스

| 작업 유형 | V1 | V2 | V3 | V4 | V5 |
|---|:---:|:---:|:---:|:---:|:---:|
| 신규 spec 작성 | ✅ | ✅ | ✅ | — | ✅ |
| spec 보강 | ✅ | ✅ | ✅ | — | ✅ |
| ADR 작성 | — | ✅ | ✅ | — | ✅ |
| 코드 신규 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 코드 수정 | ✅ | — | ✅ | ✅ | — |
| Refactor | ✅ | — | — | ✅ | — |
| 문서 정정 (사소) | — | — | ✅ | — | — |

→ **신규 spec / 코드 = 5 검증 모두 적용**. 사소 정정 = V3 만.

### 4. Stop 조건

| 조건 | 다음 행동 |
|---|---|
| ✅ 모든 검증 통과 | 채택 → commit → 다음 단계 |
| ⚠️ 1 검증 실패 | 수정 → 사이클 1회 더 (V1·V2·V5 만 재검증) |
| 🔴 사용자 의도 불일치 | 재 framing → 사이클 1회 더 (전체) |
| 🛑 결정 불가 (사용자 의견 필요) | 사이클 *대기* → 사용자 응답 후 재진입 |

### 5. 사이클 횟수 권장

| 작업 규모 | 최소 사이클 | 권장 사이클 |
|---|:---:|:---:|
| 사소 정정 | 1 | 1 |
| spec 보강 (작은) | 1 | 2~3 |
| 신규 spec | 2 | **3~4** (65 spec = 4 차) |
| ADR 결정 | 1 | **2~7** (ADR-023 = 7 라운드) |
| 큰 작업 (POC v1) | — | **단계별 사이클** (각 batch 마다 사이클) |

### 6. 사용자 검토 게이트 (V3) 의 *특수성*

V3 = 다른 검증 (자동·코드) 으로 *대체 불가*. 사용자 검토의 본질:

| 영역 | 검토 내용 |
|---|---|
| **Framing 정확성** | 사용자 의도와 spec 의 *추상화 수준* 일치 |
| **누락 영역** | spec 가 *덮지 못한 영역* 발견 |
| **우선순위** | 사용자의 가치 기준 정합 |
| **명명** | 비전공자 친화·산업 표준 정합 |
| **POC vs MVP 분리** | 시점 결정 적합 |

→ V3 게이트 = *반드시 stop*. 자동 진행 금지. 사용자 응답 기다림.

### 7. 사이클 의 *공식 박제 위치*

| 영역 | 위치 |
|---|---|
| **본 ADR** | 결정 박제 (영구) |
| **각 spec § 마지막** | "본 § 의 검토 가이드" — 5 결정 항목 명시 (D1.6 패턴) |
| **commit message** | 사이클 횟수 + 검증 통과 명시 |
| **변경 이력 (§8)** | 사이클 라운드별 정정 사항 |

## Consequences

### 긍정

| 영역 | 효과 |
|---|---|
| **조기 결함 발견** | A 의 결함이 B·C 로 누적 X |
| **사용자 의도 정합** | V3 검토 게이트 = 의도 어긋남 조기 발견 |
| **누적 정확도** | 각 사이클이 *부분 정밀화* 누적 |
| **Phase 1 진입 안전성** | spec 완성도 ↑ → 구현 시 *대규모 수정* 위험 ↓ |
| **암묵적 → 명시적** | 이미 적용 중인 패턴의 공식화 |
| **다음 작업자** | Claude 다음 세션 또는 다른 작업자도 *같은 방법론* 적용 |

### 비용

| 영역 | 비용 |
|---|---|
| **작성 시간** | 단순 1회 작성보다 *2~4 배 시간* (검증·수정 포함) |
| **사용자 부담** | V3 게이트 = 사용자 응답 기다림 (대화 길어짐) |
| **commit 횟수** | 1 작업 = N commit 가능 (사이클 횟수 만큼) |

### 완화

| 비용 | 완화 |
|---|---|
| 시간 ↑ | *Phase 1 진입 후* 의 수정 시간 절감으로 상쇄 |
| 사용자 부담 ↑ | 권장 default 옵션 제시로 *빠른 응답* 유도 |
| commit ↑ | 사이클 commit 의 *체계적 박제* 가 미래 가치 ↑ |

## Alternatives

### A. Waterfall (순차) — *기각*
- 장: 단순, 사용자 부담 적음
- 단: 결함 누적, Phase 1 진입 시 대규모 수정 (사용자 명시 위배)

### B. *부분* iterative (코드만, spec X) — *기각*
- 장: 코드는 정확하나
- 단: spec 의 framing 결함이 코드로 전파

### C. *완전* iterative (모든 변경마다 사이클) — *부분 채택*
- 장: 최대 정확도
- 단: 사소 정정도 사이클 → over-engineering
- 결: **§3 의 *검증 적용 결정 매트릭스* 로 작업 규모 별 사이클 차등**

### D. 사용자 검토 *생략* (자동 검증만) — *기각*
- 장: 빠름
- 단: V3 = 의도 정합 검증 = *자동화 불가능*
