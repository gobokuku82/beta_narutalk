## §1 엔지니어링 4분류 — 용어와 판별

| 용어 | 정의 | 출처 |
|---|---|---|
| **컨텍스트 엔지니어링** | "LLM 샘플링 시 포함되는 토큰 집합의 큐레이션" — LLM이 *보는* 것의 설계. prompt engineering의 상위 집합("어떻게 묻나"가 아니라 "모델이 무엇을 알게 하나") | Anthropic effective-context-engineering · Karpathy 2025-06 |
| **하네스 엔지니어링** | 모델 바깥 비계 전부 — 실행 루프·게이트·검증·HITL·재시도. 2026-02 OpenAI가 공식 명명. **우리 게이트 28·executor·recovery가 이것** (이름 없이 해오던 것) | openai.com/index/harness-engineering · Fowler/Böckeler |
| **데이터플로(전달) 계약** | 제3범주 — tool→tool처럼 LLM을 거치지 않는 결정론 데이터 전달의 계약. 컨텍스트도 하네스도 아닌 일반 소프트웨어/데이터 엔지니어링. **이번 재설계의 본진** | 12-factor agents F4 · 학습판 §0 |
| **판별 질문** | *"이 설계가 실패하면 LLM이 오판하나(→컨텍스트), 실행이 틀리거나 거짓 성공하나(→하네스)?"* — previous_results가 시금석: 다음 tool로 가면 하네스, LLM 프롬프트로 가면 컨텍스트 | 학습판 §0 |
| 프롬프트 엔지니어링의 위치 | 현 시점 4분류 중 최후순위 — 계획 프롬프트는 게이트와 함께 이미 100%, 오해석은 입력 큐레이션 문제 | 기준서 P0 |

## §2 데이터 전달 개념

| 개념 | 정의 | 근거/구현 |
|---|---|---|
| **전달 3평면** | State(LangGraph 채널) / Context(previous_results) / Class(fetch→DataSource 창고) — tool이 데이터를 받는 세 길 | 학습판 §2 (코드 실체 확정) |
| **전달 4갈래** | tool A→B의 실제 길: ①주입(_inject_prev_outputs setdefault) ②당김(find_in_previous 첫 발견 승) ③LLM 주입(무차별 스캔→denylist→[:3000]) ④창고 경유(_storage→fetch) — 전부 "키 문자열=계약" | 학습판 §2 |
| **장부 (artifact ledger)** | 신설할 1급 객체: tool 산출마다 {이름, 스코프, 신분, 단위·정의, 생산자, 위치, 요약} 등기. 본체는 창고, 흐름엔 장부 | 기준서 D1 — 업계 5출처 수렴 (감사 §3.2) |
| **값의 신분 3분류** | answer(답) / working(작업메모 — dropped 류 정제 부산물) / internal(내부장치 — `_`접두 승격). 생산 시점 선언 | 기준서 D2 · MCP audience(참고) |
| **누적 계약** | 오너 원의도: 에이전트 언어는 layer를 건널 때 **좁아지지 않고 누적**된다(깔때기 ✕, 눈덩이 ○). 현실: planning→execution에서 의도 귀속 링크 단절 (M0 T4가 역공학으로 측정해야 했던 그 공백) | memory 박제 2026-06-13 · M0 보고서 |
| **멀티스코프 천장** | 같은 tool을 다른 기간으로 2번 호출 — 실행은 되나 소비 불가(이름 평면 첫 발견 승). "4월 매출과 3월 ROAS"의 벽. 해소 = 이름+스코프 합성 키(`total_revenue@2026-04`) | 학습판 §3-5 · 기준서 D3 |
| **지표 registry / semantic layer** | 지표의 분자·분모·단위·**grain**(전체/소재 평균/키워드 평균)을 1회 정의, 하류는 재계산 금지·조회만. 다중 ROAS 모순(6.53배/395%/393%)의 정석 해법 | dbt MetricFlow · 기준서 D7 |

## §3 구조 진단 개념

| 개념 | 정의 | 근거 |
|---|---|---|
| **계획된 블랙보드** | 우리 시스템의 정체 — 1970s 공유 칠판 패턴 + 사전 계획. 블랙보드 고전 약점(암묵 읽기 계약→무음 실패)이 우리 진단과 일치 | 학습판 §4 |
| **버그의 버그 (패치 간섭)** | 계약 없는 평면에서 패치끼리 만나 서로를 오해 — 실증: G16/G17 스텁(패치1)을 표시 합성 렌더(패치2)가 데이터로 오인해 화면 노출 (2026-06-12 실사고) | 오너 명제 + 표시품질 계획 §0-① |
| **계약-게이트 관계** | "Contracts define expectations. Gates enforce them" — 게이트는 각자 저작물이 아니라 계약의 파생 집행물이어야 함. 단 **계획층 게이트(G02~G08)는 덧댐이 아니라 뼈대의 수선층** (복합 14쿼리의 42.9%에서 발동해 만든 100%) | Ataccama(통용 표현) · 학습판 §1 실측 |
| **반쪽 뼈대 / A-B 자연 대조** | 설계가 있던 곳(계획층)은 잘 되고 없던 곳(전달층)은 사고 — 같은 시스템 안에서 "설계 유무"가 변수로 실증된 대조 실험 | 학습판 §1 vs §2~3 |
| **보존 목록 5** | 재설계 불가침: ①Intent 계약+sub_intents≥2 양보 ②닫힌 메뉴+stub 0 ③게이트 배터리와 순서 ④카탈로그 메타 코드 실측 무결성+SCOPE_PARAMS 1곳 ⑤정직 degrade. 각각 깨지면 복귀하는 사고가 박제돼 있음 | 학습판 §1 표 |
| **검사 대상 축** | 게이트 분류축: 언어(LLM 산출물 정합)/접점(언어의 약속 vs 데이터 현실)/데이터(저장 형태)/표면(사람에게 정직) — "데이터를 못 보는 layer일수록 언어 게이트가 필요" | 43 대장 v1.3 §1·§4-2 |

## §4 방법론·규약

| 개념 | 정의 | 근거 |
|---|---|---|
| **동사 규약** | 있는 것은 **명문화·재편**, 없는 것(전달 계약)은 **신설** — "도입"은 오용 (이미 있는 규율을 설치하는 것처럼 보임) | 오너 확정 2026-06-13 |
| **역할 설계 3단계** | 역할 "모호" 해소법: ①구체적으로 무엇을 처리하나 ②실제 작업환경에서 어떤 일들이 일어나나(사건 목록 — M0/M1·사고 기록이 이미 카탈로그) ③직접 책임 vs manager 위임 결정. 한 줄 미션 선언과 구별 | 오너 정의 2026-06-13 (memory 박제) |
| **문서 생존 장치** | 살아있는 문서 = **위반이 RED가 되는 문서** (43 대장=sync 테스트, 헌법=비준 절차, 카탈로그=코드 실측). 강제 장치 없는 문서는 낡은 채 신뢰받아 더 위험 (20_INTERFACE_CONTRACT — 4월 내용 그대로 + 런타임 비강제) | 본 대화 감사 |
| **검증 가능 서술 원칙** | 오너 기준 수립용 문서의 제1원칙: 모든 정의에 출처, 모든 주장에 코드 위치/실측 — "그럴듯한 설명으로 납득시키지 않기" (위임-검증 공백의 구조적 보완) | 오너 지시 2026-06-13 |
| **게이트 2분류 (관측용)** | 상시 경로형(발동률=효용 지표) vs 회귀 방어형(발동 0이 정상, 테스트 RED가 효용 지표) — 발동 수로 과방어를 심사할 땐 전자에만 | 기준서 검증 렌즈 2 |
