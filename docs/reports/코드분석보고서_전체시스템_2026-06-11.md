## 1. 시스템 개요

OctorAD는 **자연어 → 광고 데이터 분석** 변환 파이프라인이다. 사용자가 자연어로 분석을 요청하면:

```
NL 쿼리
 → Cognitive   : 자연어 → StructuredQuery(PMAL 에이전트 언어) 번역. LLM 1회.
 → Planning    : tool 카탈로그 기반 Todo[]+DAG 계획. LLM 3-stage + 결정론 게이트 샌드위치.
 → Execution   : phase 단위 실행(phase 내 병렬·phase 간 직렬). HITL pause/편집 개입 가능.
 → Response    : 에이전트 언어 → 자연어 + 첨부(PDF/PPT). LLM 0 — 결정론 표시 dispatcher.
```

### 1.1 실측 토폴로지

- **컴파일되는 LangGraph는 4노드**(cognitive/planning/execution/response, [builder.py:36-39](../../backend/app/dream_agent/system_graph/builder.py)). 정적 edge는 START→cognitive 1개뿐이고 나머지 라우팅은 각 stage의 `Command(goto=...)` 동적 분기. "13-노드"는 spec 14의 개념 카운트로 컴파일 그래프와 다른 층위다(spec 스스로 "내부 노드는 자유"라 명시).
- interrupt 지점 2개: `plan_review`(planning), `execution_pause`(execution). 영속화는 PostgreSQL checkpointer(AsyncPostgresSaver)가 전담.
- 진입점: `run_server_v2.py`(루트) → `backend/api_v2/main.py` lifespan(checkpointer fail-fast + 콘솔 풀 degrade + `DATA_BACKEND=postgres`면 DataSource/Workspace 싱글톤 swap).
- 레이어 의존은 `api_v2 → dream_agent(stage) → tools → data_sources/workspace` 단방향. 패키지 순환 없음(workflow_managers→execution import 0건 — execution→managers 의존은 전부 함수 내부 lazy import로 회피하는 암묵 컨벤션).

### 1.2 "8-gate" 하네스의 실체

run_harness.py에 8개 gate가 정의된 게 아니라, **2026-06-04~06-10 silent-0 사태 대응으로 파이프라인에 누적된 결정론 게이트 8개**를 가리킨다:

① intent_to_tasks shim ② DEGRADE_OPS 정직 degrade ③ 주제(subject-coherence) 필터 3겹 ④ data_gate(B2.1 consumes 검사) ⑤ complete_dataflow_chain(생산자 자동 삽입) ⑥ detect_plan_gaps ⑦ bind_temporal_params ⑧ degrade 응답.

이후 3개가 추가되어(ensure_interpretation_fed, LLMTool 빈입력 가드, G6 recovery 감지) 현재 결정론 개입은 사실상 **10~11개**. 8개 게이트 전부에 무-LLM 단위테스트가 1:1로 매핑되어 있다. 별도로 `scripts/agent_lang_diagnostics/`에 LLM 실호출 진단 사다리 7종(run_harness → score_coverage(LLM-judge) → measure_gate_correction → measure_stage1_coverage(full-graph) → probe 류) + corpus 5종 77쿼리가 있다.

## 2. 레이어별 상세

### 2.1 Cognitive — 자연어→정형쿼리 번역기

**구조**: 단일 LLM 호출(gpt-5.4-mini, temp 0.1) + Pydantic 검증으로 끝난다. docstring의 "5개 서브단계"는 프롬프트 내부의 개념 구분일 뿐이다. 흐름: 공용 프롬프트(cognitive.yaml) + 클라이언트 프로필(clients/{id}.yaml) 합성 → few-shot 주입 → LLM 1회 → `StructuredQuery.model_validate` → intent_shim이 tasks를 단일 task로 기계 파생 → planning hand-off.

**잘된 점**
- **클라이언트 프로필 convention 완결**: 회사 추가 = `clients/{client}.yaml` 한 장(코드 무변경). brand/KPI 어휘/은어/few-shot이 system_prompt에 구조적으로 합성된다.
- **provenance 원칙**: client_id 명시+프로필 부재 = LLM 호출 전 fail-fast, 미명시 = generic 모드 명시 경고. silent fallback 금지가 결정론 테스트로 보호됨.
- intent(PMAL)=canonical / tasks=shim 파생 그림자라는 단방향 계약이 39줄 순수 함수로 격리. raw_input/cleaned/intent 3겹 표현으로 관측 채널 분리.

**핵심 이슈**
- 🔴 **멀티턴 history 주입 end-to-end 미연결** — history_injector는 완성된 슬롯이지만 frontend가 `conversation_history`를 송신하지 않고(전수 grep 0건) 백엔드에도 채우는 MemoryManager가 없어 Session Context가 항상 빈 문자열. "이거/그 분석" 참조 해소가 멀티턴에서 작동 불가. (의도적·문서화된 Sprint 15 gap이긴 하나 이 영역 최대 기능 공백)
- 🟡 SubIntent docstring "planning 미소비" 주장이 stale — planner.py:587,625가 이미 `sub_intents>=2`를 short-circuit 우회 신호로 소비 중. 이 문서를 믿고 emit 형식을 바꾸면 라우팅이 변한다(스키마 docstring 판 catalog≠code drift). 동일 stale이 :195 Intent docstring에도 존재.
- 🟡 intent_shim이 LLM의 복수 task 분해를 단일 task로 덮어씀 — 의도된 PMAL 전환(sub_intents 채널로 이관)이지만 cognitive.yaml의 분해 지시·params_override few-shot이 domain-present 경로에서 죽은 가이드로 남아 토큰 소모.
- 🟡 LLM 재시도·타임아웃 부재 — LLMConfig가 max_retries=3/timeout 60s를 선언하나 client.py 참조 0건. SDK 기본(전송오류 2회/600s)만 적용되고, JSON 파싱·ValidationError는 1회 실패=턴 종료.
- 🟡 DEGRADE_OPS 주석·few-shot이 분석레이어 v2(06-10) 이전 구세계 — diagnose/forecast/attribute는 이제 실 tool로 라우팅되는데 계약 주석은 "tasks 비움"이 정상 경로인 것처럼 기술. degrade 안내 문구("아직 준비 중이에요")도 안전망 발동 시 실패를 미구현으로 오안내.

### 2.2 Planning — LLM 3-stage + 결정론 보강 샌드위치

**구조**: `Planner.plan()` = QA/추천 단일의도 short-circuit → Stage1 팀 선택 → Stage2 agent 선택 → Stage3 todo+DAG 생성(LLM) → 결정론 보강 5종(주제필터 → dataflow 체인 완성 → 해석 feeding → 시간 바인딩 → gap 탐지) → validate_dag. LLM은 메뉴에서 고르기만 하고, 빠뜨리는 것은 순수 함수가 사후 보강한다. ~18개 테스트 파일이 LLM 없이 게이트를 못박음.

**잘된 점**: 결정론 안전망 다층 구조 + 3계층 프롬프트 분리(stage별 필요한 메뉴만 노출)로 토큰·집중도 관리. 주제 게이트가 이름 denylist가 아닌 데이터 계약(REVIEW_DATA_ARTIFACTS) 기반. 카탈로그 drift를 자각하고 실측 근거를 주석으로 박제하는 문화.

**핵심 이슈**
- 🔴 **catalog↔code drift: metric tool 9개의 period 필수가 team_catalog에 미선언** — aov_monthly·cac_overall·grade_revenue·new_members_monthly·promotion_revenue·promotion_roas·repurchase_rate_mom·signup_conversion·unknown_revenue_share 9개는 코드와 per-tool YAML 모두 period 필수(`Missing required param` raise)인데 team_catalog.yaml만 `params_required: []`(실제 줄: 255,279,375,399,405,411,417,435,441). bind_temporal_params(자동 바인딩)와 detect_plan_gaps(사전 탐지)가 team_catalog만 읽으므로 **두 안전망이 동시에 무력화** — Stage3 LLM이 period를 빠뜨리면 곧장 런타임 FAILED. revenue_total·roas_overall만 정합 완료, 형제 9개 방치.
- 🟡 validate_dag가 비차단 — cycle/unknown-dep 탐지해도 로그만 남기고 plan이 execution으로 흘러가며, 결함 todo는 phase 빌드에서 조용히 드롭된다. HITL 검토 화면에도 issues가 전달되지 않음(gaps는 plan 안에 실리지만 frontend 렌더 0건).
- 🟡 HITL modify 후 plan 재검증 부재 — 사용자 편집이 dangling dep을 만들어도 그대로 execution행. plan_editor.remove는 잔존 todo의 depends_on·dag를 청소하지 않는다. (NL 편집 경로는 tm.validate로 탐지하지만 ack에 싣기만 하고 차단에 안 씀)
- 🟡 qa_team/decision_team이 LLM 3-stage 프롬프트에 미반영 — stage1엔 구 `factual_lookup→[]` 규칙 잔존. 복합 쿼리의 추천 sub-intent는 analysis_team의 ai_recommendation tool로 우회 충족되고 있어 완전 차단은 아니나, 신설 팀 라우팅 근거가 프롬프트에 없다.
- 🟢 team_catalog의 `task_agent_hints`·`implicit_prerequisites` 섹션은 코드가 읽지 않는 죽은 메타데이터(실제 자동 삽입은 consumes/produces 메커니즘).

### 2.3 Execution — phase 실행 엔진 + HITL 개입

**구조**: PM 패턴 3분할 — execution_stage(orchestration·이벤트) → hitl_manager(싱글톤 PM: progress·pause/resume/cancel·편집 조율) → executor.execute_phase(순수 실행, asyncio.gather 병렬). phase 내 병렬·phase 간 직렬, FAILED→halt, 데이터 불충분→SKIPPED cascade. 사용자 개입은 ws_hitl → per-session Lock → todo_manager(cascade BFS 무효화 + phase 재구성).

**잘된 점**: data_gate가 tool과 동일한 `find_in_previous`를 사용해 "검사한 것=소비하는 것" 정합을 코드로 보장. resume 멱등성(completed 필터), `_json_safe` 직렬화 정화(F1 크래시 재발 차단), HITL 편집 경로 완성도(pause-only 가드 + Lock + cascade).

**핵심 이슈**
- 🟡 **AgentPool docstring "Eager Init" ↔ 실제 Lazy** — lifespan에 초기화 코드가 전혀 없고 Agent 런타임 인스턴스도 없다(AgentSpec 메타 래퍼만). 기지(旣知)의 의도-코드 gap(메모리 박제: Sprint 15+ ADR 결정 권장)이 docstring 거짓 주장으로 잔존.
- 🟡 todo_start 이벤트가 phase 실행 **완료 후** emit — todo_start/todo_complete가 사실상 동시 도착. 긴 LLM todo가 도는 동안 관찰 콘솔은 해당 phase 무신호(실시간 표시가 phase 단위 사후 재생).
- 🟡 사용자 편집으로 cycle 생성 시 해당 todo들이 조용히 드롭되고 overall_status=COMPLETED(silent drop). mutate 후 validate 호출하지만 rollback 없음.
- 🟡 data_gate 커버리지 = consumes 선언 7/108 tool. 단 검증 결과 보정: metrics 35 등 45개는 previous_results를 소비하지 않는(원천 직접 조회) tool이라 이 게이트의 적용 대상 자체가 아니며, 이들의 0-row 위험은 B2.2/B2.3으로 명시 연기된 별도 등급이다. 게이트 스코프 내 실제 잔여 gap은 consumes 미선언 LLMTool류로 한정(LLMTool 가드가 2차 방어 중).
- 🟡 G6 recovery는 감지·로그까지만 배선(메뉴 빌드는 도달하나 resolve_choice·interrupt 발동·사용자 선택 루프 미배선) — 명시적 partial이나 모듈에 Status 마커 없음.
- 🟢 죽은 코드 6건: executor.build_phases(todo_manager에 dict판 중복 — 이중 유지보수 위험), 미사용 import 2, mock pdf_renderer 도달불가 분기, hitl.get_execution_result 등.

### 2.4 Response — 결정론 표시 dispatcher

**구조**: 2026-06-09 "2c" 전환으로 **response 레이어 LLM 0**. 서술 텍스트는 execution 단계의 LLM tool(report_writer/summary_generator/qa_responder)이 책임지고, Responder는 정직 degrade 2 게이트 → 산출물 종류별 분류·표시만 한다. 시각화는 차트 스펙이 아닌 **파일 attachment**(pdf_renderer=reportlab/pptx_generator=python-pptx 실파일 생성, /api/files/download 링크 — traversal 차단 + outputs/ 한정 보안 실재). chart_generator는 stub.

**잘된 점**: LLM 재서술 제거로 "빈 결과에 환각" 차원을 구조적으로 제거 + 전부 순수 함수라 테스트 용이(전용 테스트 15개+). silent-0 3중 방어(B2.1 게이트 + LLMTool Template Method 가드 + SKIPPED 전파) 정합.

**핵심 이슈**
- 🟡 **FAILED 실행에서 fallback 성공 문구 "분석을 완료했습니다." 노출 가능** — overall FAILED여도 text 채택 로직이 동일 진행되어 완료 산출 0이면 성공 문구가 fallback. 검증 결과 한 겹 더 악화: ws_agent.py:475가 execution FAILED여도 `status="success"`로 complete를 emit. ResponsePayload.error 필드는 설정처 0. **정직 degrade 원칙과 정면 충돌하는 경로.**
- 🟡 tools/catalog의 report_writer.yaml produces가 구 키(report_text) 잔존 — 코드(report_markdown)·team_catalog와 drift. /api/admin/catalog → frontend ToolPalette 툴팁에 **이미 사용자 UI로 노출 중**. (실행 경로는 team_catalog만 쓰므로 동작 무영향)
- ❌ 기각: "report_writer가 감성 3키 하드코딩이라 metric 기반 보고서 구조적 불가" 주장은 **반박됨** — insight_extractor가 06-10 도메인 무관으로 재작성됐고 complete_dataflow_chain+ensure_interpretation_fed가 metric→insights→report_markdown→pdf 체인을 결정론으로 배선한다(바로 그 문제 CP#1이 이미 수정 완료된 상태).
- 🟢 response_stage docstring이 폐기된 "LLM formatter" 서술 유지(진입점 첫인상이 실동작과 반대) 등 문서 drift 4건.

### 2.5 Workflow Managers — turn 상태 관리 cross-cutting 계층

**구조**: hitl_manager(646L)가 핵심 — ExecutionProgress 보유, should_continue 폴링, asyncio.Queue 기반 resume 동기화(run_turn↔ws_hitl), Todo 편집 조율. plan_editor(278L)는 NL→add/remove/modify/reorder LLM 파싱 + injection 방어. 영속화는 전적으로 checkpointer 몫.

**잘된 점**: race 방어 체계(Queue로 wait/clear race 구조 회피, stale guard 일관 적용, cleanup 멱등), plan_review/execution_pause 편집 경로 단일화(A3 Phase 5), recovery의 기계/메뉴(YAML) 2층 분리, 엣지케이스 버그픽스의 근거 주석 박제 문화.

**핵심 이슈**

**구조**: 입력 관절 DataSource(get/list_sources/has — SOURCE_REGISTRY 30 source 단일 진실)와 출력 공유 Workspace(raw|cleaned|computed 3-Layer)가 대칭 쌍. 둘 다 file/postgres 이중 백엔드, **`.env` 실측 DATA_BACKEND=postgres 활성**(octormate_data, schema-per-client). 전환은 lifespan의 set_* 2회 호출로 전 파이프라인 일괄(관절 1곳). 대용량은 save_stream/iter_streamed_rows "호스"(265MB ga4_page_events 실사용).

## 3. 시스템 수준 핵심 발견 (교차 검증 완료)

### 3.1 🔴 layer guard 상태 어휘 drift — 부분 실패가 전체 실패(fatal abort)로 격상, **프로덕션 발화 실증**

[layer_inspector.py:91](../../backend/app/dream_agent/system_graph/layer_inspector.py)이 `status == "success"`를 검사하지만 실제 TodoStatus enum은 `completed/failed/skipped`("success" 없음, execution_result.py:14-19). succeeded 카운트가 실데이터에서 영원히 0 → **failed 1개만 있어도 EXECUTION_ALL_FAILED(fatal)** 로 판정되어 ws_agent가 turn 전체를 abort. 설계된 EXECUTION_PARTIAL_FAILED(warning) 분기는 도달 불가. 단위테스트 LG-04도 같은 "success" 가짜 어휘로 GREEN — 테스트가 drift를 영속화.

**이론이 아니다**: 루트 `logs/layer_guard.jsonl`의 2026-06-10 entry에 `execution_todos_total: 12, failed_count: 1`이 EXECUTION_ALL_FAILED(fatal)로 기록된 실사례 존재 — 12개 중 1개 실패가 "전부 실패"로 abort된 프로덕션 발화 증거.

### 3.2 🔴 hitl_ack `accepted` 프로토콜 거짓말 — 항상 false + frontend 연쇄

legacy `_run_agent` 폐기(05-31) 때 `create_request` 호출이 함께 사라졌는데 ws_hitl.py:202가 여전히 `submit_response`를 호출 — `_response_events`에 request_id가 등록된 적이 없으므로 **모든 plan 승인/거부에서 hitl_ack가 accepted:false로 발신**된다(실제 resume은 signal_resume Queue로 정상 동작 — 프로토콜 계약과 실동작이 정반대). 연쇄 효과:
1. frontend hitl store가 `ack.accepted && approve`일 때만 pending을 해제 → **pending이 ack로는 영구 미해제**, 자동승인 후에도 PlanReviewModal이 잔존 가능(GlobalLayout 상시 마운트 + `!!pending?.plan` open 조건).
2. 잔류 모달 재클릭 시 중복 hitl_response → Queue 버퍼링 → 다음 interrupt가 stale action 소비 위험(reject면 turn 종료).
3. 관찰 콘솔(eventLogStore)이 모든 승인을 'rejected'로 오표기 — **"빌더용 정합성 검증 콘솔"이 거짓 신호를 표시.**

수정 방향: submit_response 호출 제거 + signal_resume 성공 여부로 accepted 구성, legacy 레지스트리/HITLRequest 모델군 일괄 정리.

### 3.3 🔴 학습 페어 수집 인프라의 전면 공백

## 4. 종합 평가

### 4.1 잘 만들어진 것 (유지·확산할 패턴)

1. **convention-over-hardcoding이 실제로 작동** — tool 등록(91/91 무필드 import), 클라이언트 프로필(YAML 한 장), client 폴더, frontend client 선택까지 일관.
