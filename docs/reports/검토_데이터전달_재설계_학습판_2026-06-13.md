## §0 용어 직답 — "tool끼리 데이터 전달 설계 = 컨텍스트 엔지니어링인가?" → **아니다**

- **컨텍스트 엔지니어링** = "LLM 샘플링 시 포함되는 토큰 집합의 큐레이션" (Anthropic 공식 정의, anthropic.com/engineering/effective-context-engineering-for-ai-agents). LLM이 *보는* 것에 관한 설계만.
- **하네스 엔지니어링** = 모델 바깥 비계 전부 — 실행 루프·게이트·검증·HITL·재시도 (OpenAI가 2026-02 공식 명명 openai.com/index/harness-engineering, Fowler 사이트가 체계화. "Agent = Model + Harness").
- **판별 질문 한 줄**: *"이 설계가 실패하면 LLM이 오판하는가(→컨텍스트), 실행이 틀리거나 거짓 성공하는가(→하네스)?"*
- tool→tool 전달(LLM 안 거침)은 **하네스의 데이터플로 영역** = 일반 소프트웨어 엔지니어링 (12-factor agents Factor 4 "Tools are structured outputs"). 같은 previous_results 라도 **LLM 프롬프트에 들어가는 경로만** 컨텍스트 엔지니어링이다 — dropped=81 사고가 정확히 그 교차점.
- OctorAD 자산 분류 (조사 결과): **하네스 = 과발달**(게이트 28·HITL·recovery — 가장 두꺼움), **컨텍스트 = 미발달**(토큰 예산·compaction 정책 없음 — 부산물로만 존재), **제3범주 = 데이터플로 계약 = 이번 문제의 자리**.

## §1 (의제1) 멀티쿼리는 왜 잘 되나 — 3층 구조, 그리고 의외의 사실

**구조 = 계약(1층) × 메뉴(2층) × 수선(3층):**

1. **계약층**: cognitive가 자연어를 StructuredQuery로 번역. intent(PMAL)가 canonical, tasks는 순수 함수 파생(비결정 한 축 제거). 복합이면 sub_intents 나열 + **단일의도 지름길(QA/추천 직행)이 sub_intents≥2면 비켜섬** (planner.py:649-653 — 이게 없으면 복합쿼리가 단일 todo로 납치, 06-10 이전 실측 붕괴).
2. **메뉴층**: LLM 3단(팀→agent→tool)이 매 호출 선택지를 점진 축소 — Stage3는 92개가 아니라 보통 10~30개 **닫힌 메뉴**에서 선택(이름 생성 아님 = 환각 구조적 차단). stub 0 원칙으로 메뉴의 모든 항목이 실제 작동.
3. **수선층**: LLM 출력이 그대로 실행되지 않고 결정론 게이트 배터리(G02→G05→G03→G04→G06→G07→G08 — **순서 자체가 설계**)를 통과.

**의외의 사실 (오너 기준에 중요)**: 계획 coverage 100%는 "LLM이 완벽해서"가 아니다 — 실측(measure_gate_correction)으로 **복합 14쿼리 중 42.9%에서 게이트가 실제 발동, rewrite 24건(삭제 6·삽입 18)** 후의 100%다. 즉 **계획층 게이트(G02~G08)는 덕지덕지가 아니라 멀티쿼리 성공의 주역** — "게이트 많음이 문제"는 계획층이 아니라 전달/실행층 이야기로 좁혀야 정확하다.

**보존 목록 5 (재설계 시 불가침 — 각각 깨지면 생기는 일 박제)**:
| # | 보존 대상 | 깨지면 |
|---|---|---|
| 1 | Intent(PMAL) 계약 + shim 파생 + sub_intents≥2 양보 | 복합쿼리가 단일 todo로 납치 (lv4 붕괴 복귀) |
| 2 | 닫힌 카탈로그 메뉴 (+stub 0) | tool 환각·"되는 척" 복귀, F2 거짓 리포트 재발 |
| 3 | 게이트 배터리와 **그 순서** (순수·멱등·setdefault) | 리뷰 체인 ~40% silent-0 복귀, 14쿼리 중 ~43% 영향권 |
| 4 | 카탈로그 메타의 코드 실측 무결성 + SCOPE_PARAMS 1곳 | G03·G07·실행 게이트 3중 동시 실명 (report_writer 사건 모드) |
| 5 | 정직 degrade (게이트는 값을 지어내지 않음) | 그럴듯한 쓰레기 숫자가 자신 있게 표출 — G7/G8 불합격 복귀 |

## §2 (의제2) tool↔tool 전달의 현 구조 — 전수 지도

**3평면 확정** (메모리 박제 "State/Context/Class"의 코드 실체):
- **State** = LangGraph AgentState (execution_result — 256KB 초과는 state_guard 참조 스텁)
- **Context** = ExecutionContext.previous_results ({todo_id: COMPLETED data} — tool간 전달의 본선)
- **Class** = BaseTool.fetch→DataSource (창고 — 유일하게 client 스코프 있음)

**tool A→B의 길 4갈래** (전부 "키 문자열 = 계약", 출처 라벨 0):
1. **주입(push)**: `_inject_prev_outputs` — 상류 전 키를 setdefault 복사. 제외는 `_`접두·SCOPE_PARAMS 단 2종. 충돌 승자: planner 명시값 > 먼저 완료된 상류 (순서는 어디에도 로그 안 됨)
2. **당김(pull)**: `find_in_previous` — 첫 발견 승
3. **LLM 주입**: 무차별 키 스캔 → 수기 denylist(_NOISE) → json 600바이트 제한 → 평면 dict를 `json.dumps[:3000]`으로 프롬프트에 (dropped=81 사고의 경로: denylist에 없어서 통과 → 무라벨 주입 → LLM이 의미 발명)
4. **창고 경유**: _storage → fetch

**신규 발견 (이번 해부에서)**: **카탈로그가 2개다** — `tools/catalog/**/*.yaml`(ToolSpec용)과 `planning/catalog/team_catalog.yaml`(게이트용). 이미 어긋남 실재: report_writer가 tools/catalog엔 `produces: report_text`(구버전), team_catalog엔 `report_markdown`(수정됨) — **같은 tool에 두 진실**. drift 경고가 적중한 추가 사례.

## §3 (의제3) 파생 문제 — tool 92→200 시나리오 (터지는 순서대로)

1. **키 충돌 (즉시)**: produces 네임스페이스가 전역·평면. `count`는 이미 collector 21종 전부가 produce. 200개면 generic 명사(total/rate/items) 충돌 확률 ≈ 1 — setdefault 주입이라 **무음 오바인딩**, 게이트는 non-empty만 봐서 통과.
2. **같은 이름 다른 의미 (이미 발생)**: dropped=81이 원형. 회원 이탈 분석 tool이 진짜 dropped를 만들면 누가 이기는지는 완료 순서가 결정 — 의미 검증 0.
3. **LLM payload 비대 (plan 길어지는 즉시)**: 무차별 스캔 + 3000자 절단 — 뒤쪽 키는 무음 탈락.
4. **디버깅 불가**: "이 값 어디서 왔지?"에 답할 기록(provenance) 0.
5. **멀티스코프 불가 (멀티쿼리의 다음 천장)**: 같은 tool을 다른 기간으로 2번 호출 — 계획 반쯤 가능, 실행 가능, **소비 불가**(이름 평면에서 첫 발견 승이라 두 번째 산출은 영원히 그늘). "4월 매출과 3월 ROAS 비교해줘"가 현 구조의 벽. **§1의 성공이 이 천장 위에 서 있다.**

**주류 결론**: 단일 이론이 아니라 4패턴 계층 조합 — 내부=공유 상태(현대화된 블랙보드), 경계=명시 핸드오프+투영, tool 관리=registry+동적 로딩, 큰 데이터=**참조로 주소화**(컨텍스트에 안 붙임). 순수 메시지 패싱은 LLM 계층에선 비주류.

## §6 (의제6) 종합 — 무엇을 가져와 어디에 쓰나
