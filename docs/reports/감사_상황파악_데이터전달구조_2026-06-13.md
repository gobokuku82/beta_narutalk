## §2 기록이 보여주는 진짜 패턴 (감사관 종합 — 양쪽 모두에게 불편한 결론)

1. **오너 우려는 매번 질문형으로 제기 → Claude가 합리적 설명으로 응답 → 오너 수용 → 작업 방향 유지.** 개별 결정은 전부 절차적으로 승인됐으나, **우려의 누적 방향(게이트 억제·tool간 계약)과 실제 작업 방향(게이트 추가·계약 연기)의 괴리**가 기록상 실체다. 책임 소재: 매번 프레임을 만든 것은 Claude의 권장이고, 오너는 그 프레임 위에서 승인했다.
2. **"계약 수술 대신 게이트"가 기록된 결정 3회**: 06-05(silent-0 전면 계약 수리 보류 — 오너 비준), 06-08(per-tool consumes 선언 대신 LLMTool 부모 가드 일반화), 06-11(G06 계약 흡수 기각 — "계약은 검증, 채움은 planning"). 전부 사유 박제 — 무단 회피는 아니나 같은 방향으로 3회 누적.
3. **균형 사실**: 28개 중 선제 추정 출생은 초기 8개뿐, 다수는 실측 사고 대응이며, F2·슬라이스1·L3/L4는 게이트+계약 수술 **병행** 사례. "전부 덕지덕지"도 "전부 정당"도 기록과 다름.
4. **오너 기억의 세부(지시 시점·산출물 유무)는 일부 기록과 다르지만, 직관의 방향(구조 문제·계약 부재·게이트 과다)은 기록과 외부 자료가 모두 지지한다.** — §3.

## §3 외부 조사 — 업계는 이 문제를 어떻게 푸는가

### 3.1 데이터 엔지니어링 진영 (정설: "Contracts define expectations. Gates enforce them.")

| 패턴 | 우리 문제 매핑 | 출처 |
|---|---|---|
| **Data Contracts** (ODCS v3.1 표준) — schema + **semantics(단위·정의·분모)** + 품질 규칙 + 소유권의 기계가독 계약 | "값만 흐르는" tool 경계에 semantics 1급 추가 — 문제의 정의 그 자체 | bitol-io.github.io/open-data-contract-standard |
| **dbt model contracts** — 계약 위반 산출물은 **생산 시점에 거부** (preflight) | catalog≠code drift를 사후 게이트가 아니라 산출 시점 차단으로 (shift-left) | docs.getdbt.com/docs/mesh/govern/model-contracts |
| **Semantic/Metric Layer** (MetricFlow·Cube·LookML) — 지표의 분자·분모·grain을 registry에 1회 정의, 하류는 재계산 금지·이름 조회만 | **다중 ROAS 사고의 정석 해법.** LLM 접지 시 정확도 +17~23%p 벤치마크 | docs.getdbt.com/docs/use-dbt-semantic-layer |

| **OpenLineage / W3C PROV** — 값의 출처(Job·Run·Dataset + facets) 표준 어휘 | "이 ROAS는 어느 tool이 어떤 입력·정의로 계산했나" 기록 | openlineage.io/docs/spec/facets |
| **Great Expectations** — 게이트는 독립 저작물이 아니라 **계약에서 자동 파생되는 집행 코드** | "게이트 28개 각자 저작" 구조의 교정 방향: 계약 1 → 게이트 N 파생 | ataccama.com (shift-left playbook) |

**정설 요약**: 게이트를 각자 저작하면 규칙이 분산 복제돼 '좋은 데이터'의 공유 정의가 사라진다 — **오너의 "게이트 많은 게 문제" 직관은 업계 진단과 일치.** 단 교정은 게이트 삭제가 아니라 계약 수립 → 게이트를 계약의 파생물로 재편성.

## §4 종합 판정

1. **구조 문제라는 오너 진단 = 타당** (기록·업계 양쪽 지지). 정밀한 형태: "게이트가 많아서"가 아니라 "**계약 없이 게이트가 각자 저작돼서**" — 계약이 서면 게이트 다수는 계약의 파생 집행물로 흡수·재편.
2. **오너 제안(#3 데이터 성격의 state 기록) = 업계 5출처 수렴 방향.** 구체화: state에는 manifest(이름·성격 3분류·단위·정의·스코프·위치·생산자), 본체는 창고, LLM 입력은 결정론 거름 1차 + 의미 동봉 2차, 지표는 registry 1회 정의(semantic layer 결).
3. **"초반 설계부터 다시"의 올바른 범위 = 계약 층** (tool 산출물 계약 + 지표 registry + state manifest). 코드 전면 재작성은 비추천 — 92 tool·956 테스트·측정 인프라가 재설계의 입력 자산. 이행은 오너 자신의 원칙(점진 추가 → 전환 Sprint)으로.
4. **Claude의 책임 (감사관 자기 판정)**: 방향 신호의 누적을 개별 결정의 합리성으로 반복해 덮은 프레임 책임. 06-11 '대기발령+면접' 제안의 변형 채택과 06-12 "더덕더덕" 질문에 대한 옹호가 대표 사례.
