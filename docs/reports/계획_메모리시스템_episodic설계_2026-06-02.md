## 0. 한 줄 요약

사용자가 요청한 "대화/답변/변환과정/todo/시간 저장 + 추후 검색"은 에이전트 메모리 이론에서 **episodic memory(과거 턴의 ground-truth 기록)** 에 정확히 해당한다. `system_data/memory/`에 **JSONL 파일(대화방당 1파일)** 로 시작하고, **Store 추상화 계층**을 두어 추후 PostgreSQL/pgvector로 **코드 변경 없이** 교체한다. 저장 시점은 이미 코드에 존재하는 턴 종료 지점([ws_agent.py](../../backend/api_v2/ws_agent.py) `_emit_complete("success")`) 하나뿐이라 통합이 깔끔하다.

## 1. 사용자 의도 분석 (정확히 재진술)

사용자가 메모리에 담겠다고 한 것:

| # | 사용자 표현 | 시스템에서 실제 데이터 | 출처 |
|---|---|---|---|
| 1 | 사용자 대화 | `user_input` (자연어 쿼리) | WS payload |
| 2 | 에이전트 답변 (시각화 포함) | `response` (`ResponsePayload`: text/summary/attachments) | [response_payload.py](../../backend/app/dream_agent/schemas/response_payload.py) |
| 3 | 사용자언어 → 에이전트언어 변환 과정 | `structured_query` (`StructuredQuery`) | [cognitive/](../../backend/app/dream_agent/cognitive/) → [structured_query.py](../../backend/app/dream_agent/schemas/structured_query.py) |
| 4 | todo 생성 과정 | `plan` (`Plan`: teams_selected/todos/dag/plan_notes) | [planning/planner.py](../../backend/app/dream_agent/planning/planner.py) |
| 5 | 생성된 todo_workflow (todo_card) | `plan.todos[]` (`PlannedTodo`) | 동상 |
| 6 | 시간 | created_at + 단계별 duration | save 시점 + `execution_result` |
| 7 | (추후) memory_manager가 유저 요청 시 검색 | `search_turns()` | [memory_manager/](../../backend/app/dream_agent/workflow_managers/memory_manager/) |

**결론: 의도는 명확하고 타당하다.** 7개 항목 모두 현재 코드에 이미 존재하는 산출물로 1:1 매핑된다. 새로 만들 데이터가 아니라, **이미 흐르고 있는 데이터를 영구 보관**하는 작업이다.

## 2. 평가 — 잘된 점 / 보완할 점 / 바로잡을 점

> 사용자가 초보자이며 바이브코딩 기반이므로, 의도를 존중하되 빠진 구조를 적극 보완한다.

### 2-A. 잘 잡은 점 ✅
- **저장 단위를 "턴(turn)" 으로 잡은 것**: 항목 1~6이 전부 한 번의 쿼리-응답 사이클에 속한다. 이게 곧 episodic memory의 "에피소드" 단위 → 이론적으로 정확.
- **테스트는 폴더, 운영은 DB로 분리한 것**: POC를 파일로 시작하고 추후 교체하겠다는 판단은 업계 표준 경로다(예: Claude Code도 대화를 세션당 JSONL 1파일로 저장 → 추후 인덱싱).
- **변환 과정(structured_query)까지 저장하려는 것**: 이건 기존 사내 계획(Sprint 15 L2)보다 **한 단계 더 깊은 좋은 결정**이다 (§3 참조).

### 2-B. 반드시 보완할 점 ⚠️ (초보자가 놓치기 쉬운 구조)

1. **"폴더만 만들면 된다"가 아니라 "교체 가능한 저장 계층(Store 추상화)"이 핵심.**
   → 파일 경로를 코드 곳곳에 하드코딩하면 추후 Postgres 전환 시 전부 뜯어야 한다. **`MemoryStore` 추상 클래스 + `FileMemoryStore` 구현**으로 두면, DB 전환 시 **새 구현 1개만 추가**하면 끝. 이 패턴은 **이미 이 코드베이스에 존재**한다 → [session.py](../../backend/app/dream_agent/workflow_managers/session_manager/session.py)의 `SessionStore`(ABC) → `MemorySessionStore`/`RedisSessionStore`. 똑같이 따라가면 된다. **이게 이번 설계의 1순위 보완점.**

2. **기존 로깅과 중복하지 말 것.** 이미 비슷한 게 두 개 돌고 있다:
   - [trace_logger.py](../../backend/app/dream_agent/workflow_managers/learning_manager/trace_logger.py) → `logs/traces/*.jsonl` (레이어별 실행 트레이스, 디버깅/분석용)
   - [query_logger.py](../../backend/app/dream_agent/workflow_managers/learning_manager/query_logger.py) → `logs/queries/*.jsonl` (쿼리 패턴 통계용)
   → 이들은 **분석/통계용 append-only 로그**고, 메모리는 **사용자에게 복원·검색해 보여주는 대화 기록**이다. **목적이 다르니 분리 유지**하되, 메모리에 trace 원본을 중복 저장하진 않는다(필요 시 turn_id로 참조만).

3. **시각화 "재표시"를 위한 데이터까지 저장해야 함.** 사용자는 "시각화 있을 땐 그것도 표시"라고 했다. 차트를 **다시 그리려면** 차트 텍스트만이 아니라 **차트 데이터/스펙**이 필요하다. 따라서 `response.attachments`(차트 스펙) + 시각화 todo의 데이터를 저장 대상에 포함한다 (§5 저장 깊이 결정).

4. **동시 쓰기 안전성.** 파일 append는 여러 턴이 동시에 쓰면 깨질 수 있다. 대화방별 `asyncio.Lock` 또는 단일 write로 직렬화한다 (§9 리스크).

5. **스키마 버전.** 추후 필드가 늘어날 것이므로 모든 레코드에 `schema_version`을 박는다. 이는 사용자가 이미 정한 원칙(JSONB + schema_version + Optional + append-only)과 정합 → 메모리 `project_extension_ease_priority`.

### 2-C. 바로잡을 점 (기존 계획의 stale 부분)
- 기존 [sprint15_memory_plan.md](../_claude/checkpointer/sprint15_memory_plan.md)는 `api_v2/ws_agent.py`를 가정했는데, 실제 진입점은 `backend/api_v2/ws_agent.py`로 **이미 존재**하고 저장 훅 위치도 명확하다(§7).
- 기존 계획은 곧장 PostgreSQL을 가정했으나, **사용자 요청대로 파일 우선**으로 바꾼다. Store 추상화가 있으니 두 계획은 충돌하지 않고, 파일 → DB는 자연스러운 연속선이다.
- 기존 L2 저장은 `structured_query`를 **저장하지 않았다.** 사용자 요청대로 **포함**한다(개선).

## 3. 개념 정립 — 이건 "episodic memory"다 (외부 근거)

에이전트 메모리는 인지과학에서 빌려온 4종으로 구분된다(CoALA 프레임워크):

| 메모리 종류 | 내용 | 이번 작업 해당 |
|---|---|---|
| Working (in-context) | 현재 컨텍스트 창 | AgentState (휘발) |
| **Episodic** | **과거 사건(대화 에피소드) 원본** | **★ 이번 작업** |
| Semantic | 정제된 사실/지식 | 추후 (요약·학습) |
| Procedural | 행동 규칙 | 추후 (skill, 미구현) |

2026년 기준 베스트프랙티스:
- **"raw 에피소드를 그대로 보존하고, LLM 과도 추출을 최소화"** (MemMachine 등) → 우리가 산출물(structured_query/plan/response)을 **가공 없이 통째로** 저장하는 방향이 정답.
- **단기 버퍼(최근 N턴) ↔ 장기 저장** 이중 구조(Zep) → 우리도 이미 단기 주입 슬롯([history_injector.py](../../backend/app/dream_agent/cognitive/history_injector.py))이 있고, 메모리는 장기 저장을 맡는다.
- **파일(JSONL) → Postgres+pgvector 이관**이 흔한 경로이며, 이관 시 **UNIQUE 제약(turn_id 중복 방지)** 이 실수 포인트.

> 즉 사용자의 직관(대화를 그대로 쌓아두고 나중에 찾는다)은 최신 이론과 정확히 일치한다. 우리는 거기에 "교체 가능한 저장 계층"만 입히면 된다.

근거 출처:

- [Memory for Autonomous LLM Agents (arXiv)](https://arxiv.org/html/2603.07670v1)
- [MemMachine (arXiv)](https://arxiv.org/pdf/2604.04853)
- [Searchable Agent Memory in a Single File](https://eric-tramel.github.io/blog/2026-02-07-searchable-agent-memory/)

## 4. 저장 대상 스키마 (레코드 설계)

### 4-A. Turn 레코드 (= 1 에피소드, 1 JSONL 줄)

```jsonc
{
  "schema_version": 1,
  "record_type": "turn",

  // ── 식별 (AgentState에서 그대로) ──
  "user_id": "demo",
  "conversation_id": "<uuid>",
  "turn_id": "<uuid>",
  "turn_index": 3,
  "client_id": "clumi",
  "thread_id": "<conv>_<turn>",          // Checkpointer 참조

  // ── 시간 ──
  "created_at": "2026-06-02T04:12:33Z",  // 저장 시점 (ISO8601 UTC)
  "duration_ms": 8421,                    // 턴 전체 소요
  "status": "success",                    // success|rejected|cancelled|aborted|failed

  // ── ① 사용자 대화 ──
  "user_input": "지난 3개월 인스타 광고 성과 분석해줘",
  "language": "ko",

  // ── ② cognitive: 사용자언어→에이전트언어 변환 결과 ──
  "structured_query": { /* StructuredQuery.model_dump() */ },
  //   targets(brand/source/period/keywords) · goal(type/format/depth)
  //   · tasks[] · meta(confidence, ambiguity, missing)  ← "변환 과정"의 근거가 여기 박힘

  // ── ③④⑤ planning: todo 생성 결과 + todo_card ──
  "plan": { /* Plan.model_dump() */ },
  //   teams_selected[] · todos[](id, task_type, agent, tool, tool_params,
  //   depends_on, rationale) · dag · plan_notes  ← "todo 생성 과정"의 근거가 rationale/plan_notes에

  // ── ② 에이전트 답변 (+ 시각화) ──
  "response": { /* ResponsePayload.model_dump() */ },
  //   format · text · summary · next_actions[]
  //   · attachments[](kind=chart/image/pdf, path/url, meta=차트 스펙)  ← 시각화
  "response_summary": "인스타 ROAS 3.2, 전월比 +12% ...",  // 검색/주입용 짧은 요약

  // ── 실행 결과 (시각화 재표시 데이터 포함) ──
  "execution_result": { /* ExecutionResult.model_dump() (대용량 raw는 §5 가드) */ },

  // ── ★ L3-full: 변환/생성 "과정" 원본 (레이어별 단일 기록자 키에서, §5-B) ──
  "process_trace": {
    "cognitive": [ /* §5-B step[] : prompt/raw_response/structured_query */ ],
    "planning":  [ /* team→agent→todo 3단계 step[] */ ]
  },

  // ── 운영 메타 ──
  "is_meta": false,        // Sprint16: memory_query 응답 자체는 true(재귀 검색 제외)
  "embedding": null        // RAG 미정 — 자리만 비워둠
}
```

## 5. ★ 저장 깊이 — **L3-full 확정 (2026-06-02 사용자 결정)**

차트를 다시 그리고 "과정"을 보여주려면 어디까지 저장하느냐가 핵심 trade-off였고, 사용자는 **가장 깊은 L3-full** 을 선택했다("변환/생성 과정"을 끝까지 보겠다는 의도와 정합).

| 옵션 | 저장 범위 | 비고 |
|---|---|---|
| L2 (기존 사내계획) | user/response + plan + execution_result 요약 | structured_query 누락 |
| L3-lite | L2 + structured_query 전체 + response 전체(시각화 포함) + execution_result | 산출물만 |
| **L3-full ⭐ (확정)** | 위 + **LLM 원본 프롬프트/응답** + **planning 3단계 중간선택**(team→agent→todo) | 과정 전부 |

### 5-A. ⚠️ L3-full의 숨은 비용 — "저장 키우기"가 아니라 "포착 훅 추가"

초보자가 놓치기 쉬운 핵심: **LLM 원본 프롬프트와 3단계 중간선택은 현재 `final_state`에 없다.** cognitive/planning 내부에서 로컬 변수로 만들어졌다가 **버려진다**:
- [cognitive_stage.py](../../backend/app/dream_agent/cognitive/cognitive_stage.py) L118: `user_prompt`/`system_prompt`/`raw`(LLM 원본 응답)가 함수 안에서만 존재.
- [planner.py](../../backend/app/dream_agent/planning/planner.py): `teams_selected`→`agents_selected`→`todos` 3단계와 각 단계 프롬프트가 내부에만 존재(최종 `Plan`엔 `teams_selected`만 남음).

따라서 L3-full은 **저장 시점 코드만 바꿔선 불가능**하고, **cognitive/planning 단계에 "중간단계를 기록하는 훅"을 심어야** 한다.

### 5-B. 포착 메커니즘 — **레이어별 단일 기록자 키 (재검증 후 수정안)**

> ⚠️ v1.1에서 "공용 `AgentState.trace`에 각 단계가 append" 라고 했으나 **재검증에서 결함 발견** → 아래로 교정(§13 검증로그 D1).

**왜 공용 `trace` 한 칸은 안 되나:**
- `AgentState.trace`는 [agent_state.py](../../backend/app/dream_agent/states/agent_state.py) L65/L124에서 **reducer 없는 순수 list**(초기 `[]`, 아무도 안 채움). LangGraph 기본 채널은 `LastValue`(덮어쓰기)다.
- 게다가 [ws_agent.py](../../backend/api_v2/ws_agent.py) `_broadcast_chunks`는 chunk마다 `final_state.update(node_state)`로 **per-key dict.update 재구성**을 한다(L309~311). 즉 cognitive가 `trace=[A]`, planning이 `trace=[B]`를 쓰면 **final_state엔 `[B]`만 남고 cognitive 기록이 소실**된다.

**교정안 — 노드마다 "자기 전용 키"에 기록 (단일 기록자 = 충돌 없음):**

| 키 | 기록자(유일) | 내용 |
|---|---|---|
| `cognitive_trace` | cognitive 노드만 | system/user_prompt, LLM raw_response, parsed=structured_query, duration |
| `planning_trace` | planning 노드만 | 3단계(team→agent→todo) 각 prompt/response/선택결과 + plan_notes |
| (선택) `execution_trace` / `response_trace` | 각 노드만 | tool 호출/포맷 단계 |

→ 각 키는 **한 노드만 쓰므로** `final_state.update`(또는 reducer 무관) 어느 방식이든 **안전하게 보존**된다. 검증 완료: execution/response 노드는 현재 trace류 키를 안 쓰므로 충돌원은 cognitive/planning 둘뿐(§13 D2).

각 step 구조(키 값 = step[] ):
```jsonc
{ "stage": "cognitive",            // cognitive | planning.team | planning.agent | planning.todo
  "system_prompt": "...",           // LLM 원본 (size 주의 — 5-C)
  "user_prompt": "...",
  "raw_response": { /* LLM 원본 출력 */ },
  "selected": { /* 단계 선택 결과 (teams_selected / agents_selected / todos) */ },
  "duration_ms": 1240,
  "ts": "2026-06-02T04:12:25Z" }
```
→ `save_turn`이 `process_trace = {cognitive: cognitive_trace, planning: planning_trace}`로 조립 저장(§4-A).

**왜 `trace_logger`를 안 쓰나(교정된 근거):** [trace_logger](../../backend/app/dream_agent/workflow_managers/learning_manager/trace_logger.py)는 코드는 있으나 [decorators.py](../../backend/app/core/decorators.py)의 `@trace_log`가 **어떤 stage에도 적용돼 있지 않다(적용 0)**. 게다가 입력을 **500자로 truncate** + **날짜별 파일** 기록이라 "원본 프롬프트 전체 · 턴 단위 복원"이 핵심인 L3-full엔 구조적으로 부적합 → 부활 안 함.

### 5-C. L3-full 용량 주의 + 완화
- system_prompt에는 few-shot 예시·catalog가 통째로 들어가 **턴마다 수 KB 반복**될 수 있다.
- 완화(선택): 정적 system_prompt는 `prompt_hash` + `prompt_version`만 저장하고 본문은 버전 테이블에 1회 보관(dedup). **POC 기본값은 inline 저장**(단순 우선), 용량 문제 시 dedup 전환.
- `raw_response`가 큰 데이터테이블이면 §9 R2 size-guard 동일 적용.

## 6. 폴더/파일 구조 (`system_data/`)

```
system_data/
└─ memory/
   └─ {user_id}/                        # 추후 다중 사용자 대비 파티션 (지금은 demo 하나)
      ├─ conversations.jsonl            # 대화방 인덱스 (append + 갱신)
      └─ turns/
         └─ {conversation_id}.jsonl     # 대화방별 턴 로그 (append-only, 1줄=1턴)
```

설계 이유:
- **대화방당 1파일** → 대화 복원(`get_turns`)이 파일 1개 읽기로 끝남. 스크롤 페이징도 tail 읽기.
- **append-only JSONL** → 쓰기가 단순(O(1) append)하고, 손상 시 마지막 줄만 영향.
- **user_id 파티션** → Postgres 전환 시 `WHERE user_id=` 인덱스와 동형. POC는 `demo` 하나뿐이라 실질 평면.
- ⚠️ **빈 폴더를 미리 git에 박지 않는다.** (사용자가 현재 gitkeep/빈폴더 정리 중) → 폴더는 **첫 실행 시 코드가 생성**(`mkdir(parents=True, exist_ok=True)`). `system_data/`는 런타임 데이터이므로 **`.gitignore`에 추가**.

## 7. 통합 지점 (정확한 코드 위치)

### 7-A. 저장 (필수, 이번 작업의 핵심)

**위치 = [ws_agent.py](../../backend/api_v2/ws_agent.py)의 `_emit_complete` 함수 내부** (L282 정의). 재검증 결과 이게 정답이다: `_emit_complete`는 success/rejected/cancelled/aborted **모든 종료 경로가 통과하는 단일 funnel**이고, 클로저로 `final_state`·`conv_id`·`turn_id`·`user_id`·`payload`·`thread_id`를 전부 들고 있다. 여기 한 곳에 넣으면 **모든 상태가 status 라벨만 다르게 일괄 저장**된다(성공만 저장하는 것보다 견고 + "실패한 작업" 질의 대비).

```python
async def _emit_complete(status: str, *, reason: str | None = None) -> None:
    # ── 저장 소스 = 체크포인트 병합 상태(권위) — resume_only 경로 대비 (D3) ──
    try:
        snap = await agent.aget_state(config)
        vals = snap.values if (snap and snap.values) else final_state
    except Exception:
        vals = final_state                      # checkpointer 없는 테스트 경로 fallback
    # ── 메모리 저장 (모든 종료 상태, status 라벨만 다름) ──
    try:
        await memory.save_turn(
            user_id=user_id, conversation_id=conv_id, turn_id=turn_id,
            user_input=payload.get("user_input", ""),
            language=payload.get("language", "ko"),
            client_id=payload.get("client_id"),
            structured_query=vals.get("structured_query", {}),
            plan=vals.get("plan", {}),
            response=vals.get("response", {}),
            execution_result=vals.get("execution_result", {}),
            process_trace={                                      # ★ L3-full §5-B
                "cognitive": vals.get("cognitive_trace", []),
                "planning":  vals.get("planning_trace", []),
            },
            thread_id=thread_id, status=status,
        )
    except Exception:
        logger.exception("memory save_turn failed", turn_id=turn_id)   # 저장 실패가 응답을 막지 않음 (R10)
    ... (기존 broadcast 로직) ...
```

검증으로 확인된 근거·주의:
- **저장 소스 = `aget_state(config).values` (D3 교정)**: `final_state`는 스트리밍 chunk만 누적해 `resume_only`(재시작 복원) 경로에서 재시작 전 cognitive 출력(`structured_query`/`cognitive_trace`)이 빠진다 → 체크포인트 병합 상태에서 읽으면 정상·복원 경로 **둘 다** 완전. checkpointer 없는 테스트는 `final_state`로 fallback.
- **단일 기록자 키 보존**: structured_query/plan/execution_result/response 및 `cognitive_trace`/`planning_trace`는 각자 한 노드만 쓰는 키라 채널 충돌 없음(§5-B). *공용 `trace` 한 칸이었다면 소실됐을 것.*
- **계측(P2.5) 선행**: 두 trace 키가 채워지려면 cognitive_stage·planner가 step을 반환하도록 먼저 계측. 계측 전엔 `[]`로 저장돼도 무방(점진).
- **단일 호출 보장**: `_emit_complete`는 각 종료 경로에서 1회만 호출되고 직후 `return` → **중복 저장 없음**(검증 §13 D5). 방어적으로 `save_turn`은 turn_id 멱등(같은 turn_id 재저장 시 덮어쓰기/스킵).
- `_json_safe`(같은 파일 존재) 재사용으로 NaN/pandas 안전 직렬화.

### 7-B. 불러오기 — 이전 대화 context 주입 (권장, 멀티턴 기억)

현재 `conversation_history`는 **클라이언트가 payload로** 넘긴다([ws_agent.py](../../backend/api_v2/ws_agent.py) L175). 이를 **서버측 메모리에서** 채우도록 전환:

```python
# run_turn / runner 시작부, state 빌드 직전
history = await memory.get_history_for_cognitive(conv_id, limit=history_limit)
# → payload["conversation_history"] = history (없을 때만 fallback)
```

[history_injector.py](../../backend/app/dream_agent/cognitive/history_injector.py)가 `{turn_index, user_input, response_summary}` 포맷을 **이미 소비 준비** 완료 → 데이터만 채우면 멀티턴 기억이 즉시 동작.

> 분리 제안: **7-A(저장)를 먼저** 완성·검증하고, **7-B(주입)는 후속**으로. 7-A만으로도 "기록+검색"이라는 사용자 핵심 요구가 충족되고, 7-B는 현재 동작(client 주입)을 바꾸므로 회귀 위험을 분리한다.

## 9. 인터페이스 초안

```python
# store.py — 교체 seam (SessionStore 패턴 동일)
class MemoryStore(ABC):
    async def append_turn(self, record: dict) -> None: ...
    async def read_turns(self, conversation_id, limit=20, before_turn_index=None) -> list[dict]: ...
    async def upsert_conversation(self, conv: dict) -> None: ...
    async def list_conversations(self, user_id, limit=20, offset=0) -> list[dict]: ...
    async def get_conversation(self, conversation_id) -> dict | None: ...

class FileMemoryStore(MemoryStore):       # system_data/memory/ JSONL (이번 구현)
    def __init__(self, root="system_data/memory"): ...
# 추후: class PostgresMemoryStore(MemoryStore)  ← 새 구현 1개만 추가

# manager.py — 비즈니스 로직 (Store 주입)
class MemoryManager:
    def __init__(self, store: MemoryStore | None = None): ...   # 기본 FileMemoryStore
    async def save_turn(self, ...): ...                         # ★ 핵심
    async def get_recent_turns(self, conversation_id, n=3): ...
    async def get_history_for_cognitive(self, conversation_id, limit=3): ...
    async def list_conversations / get_conversation / update_title / pin / delete_conversation: ...
    async def auto_generate_title(self, user_input) -> str: ...
    async def search_turns(self, ...): ...                      # Sprint16 자리
```

**`save_turn` 내부 책임 (재검증에서 누락 발견 — 명시):**
1. **turn_index 계산**: 해당 conversation의 현재 최대 index + 1 (첫 턴이면 1).
2. **conversation upsert**: 레코드 없으면 생성(create) + `auto_generate_title`(첫 쿼리), 있으면 `turn_count`/`last_active_at` 갱신.
3. **response_summary fallback**: `response.summary` 없으면 `response.text[:200]`로 생성(검색·주입용 비어있지 않게).
4. **동시성**: conversation별 `asyncio.Lock`으로 index 경합 방지(§11 R1).

**`get_history_for_cognitive` 정렬 계약**: [history_injector.py](../../backend/app/dream_agent/cognitive/history_injector.py)는 "index 0=오래된, -1=최근" 순서를 가정하고 tail N개를 취함 → **오래된→최근(ascending)** 으로 반환할 것.

## 10. PostgreSQL / RAG 이관 경로 (추후, 코드 변경 최소)

- `conversations.jsonl` → `conversations` 테이블, `turns/{conv}.jsonl` → `turns` 테이블.
- JSON 필드(structured_query/plan/response/execution_result) → **JSONB 컬럼** 그대로.
- 교체 작업 = **`PostgresMemoryStore` 1개 구현 + 주입 한 줄**. `MemoryManager`·`ws_agent`·테스트는 **불변**.
- ⚠️ 이관 시 `turn_id` **UNIQUE 제약** 필수(중복 레코드 사고 방지 — 업계 사례 교훈).
- **RAG 결정 보류 상태 존중**: `embedding` 필드와 `index/` 폴더 자리만 비워둠. 도입 시 pgvector 컬럼 추가 + `search_turns`에 의미검색 분기. 도입 안 해도 키워드/기간 검색(SQL LIKE)으로 Sprint16 동작 가능 → **RAG는 옵션이지 전제 아님.**

| **D3: `resume_only` 저장 (3차 패스)** | ws_agent L259 `final_state={}` + L344 초기 astream skip | ❌ **결함** → 재시작 전 cognitive 출력 누락 → 저장 소스를 `aget_state.values`로 교정(§7-A, R12) |
| D4: cognitive 계측 가능성 (3차) | cognitive_stage 전체 — L118 raw/prompt, L130 `Command(update={...})` | ✅ return 시점에 prompt/raw 살아있음 → `cognitive_trace` 추가 가능 확정 |
| D5: 중복 저장 (3차) | `_emit_complete` 호출처 전부 직후 `return` | ✅ 턴당 1회만 호출 → 중복 저장 없음(방어로 turn_id 멱등 추가) |
| 재개 run plan 정합 (3차) | planning_stage interrupt 재실행 분석 | ✅ 메모리는 실제 실행 plan 저장 → 자기일관적(R11 명시) |

**3차 패스 핵심(D3):** L3-full을 정확히 저장하려면 소스가 `final_state`(스트림 누적)가 아니라 **`aget_state(config).values`(체크포인트 권위 상태)** 여야 한다. 안 그러면 서버 재시작으로 복원된 턴은 cognitive 변환과정이 통째로 빈 채 박제된다.

**핵심 교정(D1):** L3-full의 과정 기록을 공용 `state["trace"]` 한 칸에 여러 노드가 쌓는 방식은 LangGraph `LastValue` + ws_agent의 per-key `final_state.update` 재구성 때문에 **cognitive 기록이 소실**된다. → `cognitive_trace`/`planning_trace` **단일 기록자 키**로 분리하면 충돌 없이 보존(reducer 불필요). 이 한 줄이 L3-full 성패를 가른다.
