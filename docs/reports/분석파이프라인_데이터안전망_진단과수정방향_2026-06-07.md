## 0. 이 세션을 관통하는 한 가지 주제

서로 달라 보인 5개 질문이 사실 **한 문장**으로 모인다:

> **"데이터가 비거나 틀렸을 때, 시스템이 멈추는가 — 아니면 그럴듯한 틀린 답을 내는가."**

| 세션 질문 | 사실 같은 주제 |
|---|---|
| ① 고객마다 컬럼이 다르면? | 컬럼 안 맞으면 → 조용히 0 → 틀린 답 |
| ② 계산은 코드, 분석은 LLM이 맞나? | LLM은 숫자 **검증 안 함** → 틀린 입력을 그럴듯하게 **증폭** |
| ③ tool 선택 프롬프트 문제 있나? | silent-0: 0건인데 거짓 보고서 |
| ④ 문제 생기면 HITL 부르면 되나? | "멈추고 개입" 직감은 맞으나 장치가 다름 |
| ⑤ 1단계 수정은 어떻게? | 빈 데이터를 **탐지해 멈추는** 게이트 |

**결론 한 줄:** 사장님 아키텍처(코드가 데이터 준비 → LLM이 보고)는 옳다. 단 그 구조는 **"비거나 틀린 데이터에서 멈추는 안전망"에 전적으로 의존**한다. 이 세션은 그 안전망의 현재 상태를 점검한 것이다.

## 1. 두 개의 분리된 문제 (요지 — 상세는 별도 문서)

"고객마다 다 다르다"는 걱정은 **두 문제**다:
- **(A) 저장 장소**: data 폴더 → 외부 DB. → 이미 추상화 준비됨(어댑터 1개+설정 1줄). **[Postgres 설계 문서](../_claude/data/data_db_postgres_설계_2026-06-07.md)로 위임.**
- **(B) 데이터 모양**: client마다 컬럼명 다름. → **번역표**(raw컬럼→표준명)로 흡수. **[컬럼차이 문서](./클라이언트별_데이터차이_현황진단과_해결_2026-06-07.md)로 위임.**

핵심: 둘은 **별개**이고, 코드 위험은 B가 더 크다.

## 2. 코드 vs LLM 역할 경계 (사장님 의도 = 맞음, 단 정확히)

| 단계 | 주체 | 하는 일 |
|---|---|---|
| 수집 | **코드** | raw 가져옴 |
| 정제 | **코드** | 표준화 |
| **분석(계산)** | **코드** (47 계산식) | ROAS·매출·세그먼트 **직접 계산** |
| 보고 | **LLM** | 계산된 숫자를 **자연어로 서술**(번역) |

근거: [responder.py:3](../../backend/app/dream_agent/response/responder.py#L3) "기계 언어 → 사용자 언어 역번역", [response.yaml](../../backend/app/dream_agent/llm_manager/prompts/response.yaml) "convert results into natural language". LLM에 주는 건 **압축 요약**([responder.py:137](../../backend/app/dream_agent/response/responder.py#L137)) — 원본 데이터를 받지도 않음.

**핵심 3가지 (사장님 의도 확인 + 보강):**
1. **계산을 코드로 둔 건 옳다** — 정확·무토큰·재현가능. LLM은 ROAS를 계산하지 않고 이미 계산된 값을 받음.
2. **LLM의 추론적 분석(원인·예측)은 지금 OFF** — diagnose/forecast/attribute는 [responder.py:34](../../backend/app/dream_agent/response/responder.py#L34) `DEGRADE_OPS`로 차단("아직 준비 중"). 과거 "왜 매출 늘었어?"에 리뷰로 거짓 리포트 쓴 사고([planner.py:32-44](../../backend/app/dream_agent/planning/planner.py#L32-L44)) 때문.
3. **LLM은 숫자를 검증 안 하고 믿는다** → 코드가 틀리면 **그럴듯한 오답으로 증폭**. → 코드 단계가 *덜*이 아니라 *더* 중요. LLM은 안전망이 아니라 **증폭기**.

## 4. silent-0 — 무엇이고, 왜 위험하고, **현재 왜 보류인가**

### 증상 (데이터 흐름)

```
[정상]  수집→정제→분석(데이터 OK)→ report_writer → responder → ✅ 진짜 보고서

[silent-0]  수집→정제→분석(0건)→ report_writer → responder → ❌ 가짜 보고서
                          │              │              │
                    sentiment={}   게이트가 여기서   "COMPLETED네,
                    insights=[]    멈춰야 하는데      성공이군" →
                    (빈 신호)      통과 ❌            정직degrade 안 함
```

### 근본 원인 (코드 확정 — [d4 문서](../_claude/4layer_system/d4_silent0_rootcause_260606_v1.md))

`report_writer`는 [report_writer.py:30-32](../../backend/app/dream_agent/tools/report/report_writer.py#L30-L32)에서 `insights` 등을 읽는데 `or {}`/`or []` 폴백이라 **빈 입력에도 LLM을 호출해 보고서를 지어냄**. 안전 게이트([data_gate.py](../../backend/app/dream_agent/execution/data_gate.py))는 tool이 선언한 `consumes`만 검사하는데, report_writer는 카탈로그에 `consumes`를 **선언 안 함** → [executor.py:188](../../backend/app/dream_agent/execution/executor.py#L188)에서 검사 0회 → 무검사 통과.

→ silent-0 = "문 3개 + 급소 1개"로 정리됨([b2 문서 §0](../_claude/4layer_system/b2_silent0_impl_plan_260605_v2.md)): 문1(체인 tool)=✅게이트 닫힘 / 문2(report_writer 등)=❌우회 / 문3(직접fetch tool)=❌게이트 못 닿음 / 급소(responder가 COMPLETED를 성공 오인).

### ★ 현재 결정: **구현 보류 + 알려진 한계로 기록** (2026-06-05)

객관적으로 — 이건 "지금 당장 불나는" 상태가 **아니다**. [b2 계획서](../_claude/4layer_system/b2_silent0_impl_plan_260605_v2.md)의 최종 결정 근거:
1. **현 POC는 기간 필터가 없어** "진짜 0건"이 거의 안 생김(조회 시 전체 반환).
2. **빈 파일은 정직하게 FAILED** 남(silent 아님).
3. 가짜화를 터뜨리려면 **강제 빈 입력**(monkeypatch) 필요.
4. 게다가 `intent_shim` 한계로 **보고서 task가 plan에 잘 안 들어감** → 실발현 빈도 낮음.

→ **유지: B1(미구현 op 정직 degrade) + B2.1(체인 consumes 게이트)** = 실제 발생 케이스는 이미 커버.

### 지난 세션 톤 정정 (정직)

이 대화 중 silent-0을 "실고객 전 1순위"로 표현했는데, 더 정확히는: **"현 POC에선 보류가 타당, 단 아래 재방문 트리거가 오면 고쳐야"**. 두 표현은 모순이 아니다 — 둘 다 "지금 아님, 실데이터/실고객 전"을 뜻한다.

### 재방문 트리거 (이게 오면 §5 착수)

- **기간 필터 도입**(특정 월 조회 → 진짜 0건 발생 가능)
- **실고객의 희소/누락 데이터** 또는 **2번째 고객의 컬럼 누락**(= 세션 1번 문제와 연결)
- 보고서가 plan에 정규 진입하게 되는 변경(intent_shim 확장)

상세 트리거·작업 형태: [b2 계획서 §8](../_claude/4layer_system/b2_silent0_impl_plan_260605_v2.md).

## 5. silent-0 1단계 수정 설계 (착수 시 — 지금 아님)

> ⚠️ 아래는 **재방문 트리거가 왔을 때** 펼칠 설계. 현재는 §4 결정에 따라 **착수 보류**.

**좋은 소식: 멈추는 장치(SKIP)·정직 메시지가 이미 다 있고, report_writer만 연결이 빠졌다.**

### 게이트는 이미 작동한다

[executor.py:188-202](../../backend/app/dream_agent/execution/executor.py#L188-L202)는 모든 tool 실행 직전에 게이트를 통과시킨다:
```
실행 직전 → check_consume_sufficiency(tool의 consumes, 이전 결과):
   ├─ 선언한 consumes가 비었으면 → SKIP + "data_insufficient" 사유
   │         → (실행 안 함) → 기존 정직 메시지(responder.py:83) ✅
   └─ 차있으면 → 정상 실행
```
게이트 설계자 주석([data_gate.py:15](../../backend/app/dream_agent/execution/data_gate.py#L15)): "consumes 미선언 tool은 무검사 → **점진 확대**". 즉 이렇게 하나씩 잇는 게 **원래 의도된 확장**.

### 수정 = 카탈로그에 "진짜 필요한 것" 선언

```
[지금]   report_writer.consumes = []         → 검사 0회 → 통과 ❌
[수정]   report_writer.consumes = [insights] → "insights 비었네" → SKIP ✅ → 정직 메시지
```

### ⚠️ 함정 (무조건 쉬운 길 금지)

카탈로그엔 `params_required: [analysis_results]`라 적혀 있으나 **그걸 생산하는 tool이 0개(orphan)**. naive하게 `consumes=[analysis_results]`로 하면 **항상 막힘**. → 반드시 **코드가 실제 읽는 키**(`insights`)로 선언. "카탈로그가 잘못 적은 키"가 아니라.

### 수정 범위 (계층)

| 계층 | 내용 | 시점 |
|---|---|---|
| 본체 | 게이트·SKIP·메시지 = **이미 존재**, 연결만 | — |
| 1단계 | `report_writer.consumes=[insights]` 선언(올바른 키) + "0건이면 SKIP" 테스트 | 착수 시 |
| 급소 보강 | responder가 "빈 입력 COMPLETED"를 성공 오인 안 하게(같이) | 착수 시 |
| 구조 개선 | `ToolSpec`에 `consumes` 칸 추가 → 모든 tool 자동 확대 | 중기 |
| produces drift | report_writer `produces=[report_markdown]` vs 실반환 `report_text` 정리(team_catalog 1곳) | 중기 |

## 6. "없다"의 UX 3갈래 (다음 이야기 — 1단계 후)

멈춘 뒤 무슨 말을 할까. **"없습니다"(막다른 길)보다 "없어요 + 다음 행동"이 맞다.** 더 정확히는:

```
 ① 0건이 정답         → "4월 환불은 0건입니다" (정상 답변! 에러 아님)
 ② 데이터 부재/미연동  → "그 데이터는 아직 없어요. 기간/대상 바꿔 재시도"  ← 기존 메시지가 여기
 ③ 질문이 모호        → 되묻기 (여기가 HITL 자리)
```

통찰: "0건"이 항상 에러는 아니다(때론 정답). silent-0의 죄는 *0이 도달한 것*이 아니라 *내용을 지어낸 것*. → 이 3갈래를 구분하려면 §5의 **탐지(로직)**가 선행돼야 함(UX와 로직이 맞물림).

## 7. HITL 판단 (객관)

HITL은 종류가 4개뿐([enums.py:23](../../backend/app/dream_agent/models/enums.py#L23)): `PLAN_REVIEW`·`CLARIFICATION`·`APPROVAL`·`INPUT`. → **"사람이 *결정*할 때" 부르는 장치**(계획 승인·모호한 질문 되묻기), 데이터 검증 장치 아님.

| 무엇이 잘못됐나 | 올바른 응답 | 누가 |
|---|---|---|
| ① 진짜 데이터 없음 | 자동 정직 degrade | (사람 불필요) ← silent-0은 여기 |
| ② 설정/스키마 깨짐 | fail-fast + 빌더 알림 | 빌더 ← 마케터는 못 고침 |
| ③ 모호/진짜 결정 | HITL 호출 | 사용자 ← HITL의 진짜 자리 |

→ "데이터 문제 = HITL"은 직감(멈추고 개입)은 맞으나 위치가 어긋남. silent-0은 ①(자동 degrade)이지 ③(HITL)이 아님.
