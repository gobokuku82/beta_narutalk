# 계획 박제 — 로그인 별 vs 회사별 인스턴스 차등 모델 4 perspective 의견 분석 (2026-06-02)

> 사용자 본질 질문: 로그인 계정별 agent/tool/dashboard/data layer 차등 → 회사별 맞춤화 본질 = white-label / multi-instance vs multi-tenant 결정.
> 본 박제 = 결정 보류 자취 + 미래 진입 참조.

---

## §0 사용자 본질 질문 자취

> "이제 로그인 기능을 만들어서 로그인 계정마다 에이전트 / tool / 대시보드 / 데이터 layer 를 다르게 조정하고 싶은데 어떻게 하면 좋을지 다양한 의견줘"

→ 후속 명확화:
> "내 꺼를 베이스로 특정 회사에 맞춤화를 할꺼야. 근데 회사마다 데이터 구조가 달라서, 사실 tool은 많이 안 바뀌는 data layer 가 많이 바뀔꺼야. 그래서 로그인 별로 할까? 아니면 그냥 아예 새롭게 만들어서 도커로 빌드하는게 맞는가?"

→ 본질 = **B2B 컨설팅 SaaS / White-label** (per-customer customization) 본질 박제.

## §1 4 perspective workflow 의견 자취 (multi-tenant 가정)

워크플로우 = `multi-tenant-design-opinions` (4 agent parallel fan-out).

### 1.1 Conservative Pragmatist
- **스택**: FastAPI-Users (자체) + 1 테이블 (`allowed_clients/pages/tools/agents` 배열) + JWT
- **권한 모델**: 단순 ACL
- **POC 비용**: 3 commit / 1주
- **핵심 단언**: POC 에서 SaaS·Auth-First·Phased 모두 over-kill. 단일 매핑 + JWT 1개로 80% 달성

### 1.2 Standard SaaS Architect
- **스택**: Clerk B2B Organizations + React drop-in + FastAPI middleware
- **권한 모델**: RBAC base + JSONB ABAC override
- **POC 비용**: 2-3일
- **핵심 단언**: POC 즉시 도입. 인증 도입 시점 = `client_id` hardcode 회귀 비용과 동일, 늦출수록 비싸짐

### 1.3 Phased Migration Specialist
- **스택 Stage A**: `config/accounts.yaml` 정적 매핑 + `X-Account-Id` 헤더 미들웨어 (인증 미루기)
- **우선순위**: Data > Dashboard >> Tool > Agent
- **POC 비용**: 30분
- **핵심 단언**: 사용자 1명이면 인증 만들지 마라. yaml `schema_version` 박제 → DB 마이그레이션 무비용 진입

### 1.4 Auth-First Security Specialist
- **스택**: Supabase Auth + ReBAC (4 join table) + RLS + audit log
- **권한 모델**: ReBAC (user_dashboard_access / user_client_access / user_tool_access / user_agent_access)
- **POC 비용**: 중간 (PostgreSQL → Supabase 전환)
- **핵심 단언**: 잘못 세우면 다른 회사 데이터 누출 = 서비스 종료. auth 먼저, 시각화 나중

## §2 본질 재해석 — Multi-Tenant vs Multi-Instance

사용자 후속 명확화 (data layer 변동 多) = 4 perspective 의 전제 (multi-tenant SaaS) 가 **잘못된 전제** 박제.

### 2.1 패턴 비교

| 항목 | X. Multi-Tenant | Y. Multi-Instance Docker |
|---|---|---|
| 배포 | 한 시스템 = 모든 회사 공유 | 회사별 별도 Docker container |
| URL | 단일 (예: `octorad.io`) | 회사별 (예: `customer-a.octorad.io`) |
| DB | 공유 + tenant_id 격리 | 회사별 별도 |
| schema 차이 처리 | 어려움 (단일 schema 가정) | **자연** (회사별 별도 schema) |
| 인증 | 복잡 (multi-tenant RBAC) | 단순 (인스턴스 = 회사) |
| 운영 부담 | 한 시스템 운영 | 인스턴스 多 운영 (CI/CD) |
| **사용자 의도 정합** | ❌ (schema 다름) | ✓ |

### 2.2 패턴 Y 안에서 2 옵션

#### Y-1 순수 Multi-Instance (회사별 fork)
- 회사 = git branch / 별도 repo
- 자유도 100%, base 동기 어려움

#### Y-2 Hybrid Base + Plugin ★ 권장
- **Base** (공통): frontend 5 v2 page + 85 tool + 21 agent + pipeline DSL
- **Plugin** (회사별): `customization/{client}/` 폴더
  - `normalizers/{client}.yaml` (이미 ADR-027 박제)
  - `dashboards/{client}.yaml`
  - `data_sources/{client}.py`
- 인스턴스 = base + 한 회사 plugin Docker build

## §3 객관 권장 (workflow 결과 + 본질 재해석 종합)

### 3.1 패턴 결정
**Y-2 (Hybrid Multi-Instance)** ★

### 3.2 이유

| 사용자 자취 | 정합 |
|---|---|
| 회사별 data layer 변동 大 | Plugin 폴더 자연 흡수 |
| Tool 변동 적음 | Base 공유 = 갱신 한 곳 |
| 비전공자 운영 | 한 회사 = 한 Docker = 단순 |
| 이미 ADR-022/027 박제 | `normalizers/{client}.yaml` 자취 정합 |
| memory `project_data_folder_structure` | `data/{client}/` 자취 정합 |
| memory `project_extension_ease_priority` | Plugin layer = 확장 용이 |

### 3.3 인증이 단순화되는 이유
- 한 인스턴스 = 한 회사 = 회사 직원만 사용
- 4 layer 차등 자연 해소:
  - Data: 인스턴스 = 회사 = 자동 격리
  - Dashboard: customization/{client}/dashboards.yaml
  - Tool: customization/{client}/tools.yaml (선택)
  - Agent: customization/{client}/agents.yaml (선택)

## §5 미래 진입 옵션 (사용자 의향 정합)

사용자 명시 의향 = "현 버전 백업 + 맞춤형 새로 만들기" = **Y-1 단순 fork** 패턴.

### Option A: git tag/branch 백업 + 새 fork
1. `git tag v0.1-clumi-poc` (현 상태 박제)
2. 새 branch `customer-XXX` 시작
3. 회사별 customization 진행

비용 = 작음 (몇 분). 단점 = base 갱신 동기화 어려움.

### Option B: customization/ 폴더 박제 + 단일 repo
1. 현 코드 그대로 + `customization/clumi/` 폴더 생성 (기존 clumi 박제 이동)
2. 새 회사 진입 = `customization/{새client}/` 폴더만 추가
3. Docker build = `--build-arg CLIENT=clumi` 같은 식
4. 한 codebase 운영 (base 갱신 자동 전파)

비용 = 중간 (Plugin layer 박제 작업 1~2주). 단점 = 초기 구조 박제 부담.

### Option C: docs/_claude/architecture/ 결정 보류 + 미래 진입
- 본 보고서만 박제
- 첫 외부 회사 진입 시점 결정

비용 = 0. 사용자 명시 현재 의향과 정합.
