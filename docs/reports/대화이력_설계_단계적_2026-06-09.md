## 2. 쉬운 그림 — 무엇을 저장하고 무엇을 보여주나

화면은 **두 개**, 저장은 **"다시 보여줄 만큼"**:

```
[대화이력 페이지]                      [채팅창 (클릭 시 복원)]
┌──────────────────────┐            🙋 네이버 ROAS 왜 떨어졌어?
│ 📋 네이버 ROAS 개선    │            🤖 4월 380%… + [차트]
│    2턴·완료·06-10  🗑 │   클릭 →    🙋 PPT로 만들어줘
│ 📋 5월 성과 리포트     │            🤖 [슬라이드][2][3] + 📎다운로드
│ [+ 새 대화]           │            ───────────────
└──────────────────────┘            (P1.5에서 "이어서 대화")
```

- **표시(채팅창)** = 메시지 = 사용자 말 + AI 답(텍스트/슬라이드/다운로드). 워크플로우·결과는 **온디맨드**('보여줘'). 실행 중 표시(진행 todo·PhaseIndicator·PauseBox)는 제외.
- **저장 = 전부 이미 checkpoint에.** 한 턴 checkpoint에 대화기록 + 작업결과(execution_result) + 워크플로우(plan) + 해석이 다 들어있음(→ §5). **"checkpoint를 가져온다" = "이 전부를 가져온다"** (적게가 아님).
- **목적 = 감상이 아니라 작업 이어가기.** 클릭 복원 = 채팅 재현 + **다음 턴이 과거 맥락을 갖고 이어감**(§8 P1.5). 워크플로우/자료 재사용은 온디맨드/회상(§8 P3).

## 3. conversation vs memory — 절대 안 섞기 (핵심)

사용자 우려("내가 중간에 바꾸면서 섞였다")의 해소. **개념·저장소·매니저를 갈라놓는다.**

| | **대화 (conversation)** | **메모리 (memory/학습)** |
|---|---|---|
| 무엇 | 채팅 turn·워크플로우·자료출처 | 선호·패턴·워크플로우 템플릿 |
| 화면 | **대화이력 페이지** + 채팅창 | **메모리 페이지** |
| 저장소 | **checkpoint** (+ `conversations` 테이블) | **`memory_entries`** |
| 매니저 | **`ConversationManager`** | `MemoryManager` |

- **구분 기준 = 저장소·매니저로.** 한 테이블에 `type`으로 혼용(옛 spec 35 §4)하던 게 섞임의 원인 → **안 씀.**
- `memory_entries` 이름은 **메모리 전용**으로 두면 정확. 대화는 거기 **안 들어감.**
- 둘은 코드에서 절대 안 거침: 대화이력 페이지 → ConversationManager만 / 메모리 페이지 → MemoryManager만.

## 4. 지금 구현 현황 (검증된 표)

| 데이터 | 경로 | 저장 위치 | 됐나? |
|---|---|---|---|
| turn 본문 + `plan`(워크플로우) + `execution_result`(자료출처) + `response` | 대화 | **checkpoint** (thread_id=conv_turn) | ✅ **동작 — 유일하게 턴마다 실제 저장** |
| layer guard 로그 | (관찰) | layer_guard.jsonl | ✅ (대화/메모리 무관) |
| 대화 목록 메타 | 대화 | `conversations` 테이블 | ❌ 미생성 (P1은 checkpoint 스캔) |
| 조회 매니저 | 로드 | `ConversationManager` | ❌ 신규 (현 `MemoryManager`=0 byte) |
| 학습 trace | 메모리 | learning_manager `@trace_log` | ⚠️ 정의만, **적용 0 (안 돎)** |
| 선호/패턴/템플릿 | 메모리 | `memory_entries` | ❌ 미생성 (메모리 페이지=SAMPLE) |

→ **턴마다 실제 저장되는 건 checkpoint 하나.** 그런데 거기에 대화 본문·워크플로우·자료출처가 다 있음.
→ **"로드 기능만 없다"(대화 한정) = 맞음.** 프론트 화면 = `ConversationsPage`.

## 5. 무엇이 어디에 저장되나 (전부 코드로 verified)

**checkpoint(`octormate_system`) — 한 턴 = GraphState 통째 직렬화:**

| 필드 | 무엇 | 회상에 쓰임 |
|---|---|---|
| `structured_query` | AI가 처음 해석한 의도 | "어떻게 이해했어?" |
| **`plan`** (todos+dag+rationale) | **워크플로우 그 자체** (프론트 WorkflowCanvas와 동일 데이터, ADR-010) | **"아까 워크플로우 보여줘"** |
| **`execution_result`** (todo별 tool·입력·출력) | **자료 출처/계산 과정** | **"그 자료 어떻게 나왔어?"** |
| `response` (format·text·**attachments**) | 최종 답(텍스트/슬라이드/다운로드) | 채팅 재현 |
| `client_id` | 클라이언트 | 목록 필터 |

**식별 체계(검증):**
- `thread_id = "{conversation_id}_{turn_id}"` — LangGraph 체크포인터의 **유일한 키, 키 이름 하드코딩(못 바꿈)**. 값도 기존 데이터에 고정.
- **대화 그룹핑 = `conversation_id`** (thread_id를 `parse_thread_id`로 분해해 얻음).
- ⚠️ `session_id`는 코드상 **`turn_id`의 deprecated 별칭** — **thread_id가 아님**. 식별자로 쓰지 않음(혼동 방지).
- DB 주의: `CHECKPOINT_DB_URI` config 기본값은 `dream_agent`지만 **.env는 `octormate_system`** — 실제는 octormate_system.

## 6. 설계 핵심 — API 계약을 seam(관절)으로

```
프론트 useConversations 훅 (한 번만 배선)
   └ GET /api/conversations?client=     ← 응답 스키마 고정
        ├ Phase 1: checkpoints 유도 (지금 실데이터, 새 테이블 0)
        └ Phase 2: conversations 테이블 (정식, persist hook)
```
같은 응답 스키마를 두 구현이 공유 → **Phase 1에 배선해두면 Phase 2 전환 시 프론트 무수정.**

**응답 스키마(고정):**
```jsonc
// GET /api/conversations?client=clumi&limit=20
{ "items":[{ "conversation_id","title","preview","turn_count",
             "status":"active|completed|error", "updated_at","client_id" }],
  "total","has_more" }
// GET /api/conversations/{conversation_id}/turns
{ "items":[{ "turn_id","messages":[{role,content,format,attachments,ts}],
             "status","created_at" }] }
```

## 7. ConversationManager (전용 — 검증으로 정정된 결정)

> 사용자가 명시한 "ConversationManager가 내부 DB 읽고 답함" = **전용 클래스로.** (이전에 MemoryManager로 통합했던 것 → 분리 의도와 어긋나 정정)

- **책임**: checkpoint(+ Phase 2의 `conversations`)를 읽어 과거 turn(목록·메시지·plan·execution_result)을 반환. **회상(P3)도 이 매니저를 경유.**
- **메서드(초안)**: `list_conversations(client, limit, offset)` / `get_turns(conversation_id)` / `get_turn(turn_id)` / (P3) `recall(conversation_id, hint)`.
- **위치**: `backend/app/dream_agent/workflow_managers/conversation_manager/` (MemoryManager와 형제, 분리).
- MemoryManager(메모리/학습)와 **읽는 저장소가 다름** → 경로 안 섞임.

## 8. 단계 계획

```
P1  기본 대화이력 + 복원 표시 (read-only)    ← 먼저
    ConversationManager.checkpoint 스캔 → GET /api/conversations(+/{id}/turns)
    → useConversations 훅 → ConversationsPage(features/conversations) SAMPLE_CONVERSATIONS 교체
       (카드 필드 title/preview/turnCount/updatedAt/status 1:1 매핑 — 거의 배열만 교체)
       + 카드 onClick(클릭→복원) 추가 + status에 error/cancelled 처리(현 active|completed만)
    → 클릭 시 useAgent.messages 로드 → 채팅 메시지 재현(텍스트·슬라이드·다운로드)
    (워크플로우·결과 시각 표시는 P3 회상에서)
    제목 = AI 요약(첫 턴 후 1회 LLM 생성·저장) / P1 임시 fallback = 첫 질문 truncate
    검증: 실 체크포인트로 목록·복원 뜨는지

P1.5  이어서 작업 (★핵심 — "감상 아닌 이어가기")   ← 그 다음
    ① conversation_id 전환·새대화 (session/store, 현재 localStorage 1개 고정)
    ② 과거 맥락을 에이전트에 공급 = conversation_history 주입
       (현재 슬롯만·공급자 없음 → ConversationManager가 채움)
       → 다음 턴이 과거 대화·결과를 알고 이어감 = 진짜 "이어서 작업"

P2  conversations 테이블 정식
    DDL(대화 전용, octormate_system, messages=JSONB) + persist hook(턴 완료 시)
    + 엔드포인트 데이터소스 checkpoint→conversations 교체(스키마 동일 → 프론트 무수정)

P3  회상 = 과거 산출물 재사용 (온디맨드)      ← 기본 이력 후
    "아까 그 워크플로우 수정"·"그 자료 다시" → recall tool + 회상 의도 인식(cognitive)
    + ConversationManager가 checkpoint에서 plan/execution_result 꺼냄 → Canvas 재편집·데이터 재사용
    저장 이미 됨 — retrieval만
```

## 9. 빠진 것 · 결정해야 할 것 (검증 gap 반영)

**🔴 높음 (P1~P2에서 처리):**
- **턴 상태**: 지금 '완료'만 가정 → `status ∈ {completed, error, cancelled, in_progress}` 정의. 에러/취소 턴도 이력에 표시(회색/재시도). checkpoint에서 상태 추출 방법 명시.
- **진행중 턴**: 목록에 active 표시(상단 고정·로딩). summary/last_at 갱신 시점.
- **진실원본**: turn 본문이 checkpoint(P1)와 conversations(P2) 둘 다 → **checkpoint=진실원본(LangGraph 복원용), conversations=빠른 조회 사본.** persist_turn은 non-blocking이라 누락 가능 → conversations 없으면 checkpoint fallback.
- **이어서 대화 전환**: conversation_id 교체 흐름 구체화(P1.5, §8).

**🟡 중간 (정책 결정):**
- 삭제 cascade: turn·meta·checkpoint·첨부파일(outputs/) 어디까지? soft delete?
- 첨부 파일 수명: `outputs/` 정리 정책(대화 삭제 시/만료/용량). 복원 시 404 대체.
- 멀티탭: 같은 localStorage conversation_id 충돌 → POC는 "단일탭 가정" 명시 권장.
- 회상 "아까" 해소: top-k turn 요약 LLM 선택 + 저신뢰 시 되묻기(P3).
- checkpoint 보존/비용: 무한 누적 vs 정리, P1 목록 조회 N+1(aget_state) 임계값.

**🟢 낮음:** 빈 이력 UX, client 변동 시나리오, 제목 truncate 기준(글자 vs byte). (제목 생성 = **AI 요약** 결정 → §8 P1. 사용자 편집은 추후 옵션)

## 10. 구현 전 확인 (검증으로 해소) + 위험 가정

**해소됨(✅):** checkpoint DB=`octormate_system` / state에 `client_id`·`response(attachments)` 있음 → **Phase 1 전체재현·유도 가능 확정** / 12개 사실 주장 verified.
