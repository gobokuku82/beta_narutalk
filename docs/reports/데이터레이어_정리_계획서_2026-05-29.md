# 데이터 레이어 정리 계획서 (2026-05-29)

> 목적: "client(예: clumi)를 선택하면 그 client의 데이터/캐시/분석결과로 전부 바뀐다"가
> 동작하도록, **레이어 책임(누가 무엇을 아는가)** 을 의도에 맞게 정리한다.
> 방식 = **golden 테스트로 보호되는 점진적 리팩터링** (한 단계 = 하나의 변경 → 검증 → 커밋).

## 0. 한 줄 결론

현재 코드에서 **읽기(data_sources)는 client별로 잘 동작하는데, 쓰기/캐시(workspace)가 `clumi/` 로 고정**되어 있다. 그래서 어떤 client를 골라도 같은 폴더를 읽어 화면이 안 바뀐다(E11). 이건 **ADR-022가 "MVP에서 분리"라고 적어두고 미뤄둔 항목**이다. 지금 그 미뤄둔 정리를 한다.

## 2. 당신의 멘탈모델 vs 이 시스템 (초보자용 대조)

당신이 적은 구조는 **표준 FastAPI "DB CRUD 웹앱"** 의 정석이다. 틀린 게 아니라, **이 시스템이 그 종류가 아니라서** 일부가 다르다. 이 시스템은 *"raw 데이터 → 분석으로 변환하는 파이프라인"* 이다 (DB에 행을 넣고 빼는 앱이 아님).

| 당신 모델 (표준 CRUD 웹앱) | 이 시스템의 실제 위치 | 일치? | 왜 다른가 |
|---|---|:--:|---|
| `schemas/` 들어오고 나가는 데이터 모양 (Pydantic) | `backend/app/schemas/` (`inputs/` raw 컬럼표준 · `outputs/` tool 산출형식) | ✅ 거의 동일 | 그대로 맞음 |
| `models/` DB 테이블 (SQLAlchemy) | **없음** | ❌ | **DB가 없다.** 데이터 = CSV/JSON 파일. 그래서 ORM 테이블 정의가 불필요 (`__tablename__` 0개 확인됨) |
| `crud/` DB 직접 만지는 함수 (가져오기/저장/삭제) | `data_sources/` (읽기) + `workspace/` (쓰기) | △ 둘로 쪼개짐 | "관절"=**Repository 패턴**. 파일이 DB 역할. **읽기/쓰기를 두 폴더로 나눈 게 ADR-022 결정** — 그런데 당신의 "한 곳에 모은다" 직관이 사실 더 단순하고, **쓰기 쪽이 client를 잊은 게 E11의 원인** |
| `services/` 계산·판단 로직 | `backend/app/dream_agent/tools/` (정제·지표·분석·추론) | △ 더 잘게 쪼갬 | 큰 service 하나가 아니라 **작은 tool 여러 개를 조합**. 조합 실행은 별도 층(아래)이 함 |
| `routers/` API 입구 | `backend/api_v2/routes/` (`dashboard1.py`·`pipelines.py`·`admin.py`) | ✅ 동일 | 그대로 맞음 |
| *(당신 모델엔 없음)* | `backend/app/pipelines/` (pipeline maker) + `dream_agent/` (agent) = **오케스트레이션** | ➕ 추가 층 | CRUD앱엔 없는 층. "어느 tool을 어떤 순서로" 결정·실행. 대시보드는 pipeline maker가, 채팅은 agent가 진입점 |

**요약:** 당신 모델에서 →
- `models/` 는 **빼면 됨** (DB 없음).
- `crud/` 는 **`data_sources`(읽기) + `workspace`(쓰기)** 로 존재 (= "관절"). **이 둘이 곧 "데이터 레이어"** 다.
- `services/` 는 **작은 tool들 + 그 위 orchestration** 으로 나뉨.
- `schemas/`, `routers/` 는 거의 그대로.

→ 즉 당신의 직관은 대부분 맞고, **딱 하나 — "저장/로드를 한 데이터 레이어가 client별로 책임진다"** 는 부분이 현재 코드에서 절반만(읽기만) 지켜지고 있다. 그걸 맞추는 게 이 계획.

### 2.1 목표를 "당신 용어"로 (한눈 정리)

당신 모델을 이 시스템에 맞춰 **그대로 채택**하면 목표 폴더는 이렇게 된다:

| 당신 용어 | 이 시스템에서의 이름 | 목표 상태 |
|---|---|---|
| `schemas/` | `app/schemas/{inputs,outputs}` | 유지 (이미 맞음) |
| ~~`models/`~~ | — | **삭제 개념** (DB 없음 → ORM 테이블 불필요) |
| `crud/` (저장/로드 한 곳) | **데이터 레이어** = `data_sources/`(읽기) + `workspace/`(쓰기) | **둘 다 client별** `data/{client}/{stage}/…` 로 통일 ← 이 계획의 핵심 |
| `services/` | `dream_agent/tools/` | tool은 **순수 처리만** (저장/경로 모름) |
| `routers/` | `api_v2/routes/` | 유지 (이미 맞음) |
| (추가 층) | `pipelines/`(maker) + `dream_agent/`(agent) | tool 조합·실행 (파일명 모름) |

### 2.2 결정 포인트 — `crud` 를 "한 곳"으로 합칠까? (당신이 정해주세요)

당신 모델은 저장/로드가 **`crud/` 한 곳**이다. 현재 코드는 **읽기(`data_sources`)/쓰기(`workspace`) 두 폴더**로 나뉘어 있고, 이건 ADR-022의 의도적 결정(입력 Port / 출력 Port, Hexagonal)이다.

| 선택 | 내용 | 장 | 단 |
|---|---|---|---|
| **(가) 분리 유지** (계획 기본값·추천) | 두 폴더 그대로, **둘 다 client-aware로만** 맞춤 | ADR-022 정합, 변경 최소, 입력/출력 역할 명확 | 당신 모델의 "한 곳"과 폴더 수가 다름(개념은 하나의 데이터 레이어) |
| **(나) 한 곳으로 합치기** | `data_sources` + `workspace` → 단일 데이터 레이어 폴더 | 당신 모델과 1:1, 초보자 추적 쉬움 | ADR-022 결정 변경(ADR 갱신 필요), 이름/이동 작업 추가 |

→ 본 계획서 §5·§6는 **(가) 분리 유지**를 기본으로 작성했다. 어느 쪽이든 **"출력측도 client-aware"** 라는 핵심 작업은 동일하다.

> **결정 확정 (2026-05-29): (가-개선) 분리 유지 + raw 정리.** ADR-022 분리 유지 + 출력측 client-aware. 꼬임의 원인은 "두 클래스"가 아니라 **raw를 양쪽이 언급**하는 것 하나 → **workspace에서 raw 제거**(workspace = cleaned/computed 전용), raw 소유 = data_sources(읽기) + 수집(쓰기).

### 2.3 데이터 위치 모델 (사용자 확정 2026-05-29) ⭐

```
[외부 데이터 — 남의 것 / API]
  (미래) 실제 광고·분석 API   ──API 미연결──▶  data/mock_api/{client}/   ← 현재 외부 raw 소스(mock)
         │  [수집 = collection/external 커넥터]   ※ API 연결 전까진 mock_api 에서 읽음
         ▼
[내부 데이터 — 내 서버 / 미래 Postgres·정형DB]   data/{client}/
   ├─ raw/        = 외부 API raw 를 내 서버로 "옮긴" 것 (내부 raw)   ← 수집이 씀 / data_sources 가 읽음
   ├─ cleaned/    = tool 정제 산출                                  ← workspace 가 읽고/씀
   └─ computed/   = tool 지표·분석 산출                              ← workspace 가 읽고/씀
```

**핵심 함의:**
1. **`data/{client}/` 전체 = "내 서버" 하나의 저장소** (미래 **Postgres/정형DB**). raw·cleaned·computed 모두 내부. → `client` = 미래 DB의 **tenant/schema 키**.
2. **외부(`data/mock_api/{client}`)** 는 API 연결 전 임시 소스. **수집 커넥터(collection/external)만** 접근 (현재 비활성 → POC는 raw 미리 배치).
3. `data/{client}/raw` 는 외부 raw의 **내부 복사본**. "수집이 쓰고, data_sources가 읽는다" = 정상(미래 DB에선 INSERT/SELECT).

→ **단계 2-최소(`data/{client}/{layer}`)가 이 모델과 정합:** file→Postgres 전환 시 `{client}` 가 그대로 schema/tenant 키가 됨. (raw 제거는 별도 작은 단계로 — 단계 2 이후.)

## 3. 현재 데이터 레이어 실제 구조 (코드 기준)

```
backend/app/
├── data_sources/          ← 데이터 레이어 (읽기 절반) — Repository "관절"
│   ├── base.py            DataSource ABC: get(client, source_id) / has / list_sources
│   ├── file.py            FileDataSource: data/{client}/raw/{파일}   ← client별 ✓
│   │                      SOURCE_REGISTRY 28개 (external 16 / internal 12)
│   └── __init__.py        get_default_data_source() 싱글톤
│
├── workspace/             ← 데이터 레이어 (쓰기 절반) — tool 산출물 저장/캐시
│   ├── base.py            WorkspaceBackend ABC: save / load / exists / list_keys
│   ├── file.py            FileWorkspace: data/clumi/{layer}/{key}    ← clumi 고정 ✗ (E9/E11)
│   └── __init__.py        get_default_workspace() 싱글톤 (client 모름)
│
├── schemas/               ← 데이터 모양 (Pydantic)
│   ├── inputs/            raw 컬럼 표준 (campaigns·daily_performance·reviews·creatives·…)
│   └── outputs/           tool 산출 형식 (RevenueOutput·ChannelMetricsOutput·… 36개)
│
├── dream_agent/tools/     ← 처리 로직 (services 역할). self.ds.get(client,…)로 데이터 부탁
└── pipelines/ + api_v2/   ← 오케스트레이션 + API 입구
```

**client가 흐르는 길 (추적 결과):**

```
[읽기 — 정상 ✅]
 프론트 selectedClientId → API ?client=clumi → pipelines.py pool={client,period}
  → runner.run(variables) → ${client} 치환 → tool.execute(client) → self.ds.get(client,"orders")
  → data_sources/file.py: data/{client}/raw/orders.csv      (경로 아는 유일한 곳)

[쓰기 — 끊김 ❌]
 tool: get_default_workspace().save("computed","S001_….json",…)
  → workspace/file.py LAYER_DIR["computed"]="clumi/computed"   ← client 무시
 runner: workspace.exists("computed", key_template="channel_metrics.json")  ← client 없음
```

→ **읽기는 client별, 쓰기는 clumi 고정.** 그래서 blooming을 골라도 `data/clumi/computed/`의 캐시를 읽어 화면이 안 바뀐다.

## 5. 목표 구조 (after)

- **데이터 레이어 = 읽기(`data_sources`) + 쓰기(`workspace`) 두 반쪽, 둘 다 client-aware.**
  - 모든 경로는 `data/{client}/{stage}/…` (raw·cleaned·computed 전부 client 하위).
  - 경로/파일명을 아는 곳은 이 레이어뿐.
- **tool = 순수 처리.** 데이터는 `self.ds.get(client,…)`로 부탁, 결과만 반환. **직접 저장 안 함.**
- **pipeline maker = 파일명 모름.** tool 조합·순서만 안다. 캐시키는 데이터 레이어가 client 포함해 만든다.
- **프론트 = client 이름만.** 경로/파일명 0.

> ※ 위는 **§2.2 (가) 분리 유지** 기준이다. ADR-022의 입력/출력 두 폴더 분리는 그대로 두고, **출력측(`workspace`)도 입력측처럼 client-aware로만 맞춘다** (= ADR-022 §미해결 완료). §2.2 **(나) 한 곳으로 합치기**를 택하면 본 절·§6를 통합 기준으로 고쳐쓴다.

## 6. 단계별 계획 (점진적 리팩터링 — 매 단계 golden green)

> 권장 실행 순서 = **1 → 2 → 3 → 4 → 5.** 이유는 §6.0 참고.
> 각 단계: 변경 → `golden 검증` → 커밋 → 멈춤(다음 단계 사용자 확인).

### 6.0 ⚠️ 실측 발견 → 순서 정정 (2026-05-29, 코드 진입 전 검증)

> "단계 1 먼저"를 준비하다가 **코드/테스트를 실측**한 결과, 순서를 **단계 2(최소) 먼저**로 정정한다.

**발견:**
1. **golden 베이스라인 = 299 passed / 15 failed** (15 전부 pyarrow 미설치 = 환경, 무시). ※ 일부 tool은 **저장 단계의 parquet ImportError로 통째 죽음** → "tool이 I/O하면 안 된다"의 방증.
2. **여러 테스트가 "tool이 직접 저장한 파일"을 단언**한다 (`test_active_orders_filter` parquet/schema, `test_member_metrics_validator`, `test_ad_cost_aggregator`, `test_storage_backend`). + tool 저장에는 **ERD용 풍부한 meta(columns·formula)** 가 실림. → **단계 1(tool 저장 제거)은 테스트 재작성 + meta 이관까지 필요한 *큰·섬세한* 작업.**
3. 반대로 **workspace 테스트는 `ws.save("cleaned",…)` 를 client 없이 호출하며 `"clumi/cleaned" in loc` 를 단언**한다 ([test_file.py:32](../../backend/tests/workspace/test_file.py#L32)). → **`client="clumi"` 기본값**으로 추가하면 이 테스트들이 **수정 없이 그대로 통과**한다.

**정정된 결론 — 단계 2를 "최소" 형태로 먼저:**
- `WorkspaceBackend.save/load/exists` 에 **`client: str = "clumi"` 기본 kwarg** 추가, 경로 `data/{client}/{layer}`.
- **client는 진입점(runner·dashboard1)만 전달.** tool 30개는 **무변경**(기본값 clumi로 기존과 동일 동작).
- 결과: **~4 파일**, tool·테스트 무변경, **golden 299 유지**, **E11 해소**(clumi=정상 / blooming 등=빈폴더 miss→재계산→raw 없어 에러=의도).
- 이게 §6의 "단계 2"를 POC 범위로 **최소 구현**한 것. "30 tool 저장에까지 client 완전 주입(2-complete)"·"단계 1 tool 순수화"는 **진짜 2번째 client 데이터가 생길 때** 더 큰 작업으로 진행.

**남은 wart(허용):** `client` 기본값 clumi가 *또 하나의 분산 기본값* → **단계 5에서 정리**. 만약 비-clumi client가 *성공적으로* 계산되면 tool 저장이 clumi 폴더로 감(POC에선 발생 안 함 — 데이터 부족으로 에러) → 2-complete/단계 1에서 해소.

→ **실행 순서: 단계 2(최소) → [E11 해소] → 단계 3 → 5 → (필요 시) 1·2-complete·4.**

### 단계 1 — 저장 책임 일원화 (tool 순수화) · 위반 #2

- **무엇**: tool 안의 `get_default_workspace().save(…)` 제거. tool은 결과(+ 저장 키 힌트)만 반환. 저장은 **진입점**이 단일 수행:
  - pipeline 경로 = `runner.py` (이미 fallback save 보유 → 정식 save로 승격).
  - dashboard1 경로 = `_cached_or_run` 에 save 추가 (현재 tool self-save에 의존 중).
- **대상**: ~30 tool (metrics·comparison·preprocessing·normalization·cleaning) + `runner.py` + `dashboard1.py`.
- **검증**: golden 17 정답값·291 테스트 동일 (동작 보존). 캐시 파일 위치·내용 동일해야 함.
- **리스크**: 저장 누락 시 캐시 미스(재계산)만 발생 — 값은 안전. 카테고리별 분할로 회귀 추적.

### 단계 2 — 데이터 레이어 client-aware (E11 해소) · 위반 #1

- **무엇**: 출력측 경로를 `data/{client}/{layer}` 로. `WorkspaceBackend.save/load/exists` 가 client를 받음(읽기 `ds.get(client,…)` 와 동일 컨벤션). 진입점(단계 1에서 1곳이 됨)이 `variables["client"]` / `?client=` 를 그 한 곳에 전달.
- **대상**: `workspace/base.py`(ABC), `workspace/file.py`(LAYER_DIR 동적), `workspace/__init__.py`, `runner.py`, `dashboard1.py`, `tests/workspace/test_file.py`.
- **검증**: clumi 정답값 보존 + blooming 선택 시 `data/blooming/…` 조회 → 데이터 부족이면 `DataSourceNotFound`(=의도된 "작동 안 함"). 프론트에서 client 전환 시 대시보드 실제로 바뀜.
- **리스크**: 기존 `data/clumi/{computed,cleaned}` 캐시는 경로 동일(clumi)이라 그대로 hit. 첫 비-clumi 선택만 miss→재계산.

### 단계 3 — 캐시키에서 파일명 제거 / client 포함 · 위반 #3

- **무엇**: YAML `cache.key_template` 가 client를 포함하거나(`${client}_channel_metrics.json`), 키 생성을 데이터 레이어 책임으로. pipeline maker는 "어느 layer, 어느 의미" 만 선언.
- **대상**: `pipelines/flows/*.yaml` + `runner.py` 캐시키 조립부 + `dashboard1.py` cache_key.
- **검증**: 단계 2 이후엔 폴더가 이미 client별이라 충돌은 없음 — 본 단계는 "pipeline이 파일명 모름" 원칙 정합용. golden 유지.

### 단계 4 — 직접 파일 로더 정리 · 위반 #4·#5

- **무엇**: `tools/shared/clumi_loader.py`(`load_clumi_source`/`CLUMI_SOURCES`), `tools/shared/helpers.py`(`load_mock_csv`) 의 직접 파일 읽기를 data_sources로 흡수하거나 제거.
- **대상(사용처)**: `missing_value_diagnostic` · `ga4_session_aggregator` · `kst_timezone_normalizer` · `grade_system_unifier` (clumi_loader) / sprint15 수집기 meta·kakao·naver_sa·naver_gfa·google_ads·review (load_mock_csv).
- **주의**: sprint15 수집기는 **이미 깨진 상태**(삭제된 mock 파일 참조)지만 agent team_catalog·planning prompt·sprint15 테스트에 연결됨 → **참조 전수 확인 후** 제거/대체 (큰 결합, 별도 신중 진행).

### 단계 5 — 흩어진 client 기본값 정리 · 위반 #6·#7

- **무엇**: `DEFAULT_CLIENT="clumi"`(tool), `Query("clumi")`(API), `?? 'clumi'`(프론트) 같은 분산 기본값 정리. client는 진입점에서 한 번만 결정.
- **검증**: golden 유지. 사소(경로 위반 아님) — 마지막에 청소.

## 8. ADR 영향

- 본 계획은 **ADR-022 §미해결의 "`LAYER_DIR` MVP dynamic client 분리"** 를 실행 → 완료 시 **ADR-022에 변경이력 추가** (clumi 하드코딩 해소).
- 단계 1(tool 순수화)는 ADR-022 "tool=순수 기능" 원칙의 **완성** (현재 self-save가 남은 잔여 위반).
- 단계 4 sprint15 정리는 별도 ADR 검토 가능 (agent 결합 큼).
