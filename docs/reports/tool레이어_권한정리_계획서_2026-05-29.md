# Tool 레이어 권한·정리 계획서 (2026-05-29)

> 목적: **data layer / tool layer 의 권한(책임)을 명확히** 하고, 그동안 흐려진 위반을 되돌린다.
> 사용자(비전공자)가 두 레이어를 구분 못 한 채 작업하며 생긴 모호함을 **규칙 기반**으로 정리.
> 방식 = **golden(정답지)로 보호되는 점진적 리팩터링** (한 단계 → 검증 → 커밋).

## 0. 레이어 정의 + 권한 규칙 (북극성)

### 두 레이어

| 레이어 | 폴더 | 역할 |
|---|---|---|
| **data layer** | `backend/app/data_sources/` | 데이터 **가져오기** (외부/raw 읽기) |
| | `backend/app/workspace/` | 산출물 **저장·꺼내기** (computed/cleaned) |
| | `backend/app/schemas/` | 데이터 **모양(Pydantic)** 정의 — 행동 없이 "생김새"만 |
| **tool layer** | `backend/app/dream_agent/tools/` | 데이터를 **받아 처리** (정제·지표·계산·추론) |

### 권한 규칙 (한 줄)

> **data layer 만** 데이터가 **어디** 있고 **어떻게** 저장/로드되는지 안다.
> **tool layer 는** 데이터를 **받아 처리만** 한다 — 직접 가지러/저장하러 가지 않고 data layer 에 **부탁**한다.

비유: tool=요리사, data layer=창고지기. 요리사는 "양파 주세요"(`self.ds.get`)라고 **부탁**만; 창고에 직접 들어가 꺼내거나(파일 읽기)·쟁여놓지(파일 저장) 않는다.

### "누가 무엇을 아는가"

| | data layer | tool layer |
|---|:--:|:--:|
| 파일 경로·이름 | **안다** | 모른다 |
| 파일 직접 읽기(`open`·`read_csv`) | **한다** | **안 한다** |
| 디스크 직접 저장(`save`) | **한다** | **안 한다** |
| 데이터 모양(컬럼·필드) | **정의** | 받아서 씀 |
| 계산·정제·추론 | 안 함 | **한다** |
| 데이터 요청 | (응답) | **부탁**(`self.ds.get`) |

## 1. 3개 작업 + 기존 단계 매핑

| 작업 | 내용 | 기존 계획서 단계 |
|:--:|---|---|
| **①** | tool 의 **clumi 값 하드코딩 제거** (client 필수화) | 단계 5 |
| **②** | **권한 위반 수정** (tool 이 파일 직접 읽기/저장) | 단계 4 + 단계 1 |
| **③** | tool **카테고리 기준 명확화** (수집=수집·지표=지표·계산=계산·추론=추론) | (신규 — 별도 분석) |

### ①·② 의 관계 (합칠 필요 없음 — 분리 가능)

같은 tool 안에서 ①과 ②는 **다른 줄**을 건드린다:
```python
DEFAULT_CLIENT = "clumi"                       # ← ① (client 값)
client = merged.get("client", DEFAULT_CLIENT)  # ← ① (client 값)
df = self.ds.get(client, "orders")             # OK (부탁 = 정상)
get_default_workspace().save(...)              # ← ② (권한: tool 이 저장 = 위반)
```
→ 관심사·줄이 다르므로 **따로** 고쳐도 충돌 없음. **유일한 겹침 = `clumi_loader`** (clumi 이름 + 직접 파일 읽기 둘 다 해당) → **②에서 한 번 처리하면 ①의 clumi 잔재도 같이 소멸**. (그래서 ①은 clumi_loader 안 건드리고 ②로 넘김 = 중복 없음)

**실행 순서: ① (기계적·저위험) → ② (섬세) → ③ (분석 후).**

## 2. 작업 ① — client 필수화 (clumi 값 제거)

### 분석 (코드 전수 — 검증된 수치 2026-05-29)

| 유형 | 무엇 | 위치 | 처리 |
|---|---|---|---|
| **A** | `merged/params.get("client", "clumi"\|DEFAULT_CLIENT)` 폴백 (+ `DEFAULT_CLIENT="clumi"` 상수 21개) | **46 tool** (collection 포함; ①에선 **collection 제외 ~45**) | **제거 → 필수** |
| **B** | stale 메타·주석 `"input_source":"data/clumi/clumi_mock_05_orders.csv"`(옛 파일명) | 여러 tool meta | 같은 파일 만질 때 정리(경미) |
| **C** | `clumi_loader`(이름·경로 clumi) | **5 사용처** (collection/_base·grade_system_unifier·kst·ga4_session_aggregator·missing_value_diagnostic) | → **작업 ②** |

### 정체 + 제약 + 개선안 (재검증 결과)

- A 폴백은 production 에선 **안 쓰인다**(API `Query`·runner `${client}` 가 항상 client 전달). 사실상 **테스트 편의**가 46곳에 박혀 "clumi=시스템 기본"처럼 보이는 게 문제.
- ml_models 와 **동일 원칙**: tool 도 **client 필수, 없으면 에러**.
- ⚠️ **제약 재검증:** `tests/dashboard1/` 직접호출 `.execute()` 는 **120곳**. 각 호출에 client 를 넣으면 churn 폭증.
- ✅ **개선 (핵심):** tool 이 client 를 `params` 가 아니라 **`context.client_id`** 에서 읽게 한다. `ExecutionContext.client_id` 는 이미 `Optional[str]=None`(기본값 없음=strict 준비됨). production 은 API/runner 가 ctx.client_id 를 항상 채움. 테스트는 **각 파일의 `ctx` fixture 1곳**(`ExecutionContext(..., client_id="clumi")`)만 고치면 됨 → **~16 fixture 수정**(120곳 아님).

### 실행 방식 (helper-B — 재검증 1차 확정 2026-05-29)

> **목표 = B (tool 은 client 를 모른다).** 구현 2갈래 검증:
> - **full-B**: `DataSource.get(client,X)`→`get(X)` + client-고정 인스턴스 주입. → data_sources/batch 테스트 + 전역 싱글톤(`get_default_data_source`) + 주입 3곳(runner·dashboard1·agent_pool) 연쇄 변경 = **큰 churn·위험**.
> - **helper-B** ✅: BaseTool 헬퍼가 `context.client_id` 로 client 를 채움. `DataSource`/`Workspace` 시그니처 **무변경**(단계 2 보존), data_sources 테스트 무변경. **같은 목표, 저위험.**

1. `BaseTool.fetch(source_id, context)` 헬퍼 추가 — 내부에서 `self.ds.get(context.client_id, source_id)` 수행, `context.client_id` 없으면 명확한 `ValueError`. **tool 코드는 client 를 안 쓴다.** (동작 무변경 — 아직 미사용)
2. 각 tool: `self.ds.get(client, "X")` → `self.fetch("X", context)`; `client = merged.get("client", DEFAULT_CLIENT)` 줄 + `DEFAULT_CLIENT` 상수 **삭제** → **tool 코드에서 client 완전 소멸**. (DataSource/Workspace 시그니처 무변경; tool self-save 의 client 정합은 ②-b 에서)
3. **카테고리별** 진행(metrics → analysis → preprocessing → cleaning → normalization → comparison; **collection 제외** = 작업 ②), 묶음마다 golden 검증 → 커밋. 해당 카테고리 테스트의 **`ctx` fixture 에 `client_id="clumi"` 보강**. B(stale 메타) 같이 정리.
4. **진입점도 clumi 하드코딩 제거 (데이터 기반 대체):**
   - 프론트 `selectedClientId ?? 'clumi'` → `?? clients[0]?.id` (목록의 첫 client; 옵션: `raw_count>0` 첫 client). **'clumi' 글자 제거.**
   - API `client: str = Query("clumi")` → `Query(...)` (필수). 프론트가 항상 전달. ⚠️ API 테스트가 client 미전달 시 보강.
   - 결과: 코드는 "특정 이름"이 아니라 **"목록의 첫 client" 규칙**만 안다 = convention.

⚠️ **신중 포인트:** sprint15 collectors 는 이미 **깨진 상태**(삭제된 mock 참조)지만 agent team_catalog·planning prompt·sprint15 테스트에 **결합**됨. → 참조 전수 확인 후 제거/대체 (별도 신중 단위).

### ②-b self-save 제거 — tool 순수화 (= 단계 1)

- ~30 tool 의 `get_default_workspace().save(...)` 제거 → 저장은 **진입점(runner·dashboard1)** 이 단일 수행.
- ⚠️ **신중 포인트:**
  - tool 저장 시 실린 **ERD용 풍부한 meta(columns·formula)** 를 진입점 저장으로 **이관** 필요.
  - `test_active_orders_filter` · `test_member_metrics_validator` · `test_ad_cost_aggregator` · `test_storage_backend` 등이 **tool 저장 파일을 단언** → 진입점 저장 기준으로 **테스트 재작성**.
- 방식: **확장-축소(expand-contract)** — 진입점에 저장 추가(중복 무해) → tool self-save 카테고리별 제거.

## 4. 작업 ③ — 카테고리 기준 명확화 (분석 예정)

> 아직 **미분석**. 착수 전 "개발문서 기준 + 현 분류"를 대조 분석한다 (사용자 지시: 전체코드를 다 고쳐서라도 명확히).

- 현 카테고리(폴더): `collection` · `cleaning` · `normalization` · `preprocessing` · `metrics` · `comparison` · `analysis` · `report` 등.
- 사용자 기준: **수집 / 정제 / 지표생성 / 계산 / 추론** 이 또렷이 1:1 이어야 하는데, 지금 모호(예: preprocessing↔metrics↔cleaning 경계, comparison↔metrics).
- 분석 계획: (1) 개발문서(agent_specs·ADR)의 카테고리 정의 수집 → (2) 현 tool 의 실제 동작 분류 → (3) 명확한 기준표 합의 → (4) 폴더/카탈로그 재배치(이름 기반이라 flow 무영향). golden 유지.
- → **작업 ③ 착수 시 별도 분석 문서로 진행.**
