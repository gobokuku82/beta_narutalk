## 1. 두 계약의 구분 — 같은 관절(DataSource), 다른 문제

| | ① 출구·저장 계약 (해결됨) | ② 조회 계약 (본 노트) |
|---|---|---|
| 질문 | 가져온 데이터를 **어디에 두느냐** | 데이터를 **얼마나 가져오느냐** |
| 문제 | 결과에 탑재 → state/checkpoint/WS 누수 | 합계 하나에 전체 행 적재 (계산 위치 비효율) |
| POC 실해 | **있었음** — 턴당 155MB 저장·312MB 전송·복원 5.5s·이벤트루프 블록 | **없음** — ms~s, 일시적(GC) |
| 수정 | L3 게이트 + L4 참조반환 + L5 미러제거 (`33ac21a`·`85ef5de`) | **지금 안 함** — MVP+ ADR |
| 상호관계 | ②를 고쳐도 ①은 필요(작게 가져와도 state에 실으면 누수) / ①을 고쳐도 ②는 남음 | **대체 아닌 합성** |

## 2. ②의 정체 — CSV 의미론 잔재 (역사)

[DataSource ABC](../../backend/app/data_sources/base.py#L33)의 조회 메서드는 `get(client, source_id)`(전체) ·
`stream_jsonl(...)`(전체를 한 줄씩) 뿐 — **period·필터·컬럼·집계 인자가 존재하지 않음**.
파일(CSV) 기반 POC에서 "파일 통째"가 자연 단위였고, Postgres 백엔드를 **같은 계약 그대로 drop-in**(R4)
했기 때문에 SQL이 WHERE/SUM 가능한데도 API가 파일 의미론을 물려받음. tool들이 전체 로드 후
Python 필터하는 것(`filter_active_orders(df_전체, ...)`)은 게으름이 아니라 **관절이 그것밖에 제공 안 해서**.

## 3. 진화 경로 — "갈아엎기"가 아닌 추가(additive) 3단계

**전제(실측)**: 데이터 접근은 전부 단일 관절 통과 — **52파일·60호출** (`self.fetch`/`ds.get`/`stream_jsonl`,
"raw 직접 로드 금지" 컨벤션). 변경 표면이 열거 가능. file→Postgres drop-in 교체(R4)가 tool 무수정으로
끝난 것이 관절 격리의 실증 전례.

```
1단계  DataSource 에 신규 메서드 — 기본 구현 = 현행(전체 로드 후 Python 필터)
        get(client, source_id, *, period=None, columns=None, where=None)
        aggregate(client, source_id, *, op, by=None, where=None)   # 행 대신 값
        → tool 0개 수정 · 동작 변화 0. (설계 포함 1~2일감)
2단계  PostgresDataSource 만 override → SQL pushdown. File 백엔드 = 기본 구현 유지.
        → 여전히 tool 0개 수정. 같은 API, 백엔드별 구현 = 관절의 존재 이유.
3단계  tool 점진 전환 — 큰 소스 읽는 10~20곳만 (revenue_total 등 metrics 우선).
        나머지 ~40곳(소형)은 get() 유지 무방. 기존 정답값(§S) 회귀 테스트가 안전망.
        마무리는 전환 sprint (v1/v2 공존 후 일괄 정리 — 섞임 금지 원칙).
```

부수 효과: collector 의 "count 용 전체 일시 적재"(L4 잔여)도 `aggregate(op="count")` 로 정리됨.

## 4. ADR 에서 결정해야 할 것 (진짜 일 = API 모양)
1. **필터 표현** — where dict vs 전용 파라미터(period 등) vs 미니 DSL. 과설계 금지(필요 분만).
2. **비즈니스 규칙의 거처** — "활성 주문" 정의를 SQL 로 내리면 규칙이 두 곳(코드+SQL) → 관절 안 한 곳으로 모으는 설계.
3. **두 백엔드 일관성 계약** — 같은 질의 = 같은 답. postgres_backend_e2e 패턴으로 교차 검증.
4. text2SQL 비채택 재확인 — "LLM은 숫자를 계산하지 않는다" 원칙. pushdown 은 **사람이 쓴 파라미터화 쿼리**(결정론).
   (text2SQL 은 별도 롱테일 즉석조회 레인 후보 — 정답값 아님 라벨 전제, 범위 밖.)

## 5. 트리거 — 언제 하나
**실데이터(광고 API) 진입 = MVP+.** mock 규모(수천~수만 행)에선 실측 비용 무시 가능 — ONE 변경 원칙대로
지금은 안 함. 트리거 도달 시 본 노트 → ADR 승격.
