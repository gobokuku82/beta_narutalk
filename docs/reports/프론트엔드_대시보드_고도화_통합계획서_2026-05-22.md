### 0.2 왜 1개 계획인가 — 3가지를 합친 이유

"데이터기반 대시보드 고도화 / 스타일 개선 / 시각화 논의" 3가지는 **나란한 프로젝트가 아니라 한 화면의 3개 레이어**다. 대시보드 컴포넌트 하나가 동시에 ① 무슨 데이터를 보여주나(데이터기반) ② 어떤 차트로 그리나(시각화) ③ 어떻게 칠하나(스타일)를 갖는다. 3개로 쪼개면 같은 컴포넌트가 3문서에 중복되고 합칠 때 충돌한다.

→ **원칙: 3가지로 생각하되, 1개로 쓴다 (think in 3, plan in 1).** 3은 §2.2 의 *레이어*로 살아 있고, 실행은 본 문서 하나다.

## 2. 구조 모델 — 2 트랙 + 3 레이어

### 2.1 2 트랙 — 데이터 / 프론트, 이음매는 "데이터 계약"

```
[데이터 트랙]  데이터_파이프라인_구조_계획서 + 데이터사전·설명서
                       │  raw → cleaned → computed 데이터 생산
                       │
                ┌──────┴──────┐
                │  데이터 계약   │  ← computed 데이터의 shape (TS 타입/zod + mock fixture)
                └──────┬──────┘     이게 이음매. §9 참조
                       │
[프론트 트랙]  본 문서 (1개 통합 계획)  →  계약을 화면으로
```

→ 데이터 트랙이 미완이어도, **데이터 계약(shape)** 만 먼저 못박으면 프론트 트랙은 더미 데이터로 진행 가능하다. 실데이터가 나오면 계약에 *배선만* 한다 — 컴포넌트 재작업 0. (계약 정의 = 시각화 구조이므로 프론트 트랙의 일. 계산 로직 = 데이터 트랙.)

### 2.2 3 레이어 — think in 3, build in 1

| 레이어 | = 사용자의 3가지 계획 | 내용 | 주 입력 |
|---|---|---|---|
| **[데] 데이터기반** | 데이터기반 대시보드 고도화 | *무엇을* 보여주나 — 지표·퍼널·목표·페이싱 (구성) | 데이터 시각화 구조 계획서 + 도메인 모델 §3 |
| **[시] 시각화** | 시각화 논의 | *어떻게 그리나* — 차트·표 craft, 기준선·축·in-cell viz | 본 문서 §4·§6 + 분석 §1.A~K |
| **[스] 스타일** | 스타일 개선 | *어떻게 보이나* — 위계·절제·색·타이포 (표현) | 분석 §1·§4 + 스캐폴딩 감사 |

→ 3 레이어는 **따로 작업하지 않는다.** 컴포넌트 하나를 만들 때 [데]+[시]+[스]를 *한 번에* 적용한다 (§7 로드맵의 A3·A4 가 그 지점). 3은 *생각의 렌즈*이지 작업 단위가 아니다.

## 3. 퍼포먼스 마케팅 도메인 모델 — [데] 레이어의 골격

원칙(§4)·컴포넌트(§6)·페이지(§8) 전부 이 도메인 모델 위에 선다. 상세 = 분석 문서 §0.2·§2.

### 3.1 지표는 *인과 사슬* 이다 — 점수판이 아니라 시스템

```
노출수 ─(CTR)→ 클릭수 ─(CVR)→ 전환수 ─(객단가)→ 전환매출
   │              │              │                  │
  CPM           CPC            CPA          ÷ 광고비 = ROAS
```

→ ROAS 가 떨어지면 마케터는 *어느 고리가 끊겼나*(CTR? CVR? CPC?)를 추적한다. 시각화는 이 **사슬**을 보여줘야 한다 — 서로 무관한 KPI 4칸(점수판)은 진단을 불가능하게 한다.

### 3.2 그 외 도메인 상수

| 항목 | 내용 |
|---|---|
| 목표 대비 | 모든 ROAS·CPA 는 *목표 대비*로 읽힌다. `campaigns.csv` 에 `목표ROAS`·`목표CPA`·`목표전환수` 존재. break-even ROAS = 1 ÷ 마진 |
| 예산 페이싱 | 예산은 *기간 내* 소진. under(<90%)/on-track/over(>110%) 점검이 마케터의 매일 첫 일 |
| 채널 역할 | 검색(수요 수확, ROAS↑) vs 소셜·디스플레이(수요 창출, 단기 ROAS↓). 단일 ROAS 막대 비교는 오해 — 채널별 벤치마크로 |
| 분석 위계 | 캠페인 → 소재 / 키워드. 전체 진실 지표 = blended ROAS / MER (전체 매출 ÷ 전체 광고비) |

## 4. 시각화 디자인 원칙 (P1~P9)

각 원칙 = 명령 한 줄 + 제약. 모든 컴포넌트·페이지가 따른다. anti-AI-slop 처방대로 **긍정 지시가 아니라 제약**으로 쓴다. P1~P3 = [데] 도메인 원칙, P4~P8 = [시] craft 원칙, P9 = [스] + 공통.

| # | 레이어 | 원칙 | 적용 (제약) |
|---|:---:|---|---|
| **P1** | [데] | **지표를 시스템으로 — 점수판 금지** | KPI 행은 무관한 4칸이 아니라 **퍼널 사슬**(노출→클릭→전환→매출 + 전이 비율)을 보여준다 |

## 5. 팔레트 결정 — 3안

분석 §4 결론: **톤이 아니라 색의 역할 분리 실패가 문제.**

| 안 | 내용 | 비용 |
|---|---|:---:|
| **A. 베이스 유지 + 역할 재분리** ⭐ | Warm Neutral 베이스·옥스블러드 유지. 액센트 = 강조·액션 전용, `--chart-1~5` 재설계, 채널 색과 차트 색 정리 | 저 |
| B. 톤 중립화 | 옥스블러드 → 더 중립적 액센트로 한 단계 | 중 |
| C. 전면 재설계 | 팔레트·차트 팔레트·타이포 동시 | 고 |

> **권장 = A.** 톤은 AI스러움의 주원인이 아니다. 색 역할을 P8 대로 분리하면 비용 대비 효과 최대. **→ 2026-05-22 사용자 결정: A안 채택.** Phase A2 에서 토큰 반영.

## 6. 컴포넌트 방향

방향 수준만. 데이터 시각화 구조 계획서 §5·§10 의 컴포넌트 목록과 동일 대상 — 본 문서는 *디자인 규칙*을 정의.

| 컴포넌트 | 레이어 | 방향 |
|---|:---:|---|
| **MetricChainStrip** | 데·시 | KPI 4칸 → 퍼널 사슬 strip (노출→클릭→전환→매출 + 전이 비율). `KpiCard` 개편 |
| **MetricTile** | 데·시 | 단일 지표(예: MER) — 숫자 + 목표 대비 + 전기간 + 미니 스파크라인. 아이콘 칩 제거 |
| **PacingWidget** | 데·시 | 캠페인별 집행률 under/on/over 밴드. '평균 한 숫자' 폐기 |
| **ChartFrame** | 시·스 | 차트 공통 규약 — 작은 제목, 목표선·break-even API, 축 분리 강제, 연한 그리드 |

| **ChannelComparison** | 데·시 | 단일 ROAS 막대 폐기. 채널별 small multiples / 벤치마크 대비 |
| **DataTable** | 시 | `@tanstack/react-table` — 정렬·in-cell 막대/히트·합계행. 캠페인·키워드·소재 |

## 7. 실행 로드맵 — A구간 / B구간 ⭐

**핵심 재편**: 로드맵을 *주제(데이터/스타일/시각화)순* 이 아니라 **데이터 의존성순**으로 짠다. 각 Phase 안에서 3 레이어를 *함께* 적용한다.

### A구간 — 데이터 무관 (지금 착수 가능, 전체의 ~70%)

| Phase | 작업 | 레이어 | 입력 문서 |
|---|---|:---:|---|
| **A0** ✅ | 스캐폴딩 제거 — 배지·`/api/mock` footer·`localhost:8001` 에러·제품명·favicon **(완료 2026-05-22)** | [스] | 스캐폴딩 감사 Tier 1 |
| **A1** | **데이터 계약 확정** — computed 데이터 shape (TS 타입/zod) + mock fixture. *두 트랙의 이음매* (§9) | [데] | 데이터 시각화 구조 계획서 §11 + 데이터사전 |
| **A2** ✅ | 색 역할 분리 — `--chart-1~5` 재설계(액센트·채널색과 분리) · 퍼널/키워드 막대 accent→chart-1 **(완료 2026-05-22)** | [스] | 분석 §4 / 본 문서 §5 |
| **A3 ✅** | 공통 부품 6종 완료 (2026-06-08) — MetricChainStrip · ChartFrame · DataTable · FunnelChart · PacingWidget · ChannelComparison. 5 v2 페이지 모두 적용 (dashboard·channel·trend·creative·cost). 3 레이어 동시 적용 | [데·시·스] | 본 문서 §6 + 데이터 시각화 구조 계획서 §5·§10 |
| **A4** | 대시보드 1장 파일럿 (더미) — 사슬·목표선·페이싱 패턴 박제 → **사용자 확인** | [데·시·스] | 본 문서 §4·§8 |

| Phase | 작업 | 레이어 | 입력 문서 |
|---|---|:---:|---|
| **B1** | 페이지 매핑 재도출 — clumi 20 소스 기준 (어느 지표를 어느 페이지에) | [데] | 데이터 파이프라인 산출물 + 데이터 시각화 구조 계획서 §6.3 |

| **B3** | 페이지별 레이아웃 분화 확산 — §8 매핑대로 5개 페이지 | [데·시·스] | 본 문서 §8 |

## 9. 데이터 계약 — 두 트랙의 이음매

A1 에서 못박는다. 데이터 트랙이 미완이어도 프론트가 멈추지 않게 하는 장치.

- **계약 = computed 데이터의 *shape***: 페이지별 지표 row 의 TS 타입 / zod 스키마 + 현실적 더미값을 채운 **mock fixture**.
- 계약 정의는 *시각화 구조* — 프론트 트랙의 일. *계산 로직·실제 값*은 데이터 트랙(작업 분담).
- 컴포넌트(§6)는 실데이터가 아니라 **계약**에 대고 만든다 → 실데이터 도착 시 B2 에서 배선만.
- 표면은 데이터 시각화 구조 계획서 §11 API 계약(`{data: row[], count}`)을 계승, 페이지별 row 모양까지 확장.
