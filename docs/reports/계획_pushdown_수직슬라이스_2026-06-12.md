## 0. 저장 구조 실측 (설계의 토대 — 2026-06-12 확인)

Postgres raw 는 **두 모양**으로 저장돼 있다 ([postgres.py](../../backend/app/data_sources/postgres.py) · [data_pg_util.py](../../backend/app/data_pg_util.py)):

| 모양 | 어떤 소스 | 구조 | SQL pushdown |
|---|---|---|---|
| **행-테이블** (스트리밍 적재본) | 대용량 — GA4 traffic(38,319행)·page_events 등 **(⚠→§8 V1 우선: 현 라이브 DB에서 traffic은 통 blob — 정상 적재 시의 모양임)** | `{client}.{raw_xxx}(_id, data jsonb)` 행 1개=레코드 1개, `_workspace.payload={__streamed__: 테이블명}` 마커 | ✅ **바로 가능** (`data->>'키'` + WHERE/GROUP BY) |
| **통 JSONB blob** | 소형 — orders.csv 등 | `_workspace.payload` = records 통째 | ❌ 안 함 — 소형이라 이득 0, 기본 구현(로드 후 Python)로 충분 |

→ **pushdown 이 의미 있는 곳(대용량)은 이미 SQL-ready.** 이 계획은 그 길만 판다. **(⚠→§8 V1: "이미"는 정상 적재 전제 — 착수 시점엔 재적재 선행 필수)**

| 포함 | 제외 (사유) |
|---|---|

## 2. ADR 결정 제안 4건 (본 계획 승인 = 이 결정 승인 → ADR 파일로 박제)

1. **필터 표현 = 최소 dict** — `where: {컬럼: 값}` (동등) + `{컬럼__prefix: "2026-04"}` (접두) **두 연산자만**.
   필요해질 때 연산자 추가 (과설계 금지 — convention 우선 원칙).
2. **도메인 규칙의 거처 = tool** — 관절은 **범위 축소(행·컬럼·단순 집계)만** 담당.
   "활성 주문 정의"·"GA4 소스 추출 fallback" 같은 비즈니스 규칙은 tool 코드 한 곳에 유지 (이중화 금지).
3. **두 백엔드 같은답 계약** — 같은 `query/aggregate` 호출은 File·Postgres 에서 동일 결과.
   교차 일관성 테스트로 강제 (postgres_backend_e2e 패턴).
4. **text2SQL 비채택 (본 계산 경로)** — pushdown 은 **사람이 쓴 파라미터화 SQL**(결정론).
   text2SQL 은 별도 롱테일 즉석조회 레인 후보로만 (정답값 아님 라벨 전제, 범위 밖).

## 3. 설계

### 3.1 관절 시그니처 (base.py — additive, 기존 get/stream_jsonl 불변)
```python
def query(self, client, source_id, *, where=None, columns=None) -> list[dict]:
    """부분 행 조회 — where(동등/__prefix)로 행 축소 + columns 로 투영.
    기본 구현: self.get() → list[dict] 정규화(DataFrame→records) → Python 필터/투영."""

def aggregate(self, client, source_id, *, op="count", column=None, by=None, where=None):
    """집계 내리기 — 행 대신 값/분포 반환. op ∈ {count, sum} (v1).
    by 지정 시 {그룹값: 집계값} dict, 미지정 시 스칼라. 기본 구현: query() 후 Python 집계."""
```
- 기본 구현이 베이스에 있으므로 **File 백엔드 자동 지원, 기존 tool 0개 수정, 동작 변화 0.**

### 3.2 Postgres override (postgres.py)
- 판별: `_workspace.payload` 에 `__streamed__` 마커 → 행-테이블 SQL / 아니면 `super()`(기본 구현) fallback.
- SQL (psycopg `sql.Identifier` 합성 — 테이블·컬럼 인젝션 불가, 값은 바인딩):
```sql
-- aggregate(op=count, by="event_name")
SELECT data->>'event_name', count(*) FROM {client}.{tbl} GROUP BY 1;
-- query(where={event_name: session_start}, columns=[...]) — 투영 + 축소
SELECT jsonb_build_object('a', data->'a', 'b', data->'b') FROM {client}.{tbl}
WHERE data->>'event_name' = %s;
```

### 3.3 시범 전환 — [ga4_session_aggregator](../../backend/app/dream_agent/tools/metrics/ga4_session_aggregator.py)
현행 = 38,319행 **전부**를 Python으로 스트리밍하며 두 Counter 집계. 전환:
```python
by_event  = self.ds.aggregate(client, GA4_SOURCE_ID, op="count", by="event_name")   # SQL 1방
rows      = self.ds.query(client, GA4_SOURCE_ID,
                          where={"event_name": "session_start"},
                          columns=["session_traffic_source_last_click", "event_params"])
by_source = Counter(self._extract_source(r) for r in rows)   # 도메인 규칙은 tool 유지 (ADR-2)
```
- 효과: 38,319행 전량 순회 → **SQL GROUP BY 1회 + session_start 24,000행×2컬럼 투영**.
- `_extract_source`(중첩 fallback 규칙)는 SQL로 안 내림 — 일부러 (ADR-2 실증: 관절=범위, tool=규칙).

## 4. 안전 분석
- 기존 `get`/`stream_jsonl` **무변경** — 60호출/52파일 전부 무영향.
- 신규 메서드 사용처 = 시범 tool 1개뿐. 그 tool 은 **정답값 3개로 고정**되어 있어 회귀가 강함:
  `session_start_total=24,000 · first_visit=12,496 · purchase=1,823` (docstring 박제) + S067 pipeline(가입 전환율).
- 롤백: 시범 tool 1파일 revert → 관절 신메서드는 미사용 상태로 무해 (additive).

### 8.1 착수 전 필수 보완 4건

| # | 발견 (실측) | 보완 (끼어드는 위치) |
|---|---|---|
| V1 | **§0 "실측"이 현 DB와 불일치** — GA4 traffic이 현재 행-테이블+`__streamed__` 마커가 아니라 **통 blob** (라이브 실측: payload 13.25MB). 귀속 정정(검증 R2): 사고 복구가 아니라 **외부 수집기의 blob save가 06-11 20:47 마커를 덮은 것 — V2와 동일 기전의 실증** (일회성 아님, 구조 문제). 이대로면 S2 override가 전부 fallback으로 빠져 pushdown이 발화하지 않음. **🆕테스트 검증(E2·E3)**: `raw_ga4_traffic_source` **행-테이블은 살아 있음(38,319행 = blob과 일치, typed 31컬럼)** — 마커만 끊김. 또한 traffic 행-테이블은 `(_id, data jsonb)`가 아니라 **typed 컬럼**이라 §3.2 스케치 SQL은 page_events 모양 기준이고 시범 경로는 더 단순(`SELECT event_name, count(*) … GROUP BY 1`) | **S2 앞에 단계 신설** — 옵션 2: ⓐ 경량 = **마커 복원만**(행-테이블 현존·행수 일치 검증 후 `_workspace`에 `__streamed__` 마커 재기입) ⓑ 전체 재적재(`load_raw_to_data_db` — 286MB page_events 재스트림 수 분, `data/clumi/raw`=진실원천 확인 선행). S2 감지 로직은 **typed/generic 두 행-테이블 모양 모두 인지**해야 함. §6 시간 비교는 복원 후 유효 — 단 **효과 수치는 이미 선납**(테스트 검증 E4: 현행 604ms vs SQL 23.6ms ≈ **26배**, 정답값 3개 SQL 교차 일치) |
| V2 | **마커 침묵 소멸 구조** — 외부 수집기의 blob save가 기존 `__streamed__` 마커를 덮고 스트림 테이블을 DROP → pushdown 경로가 **수집 1회마다 소리 없이 사라짐** | **ADR 5번째 결정 추가**: 대용량 jsonl 수집 저장도 save_stream 라우팅(또는 save()의 마커 보존). 최소한 S2 테스트에 "시범 source 마커 존재 assert" (침묵 강등 → RED) |
| V3 | **기본 구현의 역행** — query/aggregate 기본 구현(전량 로드 후 Python)이 시범 tool 전환 시 File/blob 경로에서 기존 스트리밍 1-pass를 **전량 적재 2회**로 바꿈 (메모리·시간 역행인데 §4 안전 분석 누락) | S1 설계에 분기 명시: jsonl 소스의 기본 구현은 stream_jsonl 기반 (스트리밍 유지). §6에 File 경로 시간·피크 메모리 비교 추가 |
| V4 | **회귀 기준선 낡음** — §5-5 "865+/기존실패 16"은 현재 919 pass/3 fail과 drift (수리된 13건의 재파손을 면책하는 수치) | S0에서 착수 시점 전체 suite 실측 → pass 수·실패 목록 박제, 그 수치 대비 회귀 0으로 교체 |
| V5 | **§5-4 "(DATA_BACKEND=postgres)" 무효** (검증 R2) — 그 env var는 테스트에 효력이 없고, 정답값 회귀는 현재 File 전용·시범 tool의 Postgres 경로 테스트는 0개. 글자대로 수행하면 File만 돌고 green | §5-4 교체: `set_data_source(PostgresDataSource())` fixture(test_postgres_backend_e2e 패턴)로 정답값 3 + S067을 **postgres 경로에서 실측** (V1 재적재 후 clumi 실DB 대상 — **skip 0 전제**, DB 미기동이면 게이트 불통과). V2 마커 assert도 fixture 스키마가 아닌 **clumi 실DB** 검사로 명시 |

### 8.2 표기 정정 3건 (소형)

- §5-2 fixture: `write_jsonl_rows_streaming` 직접 호출이 아니라 **`ws.save_stream` 경유**가 기존 패턴(test_postgres_streaming — 마커까지 생성).
- §3.1 "base.py의 기존 get/stream_jsonl 불변": `stream_jsonl`은 ABC에 없음(구현체별) — S1에서 ABC 승격 여부 1줄 결정.
- 데이터 환경 실측(2026-06-12 검증 시점): data/clumi/raw **복구 완료(30파일)**, GA4 38,319행·정답값 3개(24,000/12,496/1,823) 파일 실측 일치 — File 경로 검증은 성립, Postgres 효과 측정은 V1 해소 후 유효.
