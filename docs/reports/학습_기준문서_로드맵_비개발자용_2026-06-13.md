## §0 큰 그림 — 3 카테고리의 경계 (먼저 이걸 알아야 나머지가 정리됨)

오너가 나열한 세부 항목들("data 흐름 / 시스템 flow / tool이 데이터 가져오고 전달 / tool 연결 시 흐름 / state 관리")은 **한 카테고리에 안 들어갑니다.** 경계를 가르는 질문 하나:

> **이게 실패하면 — LLM이 오판하나(→컨텍스트), 데이터가 틀리나(→데이터), 실행이 틀리거나 거짓 성공하나(→하네스)?**

| 카테고리 | 한 줄 정의 (출처) | 다루는 것 |
|---|---|---|
| **데이터 엔지니어링** | 데이터 자체와 그 의미·이동 (LLM 무관) | data 구성·메타데이터·tool이 데이터 *가져오기*·지표 정의 |
| **컨텍스트 엔지니어링** | "LLM이 보는 토큰의 큐레이션" (Anthropic) | LLM 프롬프트 입력 조립·무엇을 넣고 빼나·누적 |
| **하네스 세팅** | 모델 바깥 비계 전부 (OpenAI 2026) | 시스템/에이전트 flow·tool *전달*·state 관리·게이트·layer 역할 |

⚠️ 오너 항목의 함정: **"tool이 데이터를 가져오고 전달"은 둘로 쪼개집니다** — *가져오기*(fetch)는 데이터 엔지니어링, *전달*(tool→tool)은 하네스. "state 관리"도 하네스. 이 분리가 첫 번째 배울 점.

## §1 데이터 엔지니어링

**정의**: 데이터가 무엇이고(구성), 어떤 의미인지(메타데이터), 어떻게 보관·조회되는지. LLM과 무관한 순수 데이터 문제. *(우리 시스템의 가장 빈 곳 — 본진)*

| 세부 항목 | 외부에서 배울 것 (검색어) | 현황 (as-is) | 만들 기준문서 (should-be) |
|---|---|---|---|
| data 구성 | 데이터 레이어(raw/cleaned/computed), 스키마 설계 | data/clumi/{raw,cleaned,computed} 존재 · [36 mock raw 설계](../agent_specs/36_clumi_mock_raw_data_design_v1.0.md) | 데이터 사전 갱신 (컬럼·단위·출처) |
| **메타데이터** | **Data Contracts (ODCS 표준), 데이터 카탈로그** | 관례 4개 자생·계약 0 (학습판 §2) | **산출 계약**(D1 장부·D2 신분 3분류) |
| tool이 데이터 *가져오기* | Repository 패턴, query pushdown | DataSource.fetch + query/aggregate (ADR-031 ✅) | 이미 양호 — 문서화만 |
| **지표 정의** | **Semantic Layer (dbt MetricFlow, Cube)** | ROAS 3값 모순 (분모 2종+grain) | **지표 registry**(D7) — ROAS 분모 결정 선행 |
| 데이터 출처 추적 | Data Lineage (OpenLineage, W3C PROV) | provenance 0 (dropped 사고의 토양) | 장부에 생산자 칸 (D1) |

## §2 컨텍스트 엔지니어링

**정의**: LLM이 추론할 때 *보는* 토큰을 무엇으로 채울지의 설계. 프롬프트(어떻게 묻나)보다 넓음(모델이 무엇을 알게 하나). *(이미 하고 있으나 정책이 없음 — 명문화 대상)*

| 세부 항목 | 외부에서 배울 것 (검색어) | 현황 (as-is) | 만들 기준문서 |
|---|---|---|---|
| 계획 LLM 입력 | 점진 메뉴 축소, 닫힌 메뉴 | **잘 됨** — 3단 메뉴(보존 목록 #1·2) | 보존 명문화 (건드리지 말 것 박제) |
| **LLM tool 입력** | LangChain Write/Select/Compress/Isolate, 12-factor F3 | 무차별 키 스캔+denylist+[:3000] (dropped 산실) | **입력 투영 정책**(C1·C2) |
| 무엇을 넣고 빼나 | Anthropic context engineering, MCP audience | 수기 denylist (한쪽 고치면 누락) | 신분 기반 거름 (D2 소비) |
| 토큰 예산·압축 | compaction, 토큰 budget | 무음 절단 (정책 0) | 예산 정책(C3) |
| **누적 계약** | (오너 원의도 — 외부엔 정식 용어 적음) | planning→execution에서 의도 단절 (M0 T4) | **의도 귀속 링크**(누적 계약) |

## §3 하네스 세팅

**정의**: 모델 바깥의 비계 — 실행 루프·게이트·검증·HITL·layer 오케스트레이션. *(우리 시스템에서 가장 두꺼움 — 재편 대상, 신설 아님)*

| 세부 항목 | 외부에서 배울 것 (검색어) | 현황 (as-is) | 만들 기준문서 |
|---|---|---|---|
| 시스템/에이전트 flow | LangGraph state graph, 오케스트레이션 | 13노드 토폴로지 (builder.py) · [10·14·15 문서](../agent_specs/14_system_agent_overview_v1.0.md) | flow 문서 ↔ 코드 일치 점검 |
| 4-layer 역할·**권한** | 책임 주도 설계(RDD), 관심사 분리 | 역할 정의는 있으나 "권한"(직접 vs manager 위임) 미결 | **책임 대장** (사건→책임 귀속) |
| tool *전달* | **Blackboard architecture, Actor 모델** | 이름 복사 4갈래·출처 0 (학습판 §2) | **전달 계약**(D6 명시 매핑) |
| **state 관리** | LangGraph state 최소주의, artifact store | state에 raw 적재→슬림 임시대응 (state_guard) | **state 명세**(장부만 싣기, D1·D5) |
| 게이트·검증 | agent harness, 계약-게이트 관계 | 게이트 28 ([43 대장](../agent_specs/43_gate_ledger_v1.0.md)) | 계약 파생물로 재편(H1~H3) |
| execution/response 역할 | 오케스트레이터 패턴 | execution이 데이터플로까지 떠안음 (무주공산) | 책임 대장(위와 동일) |

## §6 기준문서 — 무엇을 어떤 식으로 만드나

**무엇을 (우선순위순)**:
1. **산출 계약 + state 명세** (D1·D2·D5) — 본진. dropped·스텁 누출·디버깅불가를 한 번에
2. **지표 registry** (D7) — ROAS 모순. *오너 결정(분모) 선행*
3. **책임 대장** (execution/response 권한) — 사건 목록 × [layer 직접 / manager 위임 / 계약 해소]
4. **20 INTERFACE_CONTRACT 갱신** — 4월 내용 그대로인 죽은 문서 되살리기

씨앗은 이미 있음: [설계기준서 4부](설계기준서_데이터전달_4부_2026-06-13.md)가 1·2의 초안 (검증 반영 후 v1.1).

**어떤 식으로 (형식 원칙)**:
- 각 항목에 **현황(as-is) + 기준(should-be) 2칸 병기** — 현황만 적으면 옳고그름 판단 불가 (오너의 무력감 원인)
- 모든 주장에 **출처/코드 위치** — "그럴듯한 설명"으로 납득시키지 않기 (검증 가능 서술 원칙)
- 가능하면 **살아있는 문서로** — 위반 시 테스트 RED (게이트 대장 방식). 수동 관리 유지 결정이므로 강제는 선택적이나, 핵심 계약 몇 개만이라도 RED로 박으면 통제가 빨간불로 단순해짐
