# 세션 연속성(Session Continuity) — 설계·구현 계획 (2026-06-11)

> 재접속/새로고침해도 **(②)작업 중이면 입력 잠기고 (③)직전 대화가 보이고 (④)아직 도는 턴이면 현재 진행이 라이브로 이어 보임.**
> 발단: 대화이력은 클릭 복원만 됨 → "처음 접속해도 직전 채팅이 보여야 / 작업 중이면 입력 막혀야 / 6번에서 껐다 켜면 9번 작업 중으로 보여야".
> 상태: **요구·아키텍처 실측 완료. 전부 구현 합의(A+B). 코드 대기.**

## 0. 한 줄
세션 연속성 = `[정적 대화 복원] + [실행 중 입력 잠금] + [라이브 실행 재연결]` 한 빌드. A(토대) 위에 B(라이브) 적층.

| # | 능력 | 현 상태 | 비용 |
|---|---|---|---|
| ① | 브라우저 꺼도 **백엔드 실행 계속** | ✅ **이미 그럼** (독립 task) | 0 |
| ② | **실행 중 추가 채팅 입력 차단** | ❌ 실행 중에도 입력/송신 됨 | 작음(프론트) |

| ④ | 재접속 시 **라이브 실행 재연결**("9번 작업 중") | ❌ 안 됨 | 중간(백+프론트) |

## 2. 핵심 사실 (코드 실측)

- **실행 ⫽ WS 독립**: [ws_agent.py:636](../../backend/api_v2/ws_agent.py#L636) `asyncio.create_task(run_turn(...))` (주석 L487 "WS 연결과 독립된 async task") → 브라우저 꺼도 todo 7,8,9… 계속 돌고 매 노드 checkpoint 저장. → ① 이미 됨.
- **conn_manager 버퍼 없음**: [connection_manager.py:82](../../backend/api_v2/connection_manager.py#L82) `broadcast_to_user`는 현재 연결된 ws에만 쏨. 끊긴 동안 이벤트 **유실**(재생 큐 X).
- **실행 store = in-memory**: [execution/store.ts](../../frontend/src/features/execution/store.ts) plan·todoRuntime·progress가 **WS 이벤트로만** 채워짐 → 새로고침 시 전부 소실.
- **hydrate 부분 복원**: [main.tsx:11](../../frontend/src/main.tsx#L11)→[session/store.ts:95](../../frontend/src/features/session/store.ts#L95) `hydrate()`는 **conversationId만** 복원. 메시지·실행상태·turnId 복원 안 함. (단 `last_turn_id`는 localStorage에 저장돼 있음 — [store.ts:78](../../frontend/src/features/session/store.ts#L78))
- **활성 턴 레지스트리**: [concurrency_manager.py:27](../../backend/app/dream_agent/workflow_managers/concurrency_manager.py#L27) `_active[user_id]:set[turn_id]` — 백엔드가 어느 턴이 도는지 이미 보유. (`is_active` 미존재 → 추가)
- **resume_query 한계**: [ws_agent.py:643](../../backend/api_v2/ws_agent.py#L643) `resume_only`는 **pending interrupt(pause/plan_review) 턴만** 복원. 도는(비-interrupt) 턴 라이브 재구독 경로 없음.

## 3. 부팅 복원 흐름 (설계)

```
RootLayout mount (hydrate 후 1회):
  convId = session.conversationId           # localStorage 복원분
  if !convId → 아무것도 안 함 (default 빈 채팅)
  else:
    A. turns = fetchConversationTurns(convId) → agent.loadMessages(turns)   # ③ 정적 복원
    B. lastTurnId = localStorage['octormate.last_turn_id']
       if lastTurnId:
         snap = GET turn-state(convId, lastTurnId)                          # ④ 신규 경로
         if snap.is_running:
           execution.rehydrateFromSnapshot(snap.plan, snap.completed, snap.progress)  # ④
           # 이후 todo_*/progress 라이브 이벤트는 ws 재등록(user=demo)으로 자동 수신
       # 입력 잠금은 isRunning derive 로 자동                                 # ②
```
> **정적(③)과 라이브(④)는 양립**: 완료 메시지는 항상 정적 복원, 진행 박스는 is_running일 때만 rehydrate. 과거 "박스 안 없어지는 버그" 수정 존중(완료 후엔 박스 안 뜸).

## 4. 컴포넌트별 변경

### 프론트
- **`features/agent/restore.ts` (신규 공용)**: `turns → ChatMessage[]` 매핑 함수 추출 ([ConversationsPage.restore() L84-99](../../frontend/src/features/conversations/ConversationsPage.tsx#L84) 중복 제거, 양쪽 공용).
- **`routes/RootLayout.tsx`**: boot-restore `useEffect` (§3 흐름). hydrate 후 1회.
- **`features/execution/store.ts`**: `rehydrateFromSnapshot(plan, completed, progress)` 액션 신규 + `isResumedLive` 표식(선택). 라이브 이벤트와 additive 정합.
- **`features/agent/SideChatPanel.tsx`**: textarea/송신 `disabled`에 `isRunning` 추가 + placeholder "작업 중… 완료 후 입력 가능". (②)
- **`api/hooks/useConversations.ts`** (or 신규): `fetchTurnState(convId, turnId)`.
- **`features/session/store.ts`**: `lastTurnId` getter 노출(또는 boot에서 localStorage 직접 read).

### 백엔드
- **`concurrency_manager.py`**: `is_active(user_id, turn_id) -> bool` 추가 (`turn_id in self._active.get(user_id, set())`).
- **턴 상태 조회 경로 신규** — **REST 권장** `GET /api/conversations/{conv_id}/turns/{turn_id}/state`:
  - `thread_id = make_thread_id(conv_id, turn_id)` → `agent.aget_state(config)`
  - 반환 `{is_running: concurrency.is_active("demo", turn_id), plan, completed_todos, running_todo, progress}` (state.values에서 추출)
  - REST 선택 이유: boot 시 1회, WS 핸드셰이크 전에도 호출 가능, 단순. (WS msg 대안도 가능)
- **라이브 재구독 = 추가 0**: 재접속 ws가 `user_id=demo`로 재등록되면 도는 task의 broadcast 자동 수신.

## 5. 구현 순서 (검증 단위 = 커밋)

```
P1  ② 입력 잠금              [프론트만] 라이브 세션 내 즉시 검증 (실행 중 입력 막힘)
P2  ③ 정적 복원              [프론트만] restore.ts 추출 + RootLayout effect → reload 후 직전 대화 표시
P3  ④-백엔드 turn-state + is_active   headless 호출로 스냅샷 shape 검증 (running/done/없음 3케이스)
P4  ④-프론트 rehydrate + boot 분기 + 라이브 재구독 e2e   긴 턴 mock으로 6→9 시나리오 검증
```
> P1·P2는 백엔드 0. P3부터 백엔드. 각 P 완료 시 테스트 통과 후 path-scoped 커밋.

## 6. 미결정 / 리스크

1. **스냅샷 소스** — `aget_state(config).values`의 plan·execution_result vs hitl progress: P3에서 실측 후 확정(필드 shape 확인).
2. **turn-state = REST vs WS msg**: REST 권장(§4). 최종 P3에서.
3. **user_id="demo" 고정** — 멀티탭/멀티유저 라이브 이벤트 공유됨. POC 무해, 로그인 도입(Sprint 16+) 시 재검토.
4. **POC 턴 = 수 초** → ④ 체감 약함(긴 워크플로=MVP+에서 의미). 정직 표시. 검증은 인위적 지연 mock로.
5. **서버 재시작** → `concurrency._active` 소실 → `is_running=false`(턴 실제로 안 돔, 정합). 정적 복원(③)으로 충분.
6. **race**: 스냅샷(todo 9 done)과 직후 라이브(todo 10)는 additive — 무해.

## 7. 제약
정적 복원 = 완료 메시지만. 진행 박스 = is_running 라이브 재구독으로만. (④ 없으면 박스 안 뜸 = 과거 버그 수정 유지.) POC 단일 client(clumi)+mock.
