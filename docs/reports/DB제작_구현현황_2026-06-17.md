## §1.5 ★ 저장 원칙 — 영속 vs 임시 (오너 확정 2026-06-17)
- **영속(DB Workspace 레이어)**: raw / normalized / computed / blended — 재사용·질의·감사 대상.
- **임시(파이프라인 State / Session)**: cleaning→normalization 전달용 *중간물(cleaned)* 등 run-내 통과물 — DB 레이어 X, 메모리 State로 step 간 전달(`consumes`/`produces`), run 끝나면 소멸.
- ★정정(경계감사 wm425xjo3): cleaning 도구의 `_storage:{layer:'normalized'}`는 **decorative(비활성)** — 실 persist는 진입점(runner=pipeline.cache.layer / API=caller layer)이 결정하고 `_`-prefix 키는 저장 전 제거됨. 즉 **과영속은 실제로 안 일어남**(내 직전 "과영속" 표현 정정). 진짜 이슈 = *힌트↔실정책 이원화*(catalog-drift 함정). → 정합책: 저장정책 SSOT화(`_storage` 힌트를 진입점이 실소비 vs 폐기+pipeline.cache 단일화). cleaned=State(임시) 방향은 유효. **DB 제작의 적재 consumer도 같은 이유로 `_storage`에 의존 말고 명시 save 경로 필요**(§2 G3와 동일).

## §3 구현 순서 (점검 권장)
1. **reserved 가드** — write_typed_table이 정형명 DROP 금지(먼저 막아야 이후 적재 안 삼킴).
2. **write_relational_table** — `(conn, client, table, rows, *, pk_cols, col_types, layer)` CREATE IF NOT EXISTS(명시 타입+PK) + ON CONFLICT(pk) UPSERT + `_lineage jsonb`. DROP 금지.
3. **translator 행 emitter** — `_CHANNELS` spec += keys·schema(pk/types). `_translate` SUM→행. naver_sa 매핑+그룹. 행단위 lineage. `_to_date`.
4. **적재 consumer** — translator.execute가 소스별 write_relational_table 호출.
5. **(G5 결정 반영)** google 제외 12테이블.
6. **blended step** — normalized 적재 후 PK=period UPSERT.
7. **행단위 검증 테스트** — 합 불변·PK non-null/유일·lineage 채움·교차레이어 동치.
