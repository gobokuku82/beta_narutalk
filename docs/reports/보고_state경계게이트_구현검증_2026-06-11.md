## 1. 한 줄 결론

**L3+L5 = 임시조치 아님 (영구 구조 장치 — 제어 평면 입구의 문지기). 단, 발원지(근본) 수정도 아님 — 그건 L4.**
유지가 맞고, L4(collector 참조 반환)를 얹어야 근본까지 완성된다. 되돌리면 잃는 것만 있음.

## 2. 층위 정리 — 무엇이 무엇을 고치나

```
[발원지]   collector 가 raw 데이터셋(104MB)을 결과로 반환            ← L4 가 고침 (계획서 별도, 허가 대기)
   ↓ 실행 중: RAM 상주 + _json_safe 딥카피(이벤트루프 수십초 블록) + 모든 다음 tool 에 전달
[경계]     tool 결과 → state 채널 진입                              ← ★L3 가 여기서 차단 (이번 구현)
   ↓ state 에 들어가면: checkpoint 영구저장 + WS 브라우저 전송 + 이후 모든 조회 비용
[미러]     execution_progress = 같은 내용 한 벌 더 (읽는 곳 0)        ← ★L5 제거 (이번 구현)
```

- **L3가 푼 것**: checkpoint 155MB→KB · WS ~312MB→KB · 대화 복원/목록 조회 비용 · response 재검증 비용 · (미래 어떤 tool의 누수도 차단 + warning 로그 관측).
- **L3가 못 푼 것 (정직)**: 실행 *중* RAM 104MB 상주, `_json_safe` 딥카피 CPU(이벤트루프 블록 — e2e 에서 ws keepalive 끊김으로 실증), previous_results 로 전 tool 에 전달. → **L4 몫.**
- **왜 L4 후에도 L3 유지?** L4는 collector(21개)의 계약 수정. L3는 *모든* tool에 대한 경계 강제 — 리뷰 데이터가 커지는 날, 새 tool이 데이터셋을 반환하는 날을 위한 안전망. 사용자 원칙 "게이트 > 컨벤션 기대" 정합. 둘은 중복이 아니라 다른 층위.

## 5. 검증 중 부수 발견 (기존 이슈 — 본 변경 무관 증명)

1. **레거시 비대 턴 2개**(155MB×2, "4월 로아스/ROAS" 대화)가 DB에 잔존 — 열린 브라우저의 목록 자동 refetch가 이걸 반복 역직렬화 → **모든 API ~2s 지연**(신규 경로는 8ms 분리 증명). **대화이력 🗑로 삭제 시 즉시 해소.**
2. e2e GA4 턴 halt: `kst_timezone_normalizer`가 collector produces 키를 source_id로 착각(`DataSourceNotFound`) — planner tool-배선 비결정(doc 39 §5)+drift 계열, 별도 과제. (슬림은 실행 후 경계에서만 — 인과 불가.)
3. 실행 중 `_json_safe` 딥카피가 이벤트루프 블록 → ws keepalive 오탐 — **L4가 잡을 몫의 실증.**
