## §1 무엇을·어떻게 측정했나
- **목적**: ROADMAP §0.1 ②축(데이터 의미 전달) 할루시의 *라이브 기준선*. "값은 맞는데 LLM이 단위·의미를 틀리게 전달하나(roas를 %로, salesAmt를 매출로)"를 실제 그래프 실행으로 관측.
- **방법**: `build_graph()`(cognitive→planning→execution→response) 헤드리스 + `ainvoke`. **실 LLM**(OpenAI gpt-5.4-mini, layer별) + **postgres canonical**(DATA_BACKEND=postgres) + clumi 프로필 배선(A3 ✅, cognitive가 client_id로 로드·주입). `require_review=False`로 HITL 우회. 패턴 = 기존 `probe_qa_e2e.py`.
- **판정(결정론 v1)**: 응답에 정답 수치 포함? + 그 수치 *바로 뒤* 인접 단위가 올바른가(배수/원/%)? — 전역 단위 등장이 아닌 **인접성** 검사(매출용 '원'이 roas 쿼리서 false-positive 나던 것 교정).

## §3 해석 (무엇을 입증했나)
- **①데이터 정확성 + ②단위 의미가 라이브에서 둘 다 작동** — 이전엔 "프롬프트에 사전이 들어갔다"만 봤는데, 이제 *실제 응답*이 ROAS를 "배"로, 금액을 "원"으로 냄.
- **S1-S3 의미배선이 작동하는 첫 라이브 정황** — summary_generator가 glossary를 받아(S1-S3) 단위를 안 틀림. (★단 인과 미입증 — §4.)

## §4 ★ 정직 경고 — 이건 "베이스라인의 절반"
1. **4개 다 단순 metric 조회 = happy path.** 전부 `summary_generator` 경로. **②축 위험이 가장 큰 해석 tool(insight_extractor·diagnoser·forecaster — S1-S3가 의미배선한 바로 그 tool들)은 안 거침.** "왜 CAC 올랐어?"(diagnose)·"ROAS 인사이트"(insight)가 진짜 시험대.
2. **A/B 부재 → S1-S3 효과 인과 미입증.** "지금 깨끗"만 봤지 "glossary 빼면 틀리나"는 안 봄. glossary on/off A/B라야 "S1-S3가 ②축을 줄였다"가 증명됨.
3. **판정기 결정론** — 숫자+인접단위만. 해석 프로즈(추론 둔갑·트랩 오독)는 LLM judge 필요.
4. **(별개) 응답에 raw `_dataref` 누수** — 모든 응답 꼬리에 "meta_ads_raw — _dataref: True · source_id… · where: data 레이어에서 self.ds…". ②축 아닌 **응답 청결** 이슈(rendering). 별 트랙.
5. 트랩(naver salesAmt=비용)은 canonical이 이미 해소해 LLM이 raw 트랩을 직접 안 봄 — 즉 이 경로에선 ②축이 *구조적으로* 안 터짐. ②축 진짜 위험은 LLM이 raw/중첩을 해석하는 지점.

## §5 ★ 결정 — 혼합 (오너 4기준 = ②의 아키텍처 / 현 방식 = 검증)

**오너 질문**: 현 방식(measure-first) vs 오너 4기준 vs 혼합?

**결정: 혼합. 이유 = 둘은 경쟁이 아니라 직교한다.**
- 오너 4기준 = ②를 *무엇으로 만들지*(아키텍처). 현 방식 = ②가 *먹히는지 어떻게 아는지*(검증). 양자택일이 아니라 한 쪽이 설계, 한 쪽이 가드레일.

**오너 4기준 ↔ 현 시스템 매핑** (실측 기반):
| 오너 기준 | = 시스템 | 상태 |
|---|---|---|
| 1. 쿼리 이해→계획서 | cognitive + planning | ✅ 작동(C2: op=measure·plan tools 정확) |
| 2. 계획대로 tool compose 실행 | execution | ✅ 작동(C2: canonical 값 산출) |
| 3. 데이터 메타/description/칼럼 컨텍스트 설계 | **②의 "의미 계층"(설계 반쪽)** | 🟡 MVP만(COL_DESC 평면 dict·_lineage). *설계된 layer* 아님 |
| 4. 단일 프롬프트 X·조립식 O(컨텍스트엔지) | **②의 "의미 배선"(전달 반쪽)** | 🟡 MVP만(yaml에 {glossary} 1블록). *조립 시스템* 아님 |

→ **오너의 3·4 = ROADMAP §0.1이 명명한 ②의 두 반쪽(의미 계층/의미 배선)의 *성숙판*이다.** S1-S3는 그 MVP였고("사전 dict + placeholder 1개 붙이기"), 오너 3·4는 제대로 된 아키텍처("설계된 메타 layer + 조립식 프롬프트")다. **오너 방향이 더 옳다.**

**그럼 왜 현 방식(측정)도 섞나** — P2·P4·C2의 공통 교훈: **측정 없이 지으면 헛짓**(P2·P4는 감사 주장이 틀렸고, C2는 단순경로가 이미 깨끗함을 보임). 즉 오너 아키텍처를 *어디에* 지을지는 측정이 알려준다. 단순 metric은 이미 ②축 0이니, 아키텍처 투자는 **해석 tool·트랩·중첩**(측정이 가리킬 실패처)에 집중해야 과투자를 피한다.

**혼합의 구체 형태 = measure-first로 감싼 오너 아키텍처:**
```
0 측정 완성   : 해석쿼리(insight/diagnose/forecast) + 트랩 + glossary on/off A/B → ②축 *실패처* 와 *S1-S3 인과* 확정
1 ③ 의미 계층 설계 : 메타/description/칼럼 desc 를 *설계된 layer* 로 (canonical _lineage·단위·트랩·소스별 — COL_DESC MVP 승격)
2 ④ 조립식 프롬프트 : 컨텍스트 *조각*(데이터사전·lineage·단위계약·few-shot)을 모듈로 조립하는 어셈블러 (단일 프롬프트 폐기)
3 재측정       : 같은 하네스 → ②축 감소 정량 입증
```

**④ 조립식 프롬프트 아키텍처 스케치** (오너 step 4 구체화):
- 지금: 각 tool yaml = 통짜 프롬프트 + `{glossary}` 1칸. (조립 아님, 중복·드리프트.)
- 목표: **컨텍스트 조각 레지스트리** — `[데이터 사전]`·`[계보/트랩]`·`[지표 정의]`·`[단위 계약]`·`[few-shot]` 각각 재사용 블록. **어셈블러**가 (tool, inputs, client)에 맞는 조각만 골라 조립. → 한 곳 고치면 전 tool 반영(SSOT), 필요한 의미만 주입(토큰 효율), 신규 tool은 조각 선언만.

### §7.1 ★ 정정 (오너 2026-06-18) — 위 둘째 줄은 거꾸로였다
**할루시 = 증상이지 작업 대상이 아니다.** "측정이 깨끗하면 아키텍처 긴급도 낮아짐"은 할루시를 *타깃*으로 둔 틀린 프레이밍. 올바른 전제 = **load-bearing 구조(②③④)를 제대로 만들면 → 할루시가 준다.** 측정은 그 인과를 *확인*하고 회귀를 잡는 도구지 *구조 작업을 할지 말지의 게이트가 아니다.* 현 ② 구조가 MVP(평면 COL_DESC·{glossary} 1칸)라 **불안정하다는 것 자체가** 제대로 만들 충분한 이유 — 단순경로 측정이 깨끗해도 미루지 않는다. (★단 load-bearing 한정: decorative 구조 tool/category는 제대로 해도 할루시 안 줆 = P4, 그래서 화장.) → ROADMAP §0.1 "원칙 = 구조 우선, 측정은 확인" 정합.
