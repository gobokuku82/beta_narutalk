## 0. 한 줄 요약

"고객마다 다 다르다"는 걱정은 사실 **두 개의 다른 문제**다 — (A) **저장 장소**(파일→DB)와 (B) **데이터 모양**(컬럼명이 회사마다 다름). (A)는 코드가 이미 잘 분리돼 있어 *나중에* 어댑터 1개면 되고(→ Postgres 설계 문서), **진짜 급소는 (B)** 다. (B)의 해결은 **"회사 컬럼명 → 시스템 표준명" 번역표 1장**을 **코드가** 읽어 입구에서 한 번 치환하는 것. 단 지금은 client가 clumi 1개라 *번역할 대상이 없으므로*, **지금 당장 할 일은 "핵심 컬럼 없으면 멈추기(fail-fast)" 하나뿐**이다.

## 1. 출발점 — 한 질문처럼 보이지만 사실 두 문제

| | (A) 저장 장소 문제 | (B) 데이터 모양 문제 |
|---|---|---|
| 질문 | "data 폴더 → 외부 DB로 가면?" | "회사마다 자료·테이블·칼럼이 다르면?" |
| 본질 | 데이터를 **어디 두나** | 데이터의 **컬럼명·구조가 회사마다 다른 걸 어떻게 흡수하나** |
| 비유 | **이사**(짐 그대로, 집만 바뀜) | **집집마다 가구 배치가 다름**(이사와 무관하게 늘 생김) |
| DB로 바꾸면 풀리나? | — | ❌ **안 풀림.** DB로 가도 'payment_amount vs amount'는 그대로 |
| 코드 위험 | 낮음(준비됨) | **높음(절반만 됨)** |
| 고치는 위치 | `data_sources/`·`workspace/` 두 폴더 | `normalizer`·`input schema`(저장소와 무관) |

**객관적 결론:** 사장님은 "DB 전환"을 큰일로 느끼지만, **코드가 실제로 깨지는 건 (B)** 다. 두 번째 고객을 붙이는 순간 DB와 무관하게 터진다. → **우선순위는 B ≥ A.**

## 4. 질문 B (컬럼 가변) — 핵심. 해결 = "번역표"

### 4.1 갈림길 — "문서를 읽는다"의 두 가지 뜻 (반드시 구분)

"컬럼 설명을 문서로 빼서 읽게 하자"는 발상은 **정석(데이터 사전/시맨틱 레이어)**이고 방향이 맞다. 그러나 **누가 읽느냐**로 길이 갈린다.

| | (A안) **코드**가 번역표를 읽음 | (B안) **LLM**이 설명글을 읽고 매번 해석 |
|---|---|---|
| 문서 | `amount → payment_amount` (정해진 짝) | `"amount: 결제 금액"` (설명 문장) |
| 동작 | 기계가 그대로 치환 | AI가 "이게 매출이겠지" 추측 |
| 정확도 | ✅ 항상 같음, 검증 가능 | ⚠️ 실행마다 다를 수 있음 |
| 속도/비용 | 즉시·공짜 | 질문마다 느림·토큰 |

**판정:** 컬럼명 차이는 **반드시 (A안)** — 마케터 매출 숫자는 정확·반복가능해야 한다. LLM이 매 질문마다 컬럼 의미를 추측하면 어제와 오늘 답이 달라질 수 있다(돈 계산을 추측에 맡기는 격). (B안)식 자연어 설명은 버리지 말되 **다른 일**에 쓴다 → "이 회사가 무엇을 가졌나/뭐라 부르나"(의미·보유) 이해. 이건 `clumi.yaml`이 이미 함.

### 4.2 그래서 문서는 둘로 갈라진다 (각자 일이 다름)

| 문서 | 모양 | 누가 읽나 | 무슨 일 |
|---|---|---|---|
| ① **번역표** | 구조화(컬럼→표준명 짝) | **코드**(normalizer) | 회사별 컬럼명을 표준명으로 기계 치환 ← **새로 필요** |
| ② **의미·보유 선언** | 자연어 자유 | **LLM**(cognitive) | "회사가 뭘 가졌나/뭐라 부르나" ← `clumi.yaml` 이미 함 |

> **"형태는 아무거나"는 절반만 맞다.** ②(LLM용)는 자유 형식 OK. ①(코드용)은 **형태가 중요** — 기계가 읽어야 하니 `컬럼명 → 표준명` 짝이 또렷한 표여야 한다.

### 4.3 구체 예시 — 기존 `data_dictionary.csv`에 칸 2개만 더하면 번역표가 된다

현재 [clumi_data_dictionary.csv](../../data/clumi/description/clumi_data_dictionary.csv)는 이미 이렇게 생겼다(사람용):

```
column_name,  data_type, description,          example,    is_key
payment_amount, decimal, "주문 결제 금액(원)",   275000.0,   
order_status,   string,  "주문상태(취소=C40)",   C40,        
member_grade,   string,  "회원 등급",            VIP,        
```

여기에 **`standard_name`(표준명)·`required`(필수)** 두 칸만 더하면 "기계가 읽는 번역표"가 된다. 회사별로 한 장씩:

**시스템 표준 정의 (공통 — 1장)**

| standard_name | 의미 | required | 표준 타입 |
|---|---|---|---|
| `payment_amount` | 주문 결제 금액(원) | ✅ Y | decimal |
| `order_status` | 주문상태(취소=C40) | ✅ Y | string |
| `order_date` | 주문 일시 | ✅ Y | date |
| `member_grade` | 회원 등급 | ⬜ N | string |

**clumi 번역표 (회사별 — 1장)**

| standard_name | clumi raw 컬럼 |
|---|---|
| `payment_amount` | `payment_amount` (같음) |
| `order_status` | `order_status` (같음) |
| `order_date` | `order_date` (같음) |
| `member_grade` | `member_grade` (같음) |

**(가상) barfdog 번역표 (회사별 — 1장)**

| standard_name | barfdog raw 컬럼 | 메모 |
|---|---|---|
| `payment_amount` | `order_total` | 이름만 다름 → 치환 |
| `order_status` | `status` | 이름만 다름 → 치환 |
| `order_date` | `ordered_at` | 이름만 다름 → 치환 |
| `member_grade` | *(없음)* | barfdog은 등급 개념 없음 → 등급 분석 **건너뜀** |

이 표 한 장이 **세 가지를 동시에** 해결한다:
1. **번역**: `order_total` → `payment_amount` 로 입구에서 치환 → tool은 무변경(항상 표준명만 봄).
2. **fail-fast(§5의 "지금 할 일")**: `required=Y`인데 매칭 raw가 없으면 → **0 대신 멈추고 "이 회사 데이터에 매출 컬럼 없음" 알림**.
3. **보유 선언**: `member_grade=(없음)` → 그 회사엔 등급 분석을 **시도조차 안 함**(틀린 답 방지). ← LLM이 읽는 ②와 연결.

> 기계가 읽을 실제 형태는 CSV/YAML 등 구조화면 무엇이든 OK. 예(개념만, 코드 아님):
> ```yaml
> # data/{client}/column_map.yaml
> payment_amount: order_total      # 회사 raw 컬럼명
> order_status:   status
> order_date:     ordered_at
> member_grade:   null             # 미보유 → skip
> ```

### 4.4 "언제" 번역하나 — 입구에서 한 번

데이터가 **들어올 때 한 번** 번역해 표준 모양으로 저장(raw→cleaned 단계). 질문마다 매번 해석하면 느리고 들쭉날쭉. → "입구에서 통역 한 번, 안에서는 다 같은 말."

## 5. 지금 / 나중 (우선순위 — 과설계 경계)

| 시점 | 할 일 | 위치 | 왜 지금/나중인가 |
|---|---|---|---|
| **지금(유일)** | 핵심 컬럼 없으면 **멈추기**(silent 오답 차단) | [schemas/inputs/](../../backend/app/schemas/inputs/) 검증 추가 | 파일/DB 무관하게 위험. 비용 작음. 잘못된 숫자로 마케팅 결정하는 사고 차단 |
| 2번째 고객 생길 때 | **번역표** + 그걸 읽는 normalizer(주문/고객으로 확장) | `data/{client}/column_map.yaml` + `ADS_FIELD_ALIASES` 패턴 | 지금은 client가 clumi 1개 → *번역할 대상이 없음.* 빈 기계 만들기 = 헛수고 |
| 실서비스(DB) 갈 때 | 읽기/쓰기 어댑터 + 스위치 | `data_sources/db.py`·`workspace/db.py` 신규 (→ [Postgres 설계](../_claude/data/data_db_postgres_설계_2026-06-07.md)) | "실서비스에서" 필요. 인터페이스는 이미 준비됨 |

**핵심:** "문서를 만든다"는 필요조건일 뿐, **그 문서를 읽고 행동하는 주체(치환 코드)** 가 진짜다. 문서만 만들고 끝내면 시스템은 그대로 raw 컬럼에서 멈춘다.

## 6. 객관적 주의 (놓치기 쉬운 함정)

1. **"DB로 가면 다 풀린다"는 오해.** (B) 컬럼 차이는 저장소와 무관. DB부터 하면 컬럼 문제는 그대로 남는다.
2. **회사별 "맞춤 코드 복제"는 함정.** input schema를 회사 수만큼 포크하면 17개 tool import가 분기 폭발. **코드가 아니라 번역표(데이터)** 로 풀어야 싸다.
3. **번역표는 "이름 다름"만 푼다.** 개념 자체가 없는 경우(등급 미보유 등)는 번역 불가 → "보유 선언"으로 분석을 건너뛰게(이 분기 로직은 아직 미구현).
4. **"준비됨" ≠ "구현됨".** 추상 인터페이스는 됐지만 DB 구현체·delete/update는 0줄. 실측 기준 사실.
5. **schema-per-client vs client_id 컬럼**은 DB 갈 때 결정. client 1개 POC에선 가치 0(→ Postgres 설계 문서에서 schema-per-client 권장 확정).
