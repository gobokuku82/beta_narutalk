# 아키텍처 의도-정합 점검보고서 (2026-05-28)

> **목적**: 사용자(초보자)의 *의도대로* 구조가 만들어졌는지 **코드 근거로** 점검.
> "느낌"이 아니라 파일·라인 증거로. data 영역을 잘 모른다는 전제에서, 모르는 용어
> (`workspace`·`core`)도 풀어서 설명한다.
>
> 점검 대상 = 사용자가 직접 제기한 의문 3가지:
> 1. clumi(클라이언트=가상 회사명)가 *시스템 정체성*으로 잘못 박혀 있나?
> 2. tool 이 "어떤 회사/데이터인지 모르는" 순수 함수인가? 권한 구조가 맞나?
> 3. 클라이언트를 *추가*할 수 있는 구조인가, 아니면 clumi 에 *끼워맞춰진* 구조인가?

## 1. 한 줄 결론 (큰 그림)

**골격은 의도대로 맞다. 그러나 중간에 결정을 바꾸며 생긴 "꼬임"과 "이름 새어듦"이 남아 있다.**

| | 상태 |
|---|---|
| ✅ **레이어 분리** (tool / pipeline / data_sources+schemas / workspace / core / ml_models / frontend) | 의도대로 존재 |
| ✅ **client 파라미터 흐름** (드롭다운 → 페이지 → API → pipeline → tool → data_sources) | **end-to-end 로 흐름** (전부 박혀있는 게 아님) |
| 🟠 **clumi 이름 새어듦** | `clumi_loader.py`·`clumi_outputs.py`(클라명 모듈) + 거의 모든 tool 의 `DEFAULT_CLIENT="clumi"` |
| 🟠 **같은 책임의 평행 시스템 2벌** | 중간 의사결정 변경의 잔재 (아래 §6) |
| 🟠 **클라이언트 추가** | 골격은 가능. 단 **정규화(컬럼명 통일) 레이어가 없어 "새 회사 데이터가 clumi 와 똑같은 컬럼명"일 때만 작동** |

→ **시스템 정체성은 clumi 가 아니다.** 앱 이름은 `APP_NAME = "OctorAD"`([backend/app/core/config.py:27](../../backend/app/core/config.py#L27)), 화면 로고도 `OctorAD`([frontend/src/components/layout/TopBar.tsx:67](../../frontend/src/components/layout/TopBar.tsx#L67)). clumi 는 **데이터 폴더/기본 클라이언트**로만 쓰이는 게 정상인데, *코드 모듈 이름*에까지 새어든 게 문제.

## 2. 의도한 설계 vs 현실 — 레이어별 verdict

사용자가 말한 의도(왼쪽)와 실제 코드(가운데)를 대조.

| 레이어 | 사용자 의도 | 현실 (코드 근거) | 정합 |
|---|---|---|:--:|
| **tool** | 작은 단위 함수, 카테고리별, *회사/데이터 모름* | 신규 52개 = 표준 schema 경유 ✅ / 레거시 25개 = raw 컬럼·`clumi_loader` 직접 ❌. 전반적으로 `DEFAULT_CLIENT="clumi"` 기본값 박힘 | 🟠 |
| **pipeline** | 각 함수들의 조합식 | `flows/*.yaml` 52개, 순수 선언적(실행코드 0). 컬럼 하드코딩 0 (DC-PERM-2/5 PASS) | 🟢 |
| **data_sources** | 데이터 로드 관리 | `data/{client}/raw/{file}` client별 파일. 계산 0 (DC-PERM-3 PASS). 단 **컬럼명 정규화 없음** | 🟢🟠 |
| **schemas** | 데이터 구조 정의 | `inputs/`(입력 Pydantic) + `outputs/`(출력 Pydantic) ✅. 단 `models/clumi_outputs.py` 가 **평행 존재** | 🟢🟠 |
| **workspace** | *(모르겠다 하심)* | tool 산출물 저장·공유 + 캐시 (= data_sources 의 *출력* 짝). 정상 레이어 | 🟢 |
| **core** | *(모르겠다 하심)* | 앱 전역 설정·로깅·에러 (회사 무관 인프라) | 🟢 |
| **ml_models** | 현재 ml 없어 mock | ABC + Mock + Llm 어댑터 ✅. tool 은 어댑터 경유(DC-PERM-6: 신규 준수) | 🟢 |
| **frontend** | 계산식을 *표현만* | pipeline 산출을 차트로 표시 ✅. client 드롭다운 흐름 존재 ✅ | 🟢 |

**해석**: 🟢 5개 레이어는 의도대로다. 문제는 **tool 레이어(🟠)** 하나에 집중돼 있고, schemas/data_sources 에 *평행 잔재*(🟠)가 붙어 있다.

## 3. 모르겠다 하신 두 레이어 설명 (data 영역 비전공자용)

### `core/` = 앱의 *공통 설정·기반*
- 파일: [config.py](../../backend/app/core/config.py)(설정값), [logging.py](../../backend/app/core/logging.py)(로그), [errors.py](../../backend/app/core/errors.py)(에러 형식), [decorators.py](../../backend/app/core/decorators.py).
- 비유: 건물의 **전기·수도·주소** 같은 기반 설비. 회사(clumi/blooming)와 무관. 여기엔 clumi 가 없다(정상).

### `workspace/` = tool 들이 만든 *산출물 저장·공유 창고*
- 파일: [base.py](../../backend/app/workspace/base.py)(추상), [file.py](../../backend/app/workspace/file.py)(POC 파일 구현).
- **data_sources 와 짝**: `data_sources` = 바깥 raw 데이터를 *가져오는 입구*, `workspace` = tool 이 계산한 결과를 *저장하고 다음 tool/캐시로 넘기는 창고*.
- 3층(`raw` / `cleaned` / `computed`)으로 산출물을 보관. 같은 질문을 또 물으면 다시 계산 안 하고 창고에서 꺼냄(캐시).
- 비유: data_sources = **식자재 입고**, workspace = **조리된 음식 보관 냉장고**.

## 4. clumi 507건의 *역할별* 분류 (작은 그림)

`clumi` 라는 글자가 backend 에 507번 나오지만, **셋 중 무엇이냐가 중요**하다.

### 🟢 정당 — clumi = "한 클라이언트의 데이터" (이대로 OK)
- `data/clumi/raw/...` 경로 — 그 회사 데이터가 그 폴더에 있는 게 맞음.
- 테스트 fixture (`tests/.../test_*.py` 의 `client="clumi"`) — 테스트는 샘플 회사 하나로 검증.
- 화면/API 의 기본 클라이언트 값 — POC 가 단일 client 라 합리적.

### 🟠 냄새 — 회사명이 *코드*에 기본값으로 박힘 (정리 권장)
- 거의 모든 tool 상단 `DEFAULT_CLIENT = "clumi"` — tool 은 회사를 *모름*이 의도인데, "안 주면 clumi" 기본값이 박혀 있음. (예: [campaigns_aggregate.py:21](../../backend/app/dream_agent/tools/metrics/campaigns_aggregate.py#L21), [revenue_total.py:25](../../backend/app/dream_agent/tools/metrics/revenue_total.py#L25))
- [workspace/base.py:29](../../backend/app/workspace/base.py#L29) 의 예시 주석 `PostgresWorkspace: clumi_{layer}.<table>` — 추상 레이어 설명에 회사명.

### 🔴 꼬임 — 제거됐어야 할 *클라명 모듈* (정체성 착각의 핵심)
- **[`tools/shared/clumi_loader.py`](../../backend/app/dream_agent/tools/shared/clumi_loader.py)** — 파일 *이름*이 클라이언트명. 본인 주석에 *"Step 3·4 에서 app/data_sources/ 의 DataSource 로 흡수 예정 (load_clumi_source 제거)"*([clumi_loader.py:27](../../backend/app/dream_agent/tools/shared/clumi_loader.py#L27))라고 적혀 있는데 **아직 살아서**, raw collector 전체 + 레거시 tool 5개가 의존 중. → "회사 이름이 곧 데이터 로더"라는 착각이 코드로 굳어진 상태.
- **[`models/clumi_outputs.py`](../../backend/app/dream_agent/models/clumi_outputs.py)** — `RevenueOutput`·`RoasOutput` 등은 **clumi 전용이 아니라 일반 마케팅 출력 스키마**인데 "clumi 대시보드용"이라 클라명으로 묶임. 표준 위치 `schemas/outputs/` 와 **평행 존재**.
- [revenue_total.py:65](../../backend/app/dream_agent/tools/metrics/revenue_total.py#L65) 의 stale 경로 `data/clumi/clumi_mock_05_orders.csv` — 폴더 재정리(`data/clumi/raw/`) 전의 옛 경로가 meta 에 남음.

## 5. 사용자 의문 3개에 대한 직접 답

### Q1. tool 이 "어떤 회사/데이터인지 모르는" 순수 함수인가?
- **신규 tool (52개)**: 실질적으로 **모름** ✅. client 를 *파라미터*로 받고, 컬럼명은 `schemas/inputs/` 의 표준 Pydantic 필드로 접근 (raw 컬럼 직접 안 봄).
- **레거시 tool (25개)**: **앎** ❌. `df["payment_amount"]` 처럼 그 회사 데이터 컬럼을 직접 참조하고 `clumi_loader` 를 호출.
- **공통 냄새**: 둘 다 `DEFAULT_CLIENT="clumi"` 기본값 보유 → "회사를 모름" 원칙에 흠집.

### Q2. 권한 구조가 맞나? (ADR-027 5 주체)
- ADR-027 의도(tool=순수계산 / data_sources=로드·매핑 / ml_models=추론 / pipeline=조합 / maker=정의)는 **신규 레이어에서 100% 준수**. 방금 만든 **DC-PERM-1~6 정적 검사로 입증** ([backend/tests/permissions/test_dc_perm.py](../../backend/tests/permissions/test_dc_perm.py)):
  - DC-PERM-2/3/4/5 = 전 코드 PASS, DC-PERM-1/6 = 신규 PASS / 레거시 25개만 KNOWN DEBT.
- 즉 **권한 구조 자체는 맞고**, 안 맞는 건 *옛날에 만든 레거시 25개 tool*뿐.

### Q3. 클라이언트를 추가할 수 있나? ("끼워맞춤" 직관의 정체)
- **골격은 가능** ✅: 화면 드롭다운 `AVAILABLE_CLIENTS`([TopBar.tsx:28](../../frontend/src/components/layout/TopBar.tsx#L28)) → store → 페이지 `client`([DashboardV1Page.tsx:20](../../frontend/src/features/dashboard_v1/DashboardV1Page.tsx#L20)) → API → pipeline `${client}` → tool → `data/{client}/raw/`. client 가 *변수*로 끝까지 흐른다.
- **그러나 함정** 🟠: tool 은 "컬럼명이 clumi 와 똑같다"고 가정한다. 새 회사 CSV 의 컬럼명이 다르면(예: `payment_amount` 대신 `결제금액`) **tool 이 깨진다**. 이 컬럼명을 통일해 주는 **정규화(normalizer) 레이어가 아직 없다.**
- → **이것이 "끼워맞춰져 있다"는 직관의 정확한 정체**: client 는 파라미터인데, *데이터 모양*은 clumi 한 종류만 가정. (이는 POC = clumi 단일 client 결정에 따라 **의도적으로 MVP+ 로 연기**된 부분 + clumi 명 잔재가 섞인 것.)

## 6. 중간에 결정을 바꾸며 생긴 "꼬임" — 같은 책임의 평행 시스템 2벌

사용자가 말한 *"중간에 데이터·결정을 바꾸며 구조가 꼬인 부분"*의 실체. **하나의 일에 옛 방식과 새 방식이 동시에 살아 있다.**

| # | 같은 책임 | 옛 방식 (제거 대상) | 새 방식 (의도) | 증거 |
|---|---|---|---|---|
| 1 | raw 소스 매핑 | `clumi_loader.CLUMI_SOURCES` (file_no, 클라명) | `data_sources.DEFAULT_MAPPING` (source_id) | [file.py:31](../../backend/app/data_sources/file.py#L31) ↔ [clumi_loader.py:28](../../backend/app/dream_agent/tools/shared/clumi_loader.py#L28) |
| 2 | 출력 스키마 | `models/clumi_outputs.py` (클라명) | `schemas/outputs/` (표준) | validator 가 **둘 다 스캔** [validator.py:31](../../backend/app/pipelines/validator.py#L31) |
| 3 | 입력 데이터 접근 | 레거시 tool 의 raw `df["..."]` | `schemas/inputs/` Pydantic | DC-PERM-1 결과 |
| 4 | 산출물 저장 | 레거시 tool 자체 `workspace.save()` | Runner 가 캐시 소유 | [runner.py:11](../../backend/app/pipelines/runner.py#L11) 주석 |

→ 각 쌍에서 **"새 방식"이 의도**고, "옛 방식"은 DataSource·schemas·Runner 도입 때 *흡수·제거됐어야* 하는데 남았다. 평행 존재 자체가 "구조가 꼬였다"는 느낌의 근원.

## 6.5 수집 2-layer 미구현 — mock_api ↔ raw (오류, 2026-05-28 추가)

사용자 의도 = **2단계 수집**:
`data/mock_api/{client}/`(외부 API mock = "API가 돌려주는 raw") → **외부커넥터가 호출·수집** → `data/{client}/raw/`(내 서버에 저장한 raw) → 하류 tool(정제·지표·분석).

**오류 — 이 수집 단계가 코드에 없다**:
- `mock_api` 참조 코드 = **0건 (고아)**. 데이터사전(`clumi_data_dictionary.csv`)·스키마다이어그램도 `mock_api/clumi/` 에만 있고 코드와 단절.
- `FileDataSource` 는 `data/{client}/raw/` 를 **직접** 읽음 → `mock_api`(API) 단계를 건너뜀.
- `raw/` 는 `mock_api/` 를 **수동 복사·리네임**(`clumi_mock_NN_*` → semantic)한 사본. "커넥터가 API에서 가져와 저장"이 실제로 일어나지 않음.
- `mock_api/clumi/` 엔 외부(meta·naver) + 내부(orders·customers)가 **섞여** 있음 (외부/내부 미분리).

**고쳐야**: ① 외부커넥터가 `mock_api` 를 읽어(=API 호출 mock) `raw` 에 저장하는 수집 단계 구현 ② 외부/내부 분리 ③ mock→실API swap seam 을 `data_sources` 한 곳에. (네이밍·내부 mock 위치는 결정 대기)

**핵심 메시지 (초보자용 요약)**:
- 큰 구조는 **틀리지 않았다**. 무서워할 상황 아님.
- 고칠 핵심은 **딱 하나**: "옛날 clumi 전용으로 만든 레거시 25개 tool 과 clumi 이름이 붙은 모듈 2개"를, 이미 만들어 둔 **표준 방식(schemas·DataSource)으로 갈아끼우는 것.**
- 멀티 client 의 마지막 퍼즐(normalizer)은 **진짜 2번째 회사가 올 때** 하면 된다(지금 안 해도 정상).

## 부록 C. tool ↔ data layer 전수 분류 (사용자 의도 #6 기준, 2026-05-28)

> 기준: **외부 데이터 접근**(`self.ds.get`·`workspace.save/load`·`load_clumi_source`·`load_mock_csv`·`pd.read_csv`·`open`)을
> tool 안에서 하면 위반(의도 #6 "tool은 데이터를 직접 조회/저장 안 함"). **단 수집(collection)은 fetch가 본분이라 정상.**
> 내부 객체 접근(`dict.get`·`df.groupby`·`getattr`·`previous_results.get`)은 위반 아님.

### `self.ds.get()` = 외부 파일 직접 읽기
- `self.ds` = tool 에 주입된 `DataSource`([base_tool.py:26](../../backend/app/dream_agent/tools/base_tool.py#L26)) = 표준구조 crud/repository 역할.
- `.get(client, source_id)` → `data/{client}/raw/{file}` 디스크 읽기([file.py:99](../../backend/app/data_sources/file.py#L99)). → 위반.
